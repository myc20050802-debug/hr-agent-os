B 端 HR AI Agent SaaS 平台 · 产品需求草稿（PRD Draft v0.9）

产品代号：HR-Agent OS（暂定名，可替换） 文档用途：产品立项沟通 + PRD 撰写底稿 + 研发排期输入 阅读方式：非技术同学只看「📌 一句话结论」和表格；技术同学重点看第二、四、五部分 一句话概括：把 HR 每天重复问、重复填、重复催的活儿，交给四个会自己拆任务、会自己调系统的 AI 智能体去干，HR 只做「拍板」和「兜底」。

0. 先统一语言（术语表，通俗版）

术语说人话
Agent（智能体）一个能听懂目标、自己拆步骤、自己动手干活的 AI 员工。比如你说「把这批简历筛一遍」，它会自己决定先读 JD、再读简历、再打分、最后给你一张排序表
LLM（大模型）Agent 的「大脑」，负责理解语言和做判断，但它不能自己去查系统数据
Tool / 工具调用Agent 的「手」。它要查考勤、发邮件、建入职单，都得通过工具去调系统的接口
RAG（检索增强）Agent 的「翻手册」能力：先在你的公司制度文档里找到依据，再回答员工，避免瞎编
Workflow（工作流）固定的流水线，步骤写死、顺序固定，比如「入职 7 天前发提醒」——这种不需要 AI，用规则跑更省钱更可靠
HITL（人工介入）高风险动作必须停下来等人点「同意」。比如给候选人发 Offer，AI 只能起草，人必须签字
SaaS 多租户一套系统同时服务很多家公司，数据互相绝对隔离，A 公司永远看不到 B 公司的数据
关键工作原则（贯穿全文）：Agent 负责判断，Workflow 负责执行，规则/代码负责约束，人负责治理。 凡是一句 if-else 能搞定的事，绝不用大模型。这是这套产品能不能赚钱的生死线。

第一部分 · 产品定位、目标客户与核心价值

1.1 📌 一句话定位

面向 200～5000 人规模企业的「HR 数字员工平台」：把招聘、入转调离、员工咨询、人力报表四件事，从「HR 手工操作」升级为「AI 自主执行 + 人审核确认」，HR 从执行者变成管理者。

1.2 现在的痛，到底痛在哪（As-Is 现状）

不要直接抄需求，先看真实场景。以下是我们调研得到的典型一天（As-Is）：

序号HR 的真实一天耗时病根（Root Cause）
1翻 80 份简历，逐个看学历/年限/技能，凭感觉分堆3～4 小时判断标准在脑子里，没有结构化，无法复用
2挨个给候选人打电话/发微信约面试，来回改时间1.5 小时协调类工作无法批量处理
3员工微信问「年假还剩几天」「社保基数怎么算」，一天被打断 20 次2 小时制度文档写得很全，但员工懒得翻、HR 懒得答
4每月手工扒考勤、做招聘漏斗、拼周报4 小时/月数据散在 ATS、考勤机、Excel 里，靠人工搬运
5入职材料催 8 遍还收不齐，转正日期记错导致纠纷隐性风险流程靠人记，没有系统盯着

共性病根一句话：HR 的工作 80% 是「查资料 + 搬数据 + 催流程」，只有 20% 才是「做判断」。

而这 80% 恰好是大模型和 Agent 最擅长、也最容易被量化的部分。

1.3 目标客户分层

分层规模典型特征我们卖什么客单预期
主力客群（一期）200～1000 人有 HR 团队 3～10 人，用飞书/钉钉，ATS 可能只是 Excel招聘 Agent + 员工自助 Agent中等
扩展客群（二期）1000～5000 人有独立 HRIS/OA，流程复杂、合规要求高全模块 + Agent 编排 + 私有化部署高
长尾（三期，标准化）50～200 人只有 1～2 个 HR，最痛但最没钱单点 SaaS（只买员工自助 + 简历筛选）低，走量

一期不建议碰：50 人以下（付费能力弱、决策周期却一样长）、以及超大型集团（定制化黑洞，会拖垮交付）。

1.4 核心价值：卖的不是 AI，是三个数字

价值主张客户语言（销售话术）对应可量化指标
省时间「你们 HR 每天花 3 小时筛简历，我们能压到 20 分钟复核」简历初筛人效提升 ≥ 70%
少出错「转正漏提醒、材料收不齐这种事，系统会替你盯着，出事有留痕」流程逾期率下降 ≥ 60%
能说清「老板问上个月招聘情况，30 秒出一张漏斗图，不用现算」报表产出时间从 4 小时 → 5 分钟

1.5 核心价值链路（KPI 树）

text
业务目标：让 HR 团队用同样人数，支撑更多员工 / 更快招聘
  └─ 北极星指标（North Star）：每周由 AI 完成并被采纳的 HR 任务数（Accepted AI Tasks / Week）
       ├─ 业务 KPI：招聘周期（Time to Hire）、单人 HR 支持员工数、流程逾期率
       ├─ 产品指标：Agent 任务完成率、采纳率、人工接管率、周活跃 HR 数
       ├─ AI 指标：简历打分与人工判断一致率、问答有依据率（引用命中率）、幻觉率
       └─ 护栏指标（Guardrail）：越权访问次数（必须为 0）、敏感信息外泄次数（0）、高风险动作未经审批执行数（0）
为什么要护栏指标？ 因为 B 端 HR 系统一旦泄露简历或错发 Offer，客户会直接解约。护栏指标不为 0，前面所有增长都是泡沫。

1.6 明确不做什么（Non-goals）

不做原因
不做完整 HRIS/薪酬核算系统这是北森/Workday 的地盘，我们做 AI 层，通过接口读写他们
不做自动发 Offer / 自动辞退高风险不可逆，法律与舆情成本远高于省下的工时
不做「全自动无人招聘」招聘本质是人的判断，AI 做的是「排好序 + 备好材料」
不做简历爬虫抓取数据来源必须合法授权，否则是给客户埋雷
一期不做多模态视频面试分析反歧视合规风险高，且技术不成熟，容易被投诉

2.2 各层职责表（谁干什么，别越界）

层核心职责关键技术点常见坑
① 前端展现让人看得懂、点得动、能撤销支持表单 + 对话 + 看板三种形态混用，不要做成纯聊天窗口所有事都塞进聊天框，用户找不到历史记录
② Agent 调度拆任务、发工具、卡权限、逼人工审核编排引擎 + 工具注册中心 + HITL 闸门把业务逻辑写进 Prompt，导致不可测试、不可审计
③ 大模型提供理解与生成能力多模型路由：便宜模型干粗活，强模型干细活所有任务都调最贵模型，成本失控
④ 能力/数据提供事实依据向量库 + 业务库；事实以业务库为准，知识库只做解释让向量库里的过期制度文档覆盖真实考勤数据
⑤ 第三方对接真正去执行动作统一适配器 + 幂等键 + 失败重试没有幂等，重试一次就发出两封面试邀请
⑥ 基础设施隔离、审计、可恢复行级租户隔离 + 字段级脱敏多租户共用表却忘了加 tenant_id 过滤

2.4 一条数据流把架构串起来（招聘 Agent 示例）

text
HR 说：帮我筛一下「高级 Java 工程师」这个岗位的新简历
  │
  ├─[② 调度层] 意图识别 → 生成任务计划（Task Plan）：
  │      步骤1 读取岗位 JD           → 工具：ATS.getJob(jobId)
  │      步骤2 拉取近 3 日新简历      → 工具：ATS.listResumes(jobId, since)
  │      步骤3 解析简历为结构化字段   → 工具：Resume.parse（OCR+信息抽取）
  │      步骤4 按 JD 要求逐项打分     → 工具：LLM.rank（结构化输出 JSON）
  │      步骤5 敏感信息脱敏          → 工具：PII.mask（姓名/电话/性别/年龄）
  │      步骤6 写回 ATS 并生成推荐表   → 工具：ATS.updateStage（需人工确认）
  │
  ├─[③ 模型层] 步骤4 调推理模型；步骤3 调 OCR + 抽取模型；步骤5 走规则，不调模型
  ├─[④ 数据层] 步骤1/2 读业务库（权威事实）；步骤4 引用岗位胜任力标准（知识库）
  ├─[⑤ 对接层] 步骤1/2/6 调 ATS；输出结果同时推送飞书卡片给 HR
  └─[⑥ 治理层] 全程落 Trace：谁发起、调了哪些工具、每步耗时、token 花费、是否触发审核

第三部分 · 分模块详细功能

3.1 招聘 Agent

岗位定位：HR 的「招聘助理」，负责把「找简历→约面试→准备面试→发 Offer 前置材料」这条链路做工业化。

3.1.1 功能总览

子功能AI 做什么人做什么自动化等级
① JD 生成与优化根据岗位需求草稿生成完整 JD、优化措辞、检查歧视性用语修改并发布L2（AI 生成、人确认）
② 简历解析把 PDF/图片简历变成结构化字段处理解析失败件L4（自动执行、异常人工）
③ 简历筛选打分按 JD 硬性条件 + 能力项打分并排序复核 Top 名单L2（AI 生成、人确认）
④ 候选人邀约与调度生成邀约话术、给时间建议、发信、催确认异常/拒绝时介入L3（执行前确认，可开自动）
⑤ 面试辅助生成面试提纲、追问建议、面试纪要面试官主导L1（AI 建议）
⑥ Offer 及入职前置生成 Offer 草稿、薪资对比提示、入职材料清单审批与签署L1～L2（严禁 L4）

3.1.2 各子功能详细规则

① JD 生成优化

  • 输入：岗位名称、部门、汇报对象、薪资范围、必须项/加分项（可用自然语言写，如「3 年以上 Java，懂高并发，能接受出差」，只写一条也可以）
  • 输出：结构化 JD（岗位职责 5～8 条、任职要求、加分项、我们提供什么）
  • 任职要求六维度（核心要求，不允许只输出一条干巴巴的要求）：
维度内容来源
专业技能HR 已填内容原样保留 + 行业技能词库中未被提到的核心技能补位
工作经验HR 已填年限要求 + 该行业的经历特征（如制造业看现场经验、销售看完整销售周期）
学历背景按岗位设定的学历门槛生成 + 行业对口专业方向
综合素质行业化职业素养（如医疗看重查对制度、金融看重合规红线）
软技能跨部门协作、抗压、学习力等行业化表述
加分项HR 已填优先；已填 ≥3 条则不再叠加模板，避免同义重复
  • 关键约束：HR 自己写的那条要求必须原样保留并归位到对应维度，AI 只做补齐与专业化，不改写原句（避免 HR 认不出自己的岗位）
  • 内置规则（必须做）：
  • 歧视性用词扫描：性别、婚育、年龄（「35 岁以下」）、地域、院校层级、外貌 → 命中即黄色警告并给替换建议
  • 法律话术检查：避免「试用期不合格不付工资」等违法表述
  • 验收：歧视词拦截率 100%（回归集至少 30 条样本）；单条输入 → 输出 ≥5 维度、≥12 条任职要求

② 简历解析

  • 抽取字段：姓名、联系方式、教育经历（学校/专业/学历/时间）、工作经历（公司/岗位/起止/职责）、技能标签、项目经历
  • 支持格式：PDF（含扫描件 OCR）、Word、图片、ATS 结构化字段
  • 质量要求：关键字段（学历、工作年限、最近一家公司）抽取准确率 ≥ 95%；解析失败必须显式标红「需人工补录」，不允许猜
  • 脱敏：解析完成后，送入排序环节前先做 PII 脱敏（见第四部分）

③ 简历筛选打分（本模块最核心，也最容易翻车）

  • 打分维度必须显式配置，不能是黑盒：
维度权重（可配）判定方式
硬性门槛（学历/证书/工作年限）一票否决项规则判定，不调模型
技能匹配度40%模型判断 + 技能词典
行业/业务匹配度30%模型判断
稳定性（跳槽频率）15%规则计算
加分项（开源、专利、大厂背景）15%模型 + 规则
  • 输出：分数（0～100）+ 推荐等级（强烈推荐/可聊/不合适） + 逐条理由（引用简历原句）
  • 强制约束：
  • 性别、年龄、婚育、户籍、照片不得进入打分输入（技术手段：进入模型前物理删除字段）
  • 每条分数必须能追溯到简历原文，禁止「凭空印象分」
  • HR 推翻 AI 判断时，必须记录「推翻原因」，用于后续优化（这是最重要的训练数据）
  • 验收：与资深 HR 人工排序的 Top 10 重合率 ≥ 70%；歧视字段零泄漏

④ 候选人邀约与调度

  • 生成个性化邀约（邮件/短信/微信），含岗位、面试形式、时长、可选时段、联系人
  • 时间协调逻辑：读取面试官日历忙闲 → 给 3 个候选时段 → 候选人确认 → 创建日历邀请（一期必须先给 HR 确认再发）
  • 催办：候选人 24h 未回复 → 自动跟进 1 次；48h 未回复 → 转人工
  • 合规硬要求：所有邀约信必须含退订/拒绝说明，且记录发送时间与内容（留痕）

⑤ 面试辅助

  • 面试前：生成结构化面试提纲（考察维度 → 对应问题 → 期望回答要点 → 追问路径）
  • 面试中（可选）：实时转写 + 关键信息标记
  • 面试后：生成纪要草稿 + 评价表建议（不给录用建议，只做整理）

⑥ Offer 及入职前置

  • 生成 Offer 草稿（只起草，不发送，必须走审批）
  • 薪资合规检查：是否低于岗位薪资带宽下限、是否超出预算审批线
  • 自动生成入职材料清单，并移交「入转调离 Agent」

3.2 入转调离 Agent

岗位定位：HR 的「流程管家」，负责盯时间、催材料、留痕迹。

3.2.1 四条流程

流程触发AI 自动做的事强制人工确认的事
入职Offer 接受 / 手动创建生成材料清单、按天催收、OCR 校验材料完整性、发起账号开通审批合同签署、权限开通
转正试用期到期前 N 天（默认 15/7/3/1）提前提醒直属上级、拉取试用期考核表、汇总待办转正结论、薪资调整
调岗调岗审批通过生成调岗材料清单、同步更新组织架构树、通知相关系统职级/薪资变更

3.2.2 关键设计

  • 时间轴引擎（Workflow，不用 AI）：所有「提前几天提醒」都是确定性任务，用定时任务 + 规则，稳定且零成本
  • AI 只用在三个地方：① 生成的提醒文案因人而异（新人 vs 高管话术不同）② 材料 OCR 后判断「这张是不是体检报告」③ 员工用自然语言问「我该交什么材料」时给个性化清单
  • 材料收集看板：每位待入职/待转正员工一张卡片，显示「已收 3/6 项」，缺项红色标注，一键催办
  • 超期升级：逾期 2 天 → 提醒 HR；逾期 5 天 → 提醒 HR 上级
  • 验收：流程按期完成率 ≥ 90%；材料漏项率 ≤ 2%

3.3 员工自助 Agent

岗位定位：7×24 小时回答员工问题，把 HR 从「人肉客服」里解放出来。

3.3.1 功能

能力说明
自然语言问答「我还有几天年假？」「社保基数怎么算？」「报销流程是什么？」
多入口企业微信 / 飞书 / 钉钉机器人 + H5 员工端
有依据回答每个答案附「依据来源」（制度文件章节 + 最后更新时间），可点击查看原文

3.3.2 关键规则（这块最容易出事）

  1. 事实分层：涉及个人数字（年假/薪资/考勤）必须查业务系统，不许用知识库里的文档回答；制度解释类才用知识库
  2. 冲突处理：知识库文档与业务系统数据冲突时，以业务系统为准，并提示「制度文件可能已过期，已通知管理员」
  3. 权限硬隔离：员工 A 问不到员工 B 的任何数据，即使用自然语言绕过（「帮我算算张三的年假」）也必须拒绝
  4. 禁止：不给法律意见、不做薪资谈判建议、不评价同事/领导、不解读劳动合同纠纷 → 一律转 HR 或法务
  5. 测不准就说不知道：设置「置信度阈值」，低于阈值不硬答
  • 验收：常见问题（Top 50）自助解决率 ≥ 60%；答非所问率 ≤ 5%；零越权访问

岗位定位：把数据搬进搬出的活儿全干掉，让 HR 一句话出图。

3.4.2 关键规则

  • 数据必须来自权威库，不能用模型「估算」；模型只负责：自然语言转查询、挑图表类型、写结论文字

  • 验收：指标与人工核算误差 = 0（因为走的是同一套 SQL）；月报生成时间 ≤ 30 秒

第四部分 · Agent 底座必须具备的能力

这一部分是平台的地基。上层四个 Agent 是「租户」，底座是「楼板」。地基不牢，上面全塌。

4.1 任务规划拆解（Planner）

要解决什么：用户说一句模糊的话，Agent 得知道分几步干、每步用什么工具、什么时候该停下来问人。

能力具体要求
意图理解把「帮我看看这岗位招得怎么样」拆成：拉岗位数据 → 算漏斗 → 生成结论
计划生成输出版本化的任务计划（Task Plan），必须落库可回放
步骤依赖支持串行、并行（如同时解析 50 份简历）、条件分支（材料缺→催收，不缺→发起审批）
动态调整步骤失败时可换工具重试（ATS API 挂了→走导入模式），而不是整单失败
预算控制每个任务设 token / 时间 / 调用次数上限，超限暂停并通知人
计划可见HR 能看到「它打算怎么干」，并可以改（这是信任的关键）

反面案例（必须避免）：计划不落库，出问题无法复现，只能靠猜。

4.2 工具调用（Tool Calling）

能力具体要求
工具注册中心所有工具统一注册：名称、说明、参数 Schema、权限要求、是否高风险、超时时间、幂等键规则
结构化调用模型只能按 Schema 调，参数不合法直接拒绝，不让模型自由发挥
幂等保障每个写操作带幂等键（如 interview_invite:候选ID:轮次），重试不会重复发信
失败处理超时/错误 → 指数退避重试 3 次 → 仍失败转人工队列并告警
高风险标记工具打标：发送Offer、删除数据、改薪资 属于高风险，调用前强制进审核闸门
审计每次调用记录：谁发起、什么任务、入参、出参、耗时、是否被审核
权限校验工具执行前校验「发起人是否有权做这件事」，而不是「系统账号有没有权限」

4.3 长期记忆（Memory）

关键认知：记忆不是把所有聊天记录存下来，而是分层存储。

记忆层存什么存多久作用
会话记忆当前对话上下文会话结束让对话连贯
用户偏好记忆「这位 HR 喜欢先看分数再看理由」「习惯先筛学历」长期越用越顺手
任务状态记忆任务跑到第几步、中间结果任务生命周期断点续跑，不重复劳动
业务事实记忆岗位画像、团队惯例、面试官偏好长期，需人工可编辑提升判断准确度
企业知识记忆制度文档（向量化）跟随文档版本问答依据

硬规则：

  1. 记忆不能覆盖权威事实。记忆说「张三还在职」，但 HR 系统显示已离职 → 以 HR 系统为准
  2. 敏感信息不入长期记忆。手机号、身份证、薪资不写入记忆层
  3. 记忆必须可查看、可删除（合规要求，员工有权要求删除其个人数据）
  4. 记忆写入前需过「脱敏网关」

4.4 权限隔离（Permission Isolation）

四层隔离，缺一不可：

层级隔离内容实现要点
租户隔离A 公司 vs B 公司所有表带 tenant_id + 数据库行级安全（RLS），应用层强制过滤
角色隔离HR 专员 / HRBP / HRD / 面试官 / 员工RBAC：角色 → 资源 → 动作 → 数据范围
数据范围隔离HR 只能看自己负责的部门/岗位数据权限表达式，如 dept in (我的负责范围)
Agent 代理隔离Agent 不能超出发起人权限Agent 以发起人身份执行（二次鉴权），禁止使用超级账号

必须能通过的安全测试：

  • 用员工账号调「查别人薪资」接口 → 必须 403
  • 用 HR 专员账号导全公司花名册 → 必须被数据范围拦截
  • 让 Agent「帮我把所有候选人电话导出来」→ 必须拒绝并记录

4.5 敏感数据脱敏（PII Masking）

定义敏感级别：

级别字段示例处理方式
S4 极敏感身份证号、银行卡、薪资、体检报告默认全部打码，明文需单独授权 + 二次验证，查看留痕
S3 敏感手机号、邮箱、住址、家庭信息列表默认打码（138****8888），点击查看需权限
S2 内部姓名、部门、岗位、绩效等级按角色可见
S1 公开岗位信息、公司制度全员可见

脱敏网关的三道关：

  1. 入模型前：把 S3/S4 字段从 Prompt 里物理替换为占位符（[手机号]），模型永远看不到原文
  2. 模型输出后：扫描输出内容，出现疑似证件号/手机号 → 拦截
  3. 用于训练/优化前：二次脱敏 + 明确授权

招聘反歧视的技术保障：简历进入打分模型前，物理删除性别、年龄、出生日期、婚育、户籍、照片字段。这不是靠提示词「请不要考虑性别」，而是靠代码删字段——因为提示词会失效，代码不会。

4.6 高风险操作强制人工审核（HITL 闸门）

什么是高风险（清单必须写死）：

类别具体动作审核要求
法律效力类发 Offer、签合同、发解除通知、出离职证明必须人工批准，且记录审批人
金钱类任何薪资/奖金/报销金额的写入必须人工批准
不可逆类删除候选人、删除员工数据、关闭账号必须人工批准 + 二次确认
对外沟通类群发邮件/短信（>10 人）必须人工预览确认真实内容
隐私类导出名单、查看身份证原件必须授权 + 留痕 + 限量
低风险（免审）生成草稿、检索、算数、写内部分析自动执行，事后可查

审核闸门设计：

  • 审核队列：所有待审任务进统一队列，支持批量批准 / 逐条批准
  • 卡片式审核：展示「Agent 想做什么 + 具体内容 + 依据 + 影响范围」，一键通过/驳回/改后发
  • 超时策略：超过 N 小时未审核 → 提醒；超过 2N 小时 → 升级到上级
  • 驳回即学习：驳回必须填原因，原因进入优化数据集
  • 禁止绕过：任何代码路径都不得跳闸门（需要静态检查 + 单测覆盖）

# backend/app/middleware/tenant.py —— 每个请求进来自动设置租户上下文
from fastapi import Request
from starlette.middleware.base import BaseHTTPMiddleware

class TenantMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        tenant_id = request.headers.get("X-Tenant-Id")   # 生产环境从 JWT 解析，不要信请求头
        async with request.app.state.db.session() as s:
            await s.execute("SELECT set_config('app.tenant_id', :t, true)", {"t": tenant_id})

# agents/planner.py
PLANNER_PROMPT = """你是HR Agent的规划器。用户目标：{goal}
可用工具：{tools_json}
要求：
1. 输出 JSON：{"steps":[{"id":1,"intent":"...","tool":"...","params":{...},"depends_on":[0],"high_risk":false}]}
2. 只允许使用列表中的工具；参数必须符合 Schema。
3. 涉及删除/发送/金额/对外沟通的步骤，high_risk 必须为 true。
4. 步骤数不超过 8 步。无法完成时输出 {"error":"原因"}。"""

async def plan(task, tools) -> dict:
    raw = await llm_gateway.chat_json(PLANNER_PROMPT.format(
        goal=task.goal, tools_json=tools.schema_dump()))
    plan = validate_plan(raw, tools)          # 校验：工具存在？参数合法？步骤数？
    await db.execute(insert(AgentTask).values(**{
        "id": task.id, "goal": task.goal, "plan": plan["steps"], "status": "running"}))
    return plan

三条硬规则：

  1. 计划必须落库（上面已落），出问题能回放
  2. 用 JSON Schema 强约束输出，解析失败就重试一次，再失败转人工——不要让模型自由发挥
  3. 计划要给人看：UI 上先展示「我打算这么干」，人点确认后再跑。这是信任的关键设计

# tools/registry.py
@dataclass
class ToolSpec:
    name: str
    desc: str                      # 给模型看的自然语言说明，写得越清楚，模型调得越准
    params_schema: dict            # JSON Schema
    handler: Callable
    high_risk: bool = False
    idempotency_key: str | None = None   # 模板，如 "invite:{candidate_id}:{round}"
    timeout_s: int = 15

REGISTRY: dict[str, ToolSpec] = {}

def tool(**kw):
    def deco(fn):
        spec = ToolSpec(handler=fn, **kw)
        REGISTRY[kw["name"]] = spec
        return fn
    return deco

# ---- 只读工具：免审 ----

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=10), reraise=True)
async def call_tool(task_id, step, ctx):
    spec = REGISTRY[step["tool"]]
    validate_params(spec, step["params"])                     # ① Schema 校验
    await guard.check_permission(ctx, spec)                   # ② 权限：以发起人身份
    safe_params = guard.mask_pii(step["params"])              # ③ 脱敏后再传给模型/外部
    if spec.high_risk:
        await guard.enqueue_approval(task_id, spec, safe_params)   # ④ 进闸门，抛出让流程暂停
        raise ApprovalRequired()
    idem = render_idem_key(spec.idempotency_key, step["params"])
    if idem and await redis.get(f"idem:{idem}"):              # ⑤ 幂等命中，不重复执行
        return await db.fetch_tool_call_result(task_id, step["id"])
    t0 = time.time()
    try:
        res = await asyncio.wait_for(spec.handler(ctx, **step["params"]), timeout=spec.timeout_s)
        if idem: await redis.setex(f"idem:{idem}", 86400, "1")
        await log_tool_call(task_id, spec, step, res, "ok", int((time.time()-t0)*1000))
        return res
    except Exception as e:
        await log_tool_call(task_id, spec, step, None, "error", int((time.time()-t0)*1000), str(e))
        raise

# tools/guard.py
PII_PATTERNS = {
    "phone": r"1[3-9]\d{9}",
    "idcard": r"\d{17}[\dXx]",
    "bankcard": r"\d{16,19}",
}

def mask_pii(payload: dict) -> dict:
    """① 入模型前：把敏感值替换为占位符，模型永远看不到原文"""
    s = json.dumps(payload, ensure_ascii=False)
    for k, p in PII_PATTERNS.items():
        s = re.sub(p, f"[{k.upper()}]", s)
    return json.loads(s)

def scan_output(text: str) -> str:
    """② 模型输出后：兜底扫一遍，防止它把记忆里的原文吐出来"""
    for k, p in PII_PATTERNS.items():
        if re.search(p, text):
            audit_log("PII_LEAK_BLOCKED", text[:200])
            raise ValueError("OUTPUT_CONTAINS_PII")
    return text

DROP_FOR_MODEL = ["gender", "birth_date", "photo", "marital_status", "hukou"]
def strip_protected(fields: dict) -> dict:
    """③ 反歧视：物理删除受保护字段，而不是提示模型'别考虑性别'"""
    return {k: v for k, v in fields.items() if k not in DROP_FOR_MODEL}
记住这句话：提示词会失效，代码不会。凡是靠 Prompt 实现的合规，都要用代码再兜一层。

三、前端是怎么自动切换真后端的（以及登录闸门）

平台原型/src/app.js 里有一个 LIVE 开关，页面加载时会按顺序探测（liveBootstrap()）：

js
const here  = await probeHealth('');                 // ① 先探当前源（后端托管时就走这条）
if (here) return afterHealth(here);                  //    → 同源在线，与从前完全一致
if (wantOffline()) return;                           // ② ?offline=1 / #offline → 强制离线演示
const local = await probeHealth(BACKEND_ORIGIN);     // ③ 再探 http://127.0.0.1:8788
if (!local) return connBar('…离线演示态…');           //    都没有 → 离线，但**如实说明**
if (isTopWindow()) return location.replace(BACKEND_ORIGIN + '/');   // ④ 顶层窗口 → 跳过去
API_BASE = BACKEND_ORIGIN;                           // ⑤ 被嵌在预览面板里 → 跨源直连
await afterHealth(local);
  • 当前源就是后端 → LIVE.on = true，右上角亮起「🟢 真实后端 · 已认证」，此后所有动作走真 API，数据来自 hr_agent.db。
  • 有后端但无会话（strict 模式）→ 弹登录闸门（列出演示账号），登录后再进入真实态。不会白屏，也不会静默降级成假数据。
  • 当前源没后端、但本机 8788 有 → file:// 直接双击时跳转到 8788；在预览面板（跨源 iframe）里则跨源直连，不跳转 —— 后端带 X-Frame-Options: SAMEORIGIN，跳过去只会白屏。
  • 都没有 → 保持离线模式，用内置演示数据，功能照常可点；左下角状态条说明原因并给出 server/start.bat 与「重试连接」。

结论：同一份 index.html，不管从哪儿打开都会主动找到本机后端；只有显式 ?offline=1 或后端确实没起，才停在离线演示态（且会说明白，不装作正常）。

为什么先认职能，而不是只认行业？ 这是被一个真实 bug 逼出来的：以前只按「行业」取词库，于是凡是「互联网」行业的岗位——哪怕是产品经理、设计师、运营——都会被塞进 Java / Spring / 微服务这套技术栈。根因是「行业」和「职能」是两回事，混在一张表里必然串味。

现在改成职能族（Function Family）优先、行业兜底两层：

  • 行业词库（server/db.js 的 INDUSTRY_SKILLS，18 类）：互联网、制造业、零售连锁、医疗健康、教育培训、金融、销售、人力资源、建筑工程、物流运输、酒店餐饮、医药健康、游戏、能源电力、传媒文化、专业服务、物业管理、通用。只在职能识别不出来时才兜底。
  • 识别函数 detectFunction() 命中不到族时返回 null，此时才回落到行业库 —— 所以「设备维保工程师」不会被当成软件工程师（tech 族的关键词里刻意不含「工程师 / 技术」这类泛词），「AI 产品经理」也不会拿到 Java。
  • 强弱关键词：kw 收强词（命中即计 3 分）；某些族的 weak 收弱词（命中只计 1 分）。例：tech.weak = ['运维']，于是「光伏运维工程师」被强词「光伏」拉去能源电力族，而纯「运维工程师」没有强词、只剩这 1 分弱命中，仍归技术族。
  • 族与族的分界是按「这个人每天做什么」划的，不是按行业划的。例如「实施交付」与「销售」分开：前者是签约后把系统真正跑起来，后者是签约前的商机与谈判；「实施交付」与「客服」也分开：前者处理系统与业务落地，后者处理话务与客诉口径。这两个分界各对应一个真实 bug（「软件实施管培生」一度被误判为客服岗）。

岗位层级：管培生 / 实习 / 应届不设工作年限门槛

同一个职能族下，岗位层级（社招 vs 管培 / 实习）决定「工作经验」这一维怎么写。

  • ReqLib.detectJunior() 扫描岗位名与已填要求，命中 管培生 / 培训生 / 实习生 / 应届 / 校招 / 储备干部 / 见习 / 学徒 / 经验不限 即判定为初级岗。
  • 命中后：
  • 工作经验维度 → 「无需相关工作经验，欢迎应届毕业生投递」+「有 1–2 段与岗位方向对口的实习经历者优先」（不再套用 expHint 那句「有独立负责过 X 项目的经历」）；
  • 筛选 Agent 的年限门槛同步放开（gateYears = null）—— 否则会出现「JD 写着欢迎应届生、规则门槛却把应届生全拦掉」的自相矛盾。
  • 未命中则维持原口径：N 年以上 + 该职能的经历特征。
例：「软件实施管培生」（互联网）→ 识别为实施交付族 + junior。生成的岗位职责是「系统实施与交付、部署配置、上线培训、问题闭环」，工作经验是「无需经验 / 对口实习」——不会出现客服话术，也不会出现「3 年以上」。

新建岗位后能不能立刻跑筛选？能。 /api/jobs 创建岗位时会调 synthCandidates() 按该岗位画像自动生成 5 份演示简历，四档分布（强推荐 / 可聊 / 打分后不合格 / 硬性条件不符被规则拦截），所以新建完切到筛选台点运行就有结果。演示简历带 synthesized=1 标记，页面上会显示「演示简历」小标签 —— 不会和真实简历混淆。

JD 扫描是代码，不是提示词。 engine.js 里两张规则表：DISCRIMINATION（11 条，性别/婚育/年龄/户籍/院校/身体状况/外貌/地域）和 ILLEGAL（9 条，社保/合同/押金/工时/离职扣薪/工伤免责/试用期工资/限制生育），每条都带法条依据与建议改法。命中即返回 blockPublish: true，前端按钮变成「⛔ 已阻止发布」。

离线模式（直接双击 index.html）也在 src/agent.js 里维护了同源的规则，同样做真实扫描 —— 不是写死几条结论给你看。

任职要求：从「一条」扩充到「六维度」

以前的问题：HR 在必须项里写一条「3 年以上采购经验」，生成的 JD 任职要求就只有这一条 —— 单薄、不专业、不像真实招聘启事。

现在的做法（engine.js 的 expandRequirements()，离线端 src/agent.js 同源）：

text
HR 已填的必须项 / 加分项
   │ ① 原样保留，只按语义归位（含「学历」→学历背景；含「经验」→工作经验；其余→专业技能）
   ▼
按「职能族」素材补齐缺失维度（识别不到职能才按行业兜底）
   │ ② 专业技能：该职能族的核心技能里没被提到的自动补位
   │ ③ 工作经验：年限 + 该职能的经历特征（管培 / 实习岗改为「无经验 + 对口实习」口径）
   │ ④ 学历背景：按岗位学历门槛 + 职能对口专业方向
   │ ⑤ 综合素质 / ⑥ 软技能：职能化表述（医疗看查对制度、金融看合规红线……）
   ▼
JD「二、任职要求」= 维度小标题 + **自然行文段落**（v0.9.8 起不再逐条编号）

真正让 HR 头疼的不是补不齐，而是粘进去的东西被拆碎。所以生成前先做一次原文还原：

text
任职要求框里粘一整份 JD
   ▼
① 剥符号     行首的 · • - 1. （1） ① 一律去掉（否则渲染时会叠成「6. ·从0到1…」）
   ▼
② 合并断行   上一行以句中标点结尾 → 这句话没说完，并回来并补齐逗号
   ▼
③ 小标题归位 「你会做什么」→ 职责；「我们想找这样的你」→ 任职要求；「有这些更香」→ 加分项
   ▼
④ 成段输出   同维度的若干要求用「；」串成一整段话，不再一条一个编号

条目边界只由「换行」和「行首列表符号」决定。逗号、分号、顿号是句中标点，不是分隔符 ——

旧版按 [,，;；\n] 切条，一句「和顶尖算法、工程团队并肩，把想法快速上线」会被劈成两条，

一份 300 字的 JD 能变成 20 个碎片。同一个判据也保证了表单往返无损：从「用逗号拼接」改成

「一行一条」，编辑岗位时不会把你写好的要求黏成一条。

三个刻意的设计：

  • 绝不改写 HR 的原句。HR 写的那条一定出现在 JD 里，AI 只做补齐和专业化 —— 否则 HR 会认不出自己写的岗位。
  • 综合素质 / 软技能不进 must_have，只进 JD 正文。因为它们含「沟通协作」这类通用词，若进入打分关键词会稀释岗位关键词、让所有候选人得分趋同。硬性条件通道（must）只收专业技能 + 工作经验 + 学历背景。
  • 软素质不会塞进「专业技能」。「对 AI 是真热爱 / 有同理心」这类句子单列一桶归到「软技能」，否则整段读起来不着调。

一句话验证（本机已跑通）：输入 1 条要求 → 输出 5 个维度 13 条任职要求（硬性条件 7 条 + 综合素质/软技能 6 条）+ 加分项 3 条，原句完整保留。

幂等：对已扩充过的结果再扩一次，条数不变（不会无限膨胀）。

老 JD 的自我修复（jd_ver）

改了词库或职能族，已经存库的老 JD 不用手动改。jobs 表有 jd_ver 列，engine.js 里有个常量 REQ_LIB_VER。服务启动 bootstrap() 时逐个岗位比对：

text
岗位.jd_ver < REQ_LIB_VER
   │ 说明这条 JD 是用旧词库生成的（比如还含 Java）
   ▼
用当前 expandRequirements + buildJD 重算
   ▼
回写 must_have / nice_have / keywords / jd_text / jd_ver

所以升级后第一次启动，历史上那些「非技术岗被塞了技术栈」的脏数据会被自动洗一遍。同时 stripMisfitAutoFill() 会把误填进非技术岗 must_have 的自动补位技能清掉（靠自动补位句式的正则识别，不会误伤 HR 手写的原句）——双保险。

判定「同一句要求」用 similarReq()（bigram 相似度 ≥ 0.28，可调），避免「需求分析」和「需求分析与技术方案设计」被当成两条重复塞进去。HR 原文已覆盖的维度用 coveredByUser() 跳过，不重复补。

JD 职责：同族不同岗不再一字不差（pickDuties）

以前的问题：每族只有 4 条职责，buildJD() 把本族 duties 全部输出，于是「AI 产品经理」和「数据产品经理」生成的职责一字不差 —— JD 看着就不是这个岗。

现在的做法（v0.9.6）：

  • 每句职责从纯字符串升级成 { t: '句子', k: ['子方向标签'] }，例如产品族里「设计 AI 能力的产品化方案」带标签 ['AI','模型','大模型']、「参与商业化方案设计」带 ['商业化','定价','B端']。
  • 新增 ReqLib.pickDuties(fn, title, texts, max)：拿岗位名（权重×3）+ 必须项/加分项正文（权重×1）去命中每句的子方向标签，命中数降序取前 max 条（engine.js 里 DUTY_MAX = 6），命中不足则用本族其余的句子补齐。
  • 于是招「AI 产品经理」优先取 AI / 数据向的句子，招「B 端产品经理」取商业化向的句子，两份 JD 立刻不同；同一族下 8 条池子有几十种组合，且全程无模型、结果可复现。
  • 前后端同源：后端 engine.js 的 dutiesFor()、离线端 src/agent.js 的 expandReqs() 都调同一个 pickDuties()。
例：「光伏运维工程师」生成 JD 时，职责首条是「负责光伏／风电／储能项目的运行监视与发电量分析」，而不是技术族的「保障线上服务稳定性」—— 既证明职能族选对了，也证明子方向挑句生效了。

  • 调用失败 → 自动回退规则输出，页面不会报错。这条 fallback 是刻意的：模型挂了产品还得能用。
