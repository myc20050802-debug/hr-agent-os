## 一、上线 GitHub 后可优化之处

按投入产出排序。**G1 是唯一一个能改变「项目印象」级别的动作。**

### G1 · 加「零安装在线 demo」（最高杠杆）

**证据**：`平台原型/index.html` 是**完全自包含**单文件 —— 我 grep 过 `<script src=` 与 `<link href=`，**两处都是 0**，527,133 字节全部内联，且探测不到后端时会自动进离线模式。

**为什么这是第一优先**：现在访客要看到产品，必须先 clone → 装 Node 22 → `npm run dev` → 登录。任何一步掉人就永远看不到了。而这个文件**天生就是静态站点**。

**可执行方案**（约 30 分钟）：

```yaml
# .github/workflows/pages.yml
name: pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/checkout@v4
      - run: mkdir -p site && cp 平台原型/index.html site/index.html
      - uses: actions/upload-pages-artifact@v3
        with: { path: site }
      - uses: actions/deploy-pages@v4
```

然后 README 顶部放：`[▶ 在线体验（零安装）](https://<用户名>.github.io/<仓库名>/)`。

**顺带解决一件事**：有了在线 demo，「仓库里没有截图」的问题也能一起收掉（见 G3）。

## 二、项目本身存在的问题

分三层：产品定位 / 工程质量 / 资料一致性。**第三层最容易被抓，也最好修。**

### 2.1 产品定位层

#### P-1（最重要）「AI Agent 平台」的默认体验里没有 AI

**证据链**：
- `server/config.js:141-144` → `LLM_API_URL` / `LLM_API_KEY` / `LLM_MODEL`（默认 `gpt-4o-mini`）可插拔
- `server/engine.js:75` → `llmConfigured()` 为假时**自动走规则模式**
- `server/engine.js:6-7` 注释明说「未配置时自动走规则模式（离线可用）」
- `docs/12:264` 自己承认：「**没有接模型** —— 现在打分与润色全走确定性规则」

**为什么这是最大问题**：项目名叫「HR **AI Agent** 平台」，README 讲 Agent 底座六大能力。但访客跑起来，看到的是**一个规则引擎**。面试官的第一问一定是「AI 在哪」，而现在的答案是「可以配但我没配」。

**这其实是个好设计，问题只在于没讲出来。** 「规则打底 + LLM 增强」是正确的工程判断（离线可用、可回归、零 token），但你把它当成了实现细节，而它应该是**产品主张**。

**可执行方案（三步，第 2 步是关键）**：

1. README 与 UI 显式区分两种模式：页面上把「规则模式 / 模型模式」做成**状态灯**（现在成本栏已经能算出 `¥0.6` 这种数字，却没有模式标识 —— 补一个 chip 即可）。
2. **用同一份 30 例黄金集跑「规则模式 vs LLM 模式」对照评测**，把两个一致率、两个误筛率、两个成本写进 `docs/09`。
   → 这一张对照表能一次性回答「AI 在哪」「为什么不用 LLM」「用了好不好」三个问题，**是这个项目性价比最高的一项补充**。
3. 在 README 给出 LLM 模式的最小复现命令（已有 `$env:LLM_API_URL=...` 那一段，提到首屏）。

#### P-2 单租户写死，卖点缺失

**证据**：`server/auth.js:42-45` 等处以 `'T-001'` 硬编码；`server/audit.js:44` 兜底 `e.tenantId || 'T-001'`。

**为什么是问题**：B 端 HR SaaS 的准入门槛就是「两个客户的数据不能串」。这个能力**既没法演示、也没法验证**，而 `docs/05` 早就把它列成 C 档差距。

**可执行方案（不做真多租户，只做「可验证的隔离机制」）**：
1. 把租户从代码常量提到 `.env`：`TENANT_ID=T-001`（与既有 `config.js` 风格一致）。
2. 加 1 条测试：切换 `TENANT_ID` 后，岗位 / 候选人列表为空、审计日志为空。
3. README 里把这句话写实：**「租户维度已贯通到数据层与审计层，切换租户即数据不可见；生产环境需补物理隔离与 RLS」** —— 这比含糊地说「支持多租户」可信得多。

#### P-3 效果数字没有出处

**证据**：`平台原型/src/app.js:2046` —— 表格行「提醒文案生成 / 规则模板优先 / **70% 场景模板即可，无需模型** / 212 / ¥0.6」。

同页还有若干 KPI 类百分比。另外 `分享包/使用说明.txt` 自己写着「页面里的百分比（如「省 70% 时间」）是产品设计目标，不是实测结果」——**这句话只存在于分享包里，仓库里没有**。

**为什么是问题**：面试官问「70% 哪来的」，你答「设计目标」是合格答案；但如果文档里没有任何地方说这是假设，就变成了「编数字」。

**可执行方案**：把口径区分做成**视觉规范**，而不是散落的注释。

| 数字类型 | 示例 | 展示方式 |
|---|---|---|
| 实测数字 | 一致率 90.0%（27/30）、`run_all` 10 套件 | 正常展示 + 脚注写口径与样本量 |
| 设计目标 | 「省 70% 时间」 | 加 `ⓘ`，悬浮显示「设计目标，未做对照实验」 |
| 演示假数据 | 「去年同期 65%」等人力 KPI | 加「演示数据」灰标 |

并在 `docs/01` 里加一节「数字口径规范」，让后来人不再往界面里塞无源数字。

#### P-4 评测集偏小，且只覆盖 3 个岗位

**证据**：`tools/golden/golden_set.json`（12,693 字节）= 3 个岗位 × 10 例 = **30 例**，一致率 27/30 = 90.0%，**误筛率 25.0%**。
你手上有 **30 个职能族**的词库（`shared/req-lib.js`），但只测了 3 个。

**为什么是问题**：30 例里错 3 例就是 90%，Wilson 95% 区间大约 **[74%, 97%]** —— 这个置信度撑不住「一致率 90%」这种结论式表述。而误筛 25% 是 B 端客户最不能接受的方向（筛掉人 = 漏掉人才）。

**可执行方案**：
1. 扩到 **90 例**：从 30 个职能族里抽 9 个族 × 10 例（覆盖技术 / 产品 / 销售 / 职能 / 制造各至少 1 族）。
2. 报告里**给区间而不是点估计**（写「27/30，Wilson 95% CI ≈ [74%, 97%]」），这一条会显著提升专业感。
3. README 主动解释误筛 25%：「3 例分歧**全部同向且均为有意埋的边界探针**」（这句现在只存在于 `docs/03:460`，提到首屏去）。

#### P-5 无真实简历入口，演示只能用合成数据

**证据**：演示简历带 `synthesized=1`；`docs/05` 把「无真实简历入口」列为差距。

**为什么是问题**：「AI 筛简历」的说服力停在玩具数据。面试官会问「拿我这份简历试试」，而现在做不到。

**可执行方案（避开最难的 OCR）**：加「**粘贴简历文本 → 解析 → 打分**」入口。不做文件上传、不做 PDF 解析，只要一个 textarea + 现成的解析与打分链路。这一条打通，「可验证性」直接从 4 分跳到 5 分。

### 2.3 资料一致性层 —— 最容易被抓，也最好修

#### D-1 「N 个页面」四份文档四个数字，**全都不等于代码事实**

| 出处 | 写的是 |
|---|---|
| `README.md:56` | **23** 个页面 |
| `docs/04_产品复盘…md:266 / :427` | **23** 个页面 |
| `docs/09_实现说明与验收报告.md:249` | **23** 个页面 |
| `docs/02_搭建实操教程.md:66` | **12** 个页面 |
| `面试前缺口审计_待补清单.md:271` | **50** 个页面 |
| **代码事实**（`PAGES.*` 定义数） | **24** |

**为什么这是最该先修的**：它是「不认真」的直接证据。一个访客只要点开两份文档就会发现数字对不上 —— 而这种廉价的不信任何必送给对方？

#### D-2 README 字节数过期 35 KB

`README.md:56` 写 `491,922 bytes（约 480KB）`，实测 `平台原型/index.html` = **527,133 字节**。原型改了、README 没跟着改。

#### D-3 / D-4 同题材分两处

`JD生成口径修复说明.md`（根）与其后继版 `JD生成口径v13修复说明…md`（docs/）分居两地；根目录共 21 个散落文档。

#### → 统一方案：把「会腐坏的数字」变成「不会腐坏」

新增 `tools/check_docs.js`，从**代码与文件系统读取真相**并断言，纳入 CI：

| 被守护的数字 | 真相来源 |
|---|---|
| 页面数 | `平台原型/src/app.js` 里 `PAGES.*` 的个数 |
| 原型字节数 | `fs.statSync('平台原型/index.html').size` |
| 接口数 | `server/routes.js` 里 `r.(get\|post\|…)` 的个数 |
| 套件数与断言数 | `tools/run_all.js` 的套件表 |
| 一致率 / 误筛率 | `tools/golden/golden_set.json` 实跑 |

**规则：README 与 docs 里的这些数字必须写成从脚本生成的形式（或加校验注释），CI 里数字对不上就红。**
这是唯一能根治「文档数字腐坏」的办法 —— 靠人记得同步，一定会再错。
