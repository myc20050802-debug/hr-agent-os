# 打分口径 v16 · 相关性门槛（技能零命中即出局）

> 起因：黄金集里 3 个探针例（人工都标 `no`）被规则判成 `ok`。追下去发现根因不是「词库少了一个词」，
> 而是**「岗位需要的硬技能一个都没命中」这件事在打分里没有任何地方表达出来**。
> 本文记录候选方案、实测对照与最终取舍 —— 结论是「加一道相关性门槛」，而不是「改业务维度的计数」。
>
> 相关代码：`server/engine.js:skillGate` · `平台原型/src/agent.js`（离线镜像）· `shared/score-why.js`（归因文案）
> 验证：`tools/test_eval.js` A / A2 / A3 段 · `平台原型/test_prototype.js`「相关性门槛（离线镜像）」

---

## 一、问题：3 个探针例的同一个签名

黄金集 30 例（3 岗位 × 10）里，人工标注 `no` 却被判 `ok` 的有 3 例：

| 例号 | 岗位 | 简历 | 人工 | v16 前 AI |
|---|---|---|---|---|
| G-J09 | 高级 Java 工程师 | 前端负责人（JavaScript / TypeScript / Vue / React / Node.js） | no | **74 → ok** |
| G-P09 | AI 产品经理 | 资深算法工程师（算法 / Python / TensorFlow） | no | **74 → ok** |
| G-M09 | 软件实施管培生 | 资深销售（客户沟通 / 培训；保险 / 直销 / 地推） | no | **77 → ok** |

三个人的分数构成是**同一个签名**：

```
技能匹配 14（底分） + 业务匹配 30（满） + 稳定性 15（满） + 加分项 15（满） ≈ 70~77 → ok
```

四维都设了底分（这是有意设计，见 `shared/score-why.js:notesOf`），所以一份**完全不相干**的简历保底能拿 50 分 —— 50 仍在 `no` 档，底分机制本身没问题。真正的问题是：**技能一个都没命中，只被记成「触底系数 0.35」，在总分里与「命中 1 项」几乎没有区别**，而另外三维的满分足以把它抬过 60。

## 二、候选方案与实测对照

只比较「改业务维度」是不对的 —— 先跑了对照再决定。所有方案都在同一份黄金集上实跑/精确重算（业务维度按系数阶梯替换，其余维度沿用实跑结果）：

| 方案 | 档位一致率 | 误筛率（红线） | 漏筛率 | 失败例 |
|---|---|---|---|---|
| **V0 现状**（`bizN = 简历业务标签条数`） | 90.0%（27/30） | 0.0% | 25.0% | G-J09 / G-P09 / G-M09 误判 ok |
| V1 业务维度改为「与职能族业务词表求交」 | 73.3%（22/30） | **22.2%** ❌ | 16.7% | + G-J04 / G-J05 / G-J06 / G-P06 误筛 |
| V2 业务维度改为「与（职能族 ∪ 行业）词表求交」 | 80.0%（24/30） | **16.7%** ❌ | 16.7% | + G-J05 / G-J06 / G-P06 误筛 |
| **V3 V0 + 相关性门槛（技能零命中 ⇒ 出局）** | **96.7%（29/30）** | **0.0%** ✅ | **8.3%** | 仅 G-M09 |

**为什么 V1/V2 会被否**：Java 岗的职能族业务词表是**架构术语**（高并发 / 分布式 / 微服务 / 云原生 / 中台 / To B 系统 / C 端产品），而真实 Java 候选人的业务标签是**业务领域**（金融 / 风控 / 交易系统 / 企业服务 / CRM / 政务 / 外包）。求交之后，`G-J04`（电商 + 后台系统）、`G-J05`（企业服务 + CRM）、`G-J06`（外包 + 政务）这些**人工标 `ok` 的正常候选人业务分从 22 掉到 6，直接掉出 ok** —— 把「该通过的漏掉」从 0% 打到 22%，**这是安全红线，不是可以商量的取舍**。

> 顺带说明：`server/db.js` 的 `INDUSTRY_SKILLS[*].biz` 用的正是**业务领域**词（互联网 → 电商 / 交易 / 订单 / 支付 / 内容 / 社交 / SaaS），
> 与 `shared/req-lib.js` 的职能族 `biz`（架构术语）**是两套不同的词表**。这也解释了为什么 G-J01 的业务标签
> （电商 / 订单系统 / 支付 / 高并发）看着「既像又不像」词表里的词。**这份词表要不要统一，是另一个未决问题**（见第六节）。

## 三、结论：加相关性门槛，不动业务维度的计数

改的是**判定链条**，不是系数：

```
evaluateCandidate = ruleGate（年限 / 学历）
                  → skillGate（v16 新增：相关性门槛）
                  → scoreOne（四维加权打分）
```

**`skillGate` 的判据（刻意保守，两个前置条件都必须满足才可能触发）**：

1. 岗位**识别出了**关键词（`kws.length > 0`）—— 否则「判不了」，放行；
2. 简历**列了**技能（`skills.length > 0`）—— 否则「没解析出技能」，放行；
3. 在上述前提下，关键词命中数为 **0** → 出局（`gate: true`，`score: 0`，`grade: 'no'`）。

为什么是「出局」而不是「扣分」：项目有一条硬约束 —— **分数与档位必须同源**（`why` 的算式必须逐位等于总分，
见 `shared/score-why.js` 文件头）。如果只封顶档位不动分数，就会出现「74 分却不合适」这种自相矛盾的展示。
走 `gate` 与年限/学历拦截**同一条路径**（score 0 / grade no / `reasons` 里写明原因），展示与语义都自洽。

顺带修掉一处**归因文案与算法不一致**（`shared/score-why.js:dimReason`）：
业务维度数的是「简历声明的业务语境条数」（后端 `bizN = biz.length`），
旧文案却写成「命中 N 个**{职能族}**业务标签」—— 把「简历里写了什么」说成「跟岗位对上了什么」。
G-J09 会把「前端 / 性能优化」说成「技术研发类业务标签命中」。**解释与分数没打架，但它描述了一件没发生的事。**
现在改成「简历体现 N 条业务语境：…（{族}岗位参考语境：… 等）」；职能族词表只在「往哪补」的建议里出现（`liftText`），那里它确实是候选来源。

## 四、改了什么（清单）

| 文件 | 改动 |
|---|---|
| `server/engine.js` | 新增 `skillGate()`；`evaluateCandidate` 组合为 `ruleGate → skillGate → scoreOne`；业务维度 `ev` 文案纠正；`REQ_LIB_VER` 15 → 16 |
| `平台原型/src/agent.js` | 离线端镜像同一门槛（两个入口口径必须一致，否则同一份简历在离线演示与在线筛选下档位不同） |
| `shared/score-why.js` | `LADDERS.biz.unit` 改为「条业务语境」；`dimReason` 业务维度文案纠正；`liftText` 措辞对齐 |
| `tools/test_eval.js` | 探针分歧断言 3 → 1（并钉住仅存的 G-M09）；门槛例数 3 → 9 且按构成分开断言；A2 段加「必命中锚点」让开新门槛；新增 A3 段 9 条 |
| `平台原型/test_prototype.js` | ③/⑤/⑥ 兼容「门槛出局」；新增「相关性门槛（离线镜像）」断言 |
| `README.md` / `docs/03` | 基线数字与原型字节数同步 |

`REQ_LIB_VER` 递增的理由：它管的是「岗位 JD / 关键词的懒重算」，口径变了若不递增，重启后端不会重算（只在 `GET /api/bootstrap` 比对）。

## 五、实测效果（跑出来的）

| 指标 | v16 前 | v16 后 |
|---|---|---|
| 档位一致率 | 90.0%（27/30） | **96.7%（29/30）** |
| Wilson 95% 置信区间 | [74.4%, 96.5%]（宽 22.2pp） | **[83.3%, 99.4%]（宽 16.1pp）** |
| ±1 档一致率 | 100.0% | **100.0%** |
| 误筛率（安全红线） | 0.0%（0/18） | **0.0%（0/18）** |
| 漏筛率 | 25.0%（3/12） | **8.3%（1/12）** |
| 门槛拦截例数 | 3（年限 ×2 / 学历 ×1） | **9（年限 ×2 / 学历 ×1 / 技能零命中 ×6）** |

**关于区间**：点估计上升、区间收窄（22.2pp → 16.1pp），但这**不是**「一致率已达 96.7%」的证明 ——
30 例的样本量下，区间下沿 83.3% 才是可以对外说的数。要收窄只能扩样本（当前 3 岗 × 10 例，词库覆盖 30 个职能族）。
**漏筛率 25% → 8.3% 是这次更值得说的改善**：它是 B 端客户真正在意的方向。

**新增的 6 例门槛里只有 2 例（G-J09 / G-P09）原先判错**，另外 4 例（G-J10 测试 / G-P10 文案投放 / G-M08 Java 转实施 / G-M10 硬件维修）本来就是 `no` ——
这道闸只是把它们的分数从「底分堆出来的 43~59」改成诚实的 0，档位不变。**没有任何人工标 `strong`/`ok` 的样本被这道闸碰到**，所以误筛守住 0%。

## 六、已知剩余（**没有**解决的）

**G-M09 仍然是 `ok`（77 分）而人工是 `no`。** 它的技能命中 2/6（`客户沟通`、`培训` 确实对得上实施岗），
相关性门槛按设计不触发；它靠业务维度拿满 30 分（保险 / 直销 / 地推 / 团队管理 4 条标签）停在 `ok`。

这暴露的是**业务维度的一个已知简化**：它数的是「简历声明了几条业务语境」，**不与该岗位的业务做匹配**。
要修它会牵动全部岗位的口径，且上文 V1/V2 已经实测证明「直接求交会破安全红线」。
正确的修法是**先把职能族业务词表与行业业务词表统一/补齐**（`shared/req-lib.js` 的 `FUNCTIONS[*].biz`
与 `server/db.js` 的 `INDUSTRY_SKILLS[*].biz` 当前是两套词），**那是独立的一轮工作，不混在本次改**。

`tools/test_eval.js` 里有一条断言专门钉住「仅存的分歧是 G-M09」，防止它悄悄变成更多，也防止有人误以为已经全对。

## 七、反向验证（断言真的会红）

`tools/_rev_v16.py break|restore` —— 拆掉门槛（两处：引擎 + 离线镜像），确认断言变红：

| 破坏态结果 | 说明 |
|---|---|
| `test_eval.js`：A 段 4 条红 + A3 段 6 条红 | 探针分歧 3≠1、门槛例数 3≠9、技能零命中构成 0≠6、A3 的 6 条全红 |
| `test_prototype.js`（**需先 `npm run build`**）：1 条红 | 「零命中未被门槛拦下：档位 no 分数 48」 |

> ⚠️ **踩过的坑**：离线套件渲染的是**打包产物** `平台原型/index.html`。只破坏 `平台原型/src/agent.js`
> 而不重建，破坏态**照样通过** —— 断言看起来在检查、其实测的是旧产物。
> 反向验证前端改动时，`npm run build` 是前置步骤，不是可选项。

A2 段的断言在破坏态**保持绿色是正确的**：它测的是匹配层（`kwContains` / `kwHit`），与这道闸无关 ——
所以 A2 每条都带一个「必命中锚点」让开门槛，否则零命中的用例会先被门槛拦下（`why` 为 `null`），
断言会因为「出了门槛」而不是因为「匹配层判对了」变绿。

## 八、怎么撤销

门槛集中在**两处**，都以「返回 `null` 即放行」的形式存在：

- `server/engine.js:skillGate` —— 把 `if (kwHit(skills, kws).length) return null;` 之后加一行 `return null;`
- `平台原型/src/agent.js` —— 把 `if (kws.length && !kHit.length)` 改成 `if (false && kws.length && !kHit.length)`

（`tools/_rev_v16.py break` 做的正是这两处。）改完记得 `npm run build` 并 **把 `REQ_LIB_VER` 再加一**。
