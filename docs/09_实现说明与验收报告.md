## 一、目标、范围与优先序

### 1.1 为什么先做 M1（而不是先灌数据、先接模型）

`docs/05` 已给出判断：**企业级 ≠ 数据多，= 可信 + 可运维 + 可审计 + 可扩展**。而本项目当时的状态是——

| 现状（改造前） | 问题性质 |
|---|---|
| `server.js` 里 `DEMO_USER = req.headers['x-user'] \|\| 'U-001'` | **身份由客户端指定**。改一个请求头就能变成 HRD，全套「审计链 / 审批闸门 / 403 越权拦截」全部建立在可伪造的身份上 |
| 403 演示是**硬编码**的结论 | 有「越权被拦」的界面，没有「越权校验」的代码 |
| `consent_given` / `retain_until` 字段已设计 | 只有字段，**没有逻辑**（`docs/05` P1-3） |
| 手写 `migrate()` 做 `ALTER TABLE` | 无法从空库一键建到最新版本，也就无法验证「新环境能不能跑起来」 |

所以 M1 的排序理由是：**可信是一切的地基**。审计、审批、合规这些「企业级感」如果建立在可伪造的身份上，就只是布景。

### 1.2 本轮范围（In Scope）

- 自建账号 + 口令登录 + 服务端会话（可吊销）
- 三层权限：功能级（能力白名单）／行级（数据范围）／字段级（PII 脱敏）
- 审计「只插不改」，并把约束下沉到数据库层
- PIPL 数据治理：留存策略、授权留痕、删除权（匿名化 / 物理删除）、主体数据导出、到期巡检
- 版本化迁移（空库 → 最新版一键可建）
- 统一错误契约 + requestId 全链路 + 结构化日志（含脱敏）
- 限流、指标、优雅关闭
- 前端配套：登录闸门、按能力裁剪导航、**真会话**越权演示

### 1.3 非目标（本轮明确不做，避免范围蔓延）

- ❌ 不换 PostgreSQL（M1 验收口径里的「迁移到 PG」本轮**未做**，理由见 §七）
- ❌ 不做多租户隔离（`tenant_id` 仍是服务端常量 `T-001`）
- ❌ 不接任何真实大模型（保持规则模式）
- ❌ 不引入任何 npm 依赖（保持零依赖：Node 22 原生 `http` + `node:sqlite`）

## 二、关键决策（我替你拍的板 + 理由 + 被否掉的方案）

> 你说「需要拍板的你自行判断」。以下每条都按 `docs/07` 附录 A 的风格记录：**原方案 → 为什么否掉 → 改后方案 → 影响范围**。面试时「能讲出被否掉的方案」是证明「这是我做的」的唯一硬办法。

| # | 决策 | 原方案 | 否掉的理由 | 改后方案 |
|---|---|---|---|---|
| D1 | **技术栈** | 直接迁 TypeScript + PostgreSQL + pgvector（`docs/07` 的推荐 A） | **本轮要交付的是「可信」，不是「换语言」。** 迁库是高风险大工程，且**不降低企业级门槛**——身份照样可伪造。先把地基补上，迁移才有意义 | 保留零依赖 Node 22 + `node:sqlite`，但**按 `docs/08` 的 L0–L5 分层重构**；把「换 PG」降级为 M1 的**未完成项**并显式写出（§七） |
| D2 | **会话形态** | 纯 JWT（无状态、免存储） | JWT 的硬伤是**无法吊销**——HR 离职、口令泄露、批量改密，都无法立即踢下线 | 服务端**会话表 + 不透明令牌**（另有 HMAC 签名与指纹校验）。代价是多一张表、每次请求多一次查库（本地 SQLite 可忽略） |
| D3 | **口令存储** | bcrypt（需引入 npm 依赖） | 与「零依赖」硬约束冲突 | Node 内置 `crypto.scrypt`，存成自描述格式 `scrypt$N$r$p$salt$hash`（将来换参数不影响老口令校验） |
| D4 | **权限粒度** | 只在路由上标一个 role | role 一个维度不够：同是 HRBP，只能看本部门；同是招聘，**薪资字段不该可见** | **三层**：功能级能力白名单（18 个能力）＋ 行级数据范围（`all`/`dept`/`self`）＋ 字段级脱敏（PII 字段集） |
| D5 | **审计「不可篡改」的强度** | 只靠「代码里不写 UPDATE/DELETE」 | 应用层纪律挡不住 `sqlite3` 直连、挡不住将来某次手滑；且**无法自证** | **双层**：应用层只暴露 insert + **数据库层 `BEFORE UPDATE/DELETE` 触发器物理拒绝**。验收时可当场尝试 UPDATE 被拒 |
| D6 | **匿名化 vs 物理删除** | 一律物理删除（最彻底） | 删掉整个人，审计链就断了——「某人曾被评估过」这个事实消失，劳动争议时举证会断 | 默认**匿名化**（抹掉 12 个可识别字段，保留存在性与审计上下文），显式请求 `hard` 才物理删除 |
| D7 | **字段级脱敏放在哪一层** | 前端藏起来 | 前端藏 = 数据已到浏览器，抓包即得 | **服务端在出数据之前裁剪**（`scopeSnapshot`）。前端那层「按能力隐藏导航」只是界面减负，**明写不承担安全职责** |
| D8 | **错误返回形态** | 各接口自己定 `{msg}` / 抛异常 / 返回 `false` | 前端要为每个接口写一套判断；排障时无法用一句话定位 | 统一契约 `{ ok, error:{code,message,details}, requestId }` + 错误码表（10 个 code） |
| D9 | **本轮要不要前端一起改** | 只改后端，前端等 M5 | 后端上鉴权后前端**立刻全挂**（全部 401），演示资产作废 | 同轮改前端：登录闸门 + 令牌注入 + 按能力裁剪导航 + **越权演示改成真会话**（不再伪造头） |

### 3.2 认证与会话（D2 / D3）

| 机制 | 实现要点 |
|---|---|
| 口令存储 | `scrypt`，参数可配（N/r/p），存 `scrypt$N$r$p$salt$hash`；校验用 `crypto.timingSafeEqual`（防时序侧信道） |
| 登录 | 失败**文案统一**（「账号或口令不正确」），不区分「用户不存在 / 口令错」——防用户枚举 |
| 锁定 | 同一账号连续失败 5 次锁定，锁定期间同样返回统一文案 |
| 会话 | 服务端 `sessions` 表；令牌 = 随机不透明串；同时校验 HMAC 签名 + 指纹 + 过期时间 + 是否已吊销 |
| 令牌下发 | `Bearer` 头 **与** 服务端下发的 Cookie 双通道（前端用 Bearer，浏览器可依赖 Cookie） |
| 吊销 | 登出 / 改密 → **吊销该用户全部会话**；管理员可主动吊销某用户全部会话 |
| 过期清理 | 请求路径上**节流写** `last_seen_at`（不每次请求都写库——这是 `ADR-005` 那次 fsync 事故的直接教训）；进程内定时器清扫过期会话 |
| **不再信任 `X-User`** | `strict` 模式下后端**完全不读**该请求头；仅 `legacy` 模式保留（横幅打印「⚠️ 演示用，不可上生产」） |

### 3.3 三层权限（D4 / D7）

**① 功能级**：18 个能力（`kebab:action` 风格，如 `job:write`、`approval:decide`、`employee:export`、`governance:write`、`admin:user`），7 个角色（`admin / hrd / recruiter / hrbp / interviewer / employee / auditor`）。
**默认最小权限**：角色→能力是**白名单**，新角色默认无能力，必须显式授予。

**② 行级**：数据范围三档 `all / dept / self`。部门按**路径前缀匹配**（`/制造中心/装配车间` 属 `/制造中心`）；`self` 仅本人。

**③ 字段级**：无 `pii:read` 能力的角色，命中 PII 字段集即脱敏；**读取未脱敏的明细要写审计**（`needsPiiAudit`）。

**关键落点**：`routes.js` 的 `scopeSnapshot(db, ctx)` —— 在最前面就把数据裁掉。
> 注释里写明了为什么不能「全量返回 + 前端隐藏」：**数据已经到浏览器了，抓包即得**。

### 3.4 审计 append-only（D5）

| 层 | 做法 |
|---|---|
| 应用层 | `audit.js` 只导出 `record`（INSERT）与只读查询，**没有任何 UPDATE/DELETE 代码路径** |
| 数据库层 | 迁移 v4 建 2 个触发器 `trg_audit_logs_no_update` / `trg_audit_logs_no_delete`，`BEFORE UPDATE` / `BEFORE DELETE` 直接 `RAISE(ABORT)` |
| 写什么 | 所有写操作；**所有被拒绝的访问**（`result = 'blocked'`，越权尝试本身是情报）；敏感数据访问；Agent 的每次判断 |
| 失败处理 | 审计写失败**不让主业务崩**，但落 `error` 级日志（审计断链是必须排查的严重问题） |
| 401 vs 403 | **401 不写审计，403 才写**。理由写在代码注释里：401 是「还没登录」，浏览器首屏必然触发一次，写进去只会淹没真正的情报 |

### 3.5 PIPL 数据治理（D6）

| 能力 | 接口 | 说明 |
|---|---|---|
| 留存策略 | `GET/PUT /api/governance/policies` | 三类数据默认 180/180/90 天，各带**合规依据**（法条口径） |
| 授权留痕 | `POST /api/governance/consents`（+ `/revoke`） | 授权/撤销/过期三种状态；**转人才库需另行授权** |
| 到期巡检 | `POST /api/governance/sweep` | 支持 `dryRun`；到期 → 匿名化；进程内每 10 分钟自动跑一次 |
| 删除权 | `POST /api/governance/erasure` | 默认匿名化（抹 12 个可识别字段 + `anonymized_at` 标记），可显式 `hard` 物理删除 |
| 主体数据导出 | `GET /api/governance/subject/:id/export` | 一次性导出该候选人全部留存数据 |
| 治理概览 | `GET /api/governance/summary` | 候选人数 / 已匿名化 / 无有效授权 / 到期待清 |

**匿名化字段清单**（`governance.js` `IDENTIFYING_FIELDS`，共 12 项）：
`name→'已删除'`、`gender`、`birth_date`、`company`、`edu_text`、`skills`、`business_tags`、`plus_tags`、`ai_reasons`、`ai_note`、`override_reason`、`source`。

### 3.7 统一错误契约与可观测

| 能力 | 落点 | 说明 |
|---|---|---|
| 统一响应 | `errors.js` | `{ ok:false, error:{code,message,details}, requestId }`；10 个错误码：`BAD_REQUEST / UNAUTHENTICATED / FORBIDDEN / NOT_FOUND / CONFLICT / PAYLOAD_TOO_LARGE / UNPROCESSABLE / RATE_LIMITED / INTERNAL / UPSTREAM / UNAVAILABLE` |

## 四、异常处理覆盖清单

| 场景 | 行为 | 实测 |
|---|---|---|
| 无会话访问任一业务 API | `401 UNAUTHENTICATED`（**不再默认 HRD**） | ✅ 集成测试 [2]/[3] |

## 六、本轮抓到并修掉的真实缺陷

> 这 4 条**全部是在验证过程中被测试抓出来的**，不是「预想中的坑」。按「原方案 → 根因 → 改后 → 影响」记录。

### R1 · 空库启动崩溃：`table users has 15 columns but 8 values were supplied`

- **原方案**：种子用位置化 `INSERT INTO users VALUES(...)` 写 8 个值。
- **根因**：迁移 v2 给 users 补了 7 列 → 列数变 15。**只有全新库才会暴露**（老库因为表早已建好、种子跳过，一直正常）。
- **改后**：users 与 leave_balance 的种子改为**显式列名** INSERT。
- **影响**：这是「本地跑得好好的，一到新环境就崩」的典型；教训是**必须单独验空库路径**，不能只信已有环境。

### R2 · 超大请求体返回 413 却伴随 `ECONNRESET`

- **原方案**：`readBody` 检测到超限即 `req.destroy()`。
- **根因**：直接销毁连接，客户端还没读完响应就被重置 —— 表现为 `fetch failed`，用户看到「网络错误」而不是「请求体过大」。
- **改后**：**把剩余字节读完再丢弃**，然后正常返回 `413`，让连接可复用。
- **影响**：错误码能正确传给前端；也避免 keep-alive 连接池被污染。

### R3 · 测试用例「假绿」：403 用例被文案和种子数据糊过去

- **原方案**：① 断言 `drawer 文案里含 "403"`；② 断言 `存在 result='blocked' 的审计`。
- **根因**（两处，都很隐蔽）：
  - 前端 200 分支的说明文案里**本来就写着**「换个身份就会变成 403」→ 子串匹配永远为真；
  - 种子数据里**本来就有一条** `blocked` 的演示审计（`actor_type='system'`）→ 计数永远 > 0。
  - 更关键：测试脚手架注入的 `window.fetch` **无条件覆盖** `Authorization`，导致「切换到员工身份」那一步被测试自己的 HRD 令牌顶掉 —— 服务端看到的仍是 HRD，返回 200，**根本没发生越权**。
- **改后**：① 断言改为检查**渲染分支**（存在 `.scanwarn` 且含 `403 Forbidden`）；② 审计断言收紧为「`actor_type='user'` + `detail` 以『被拦截：』开头 + `object_id` 命中 `employees/export`」；③ 脚手架改为**只在前端未显式设置时才注入**令牌。
- **影响**：**这是本轮最有价值的一条。** 一个「永远是绿的」安全用例比没有用例更危险——它会让团队误以为越权已被拦住。安全断言必须**指向唯一的、真实的证据**。

### R4 · 匿名化候选人导致候选人库页面崩溃

- **现象**：`[render:candidates] Cannot read properties of null (reading 'split')`（时有时无，取决于库里有没有被匿名化过的候选人）。
- **根因**：PIPL 匿名化会把 `edu_text` 置为 `NULL`；前端该单元格直接 `c.edu.split('·')`（同一文件里另一处早已写成 `(c.edu || '')`，这一处漏了）。
- **改后**：① 前端做空值防御；② **后端**把匿名化候选人显式标为 `edu: '已匿名化'`、`company: '（已匿名化）'` —— 比让 UI 显示空白更诚实，也更符合「保留存在性」的治理意图。
- **影响**：治理功能与展示功能之间的**隐式契约**（「字段可能为空」）被显式化。

## 九、招聘链路闭环：把「已邀约」之后的断路接上（本轮追加）

### 9.1 问题：一条「画得很完整、后端为零」的链路

用户连着问了两个很朴素的问题：
> 「如果我是招聘专员，接受了 AI 的判断、简历进入下一阶段，下一阶段到谁了？」
> 「人力资源总监接受了 AI 的判断，进入下一步，下一步是给谁看？」

顺着这两个问题查代码，得到的是一个**不好看但必须承认**的结论（实测，非推断）：

| 现状（本轮之前） | 性质 |
|---|---|
| `/api/approvals` 的批准人只有 `hrd`；`recruiter` 能力表里只有 `approval:read` | 招聘专员**根本没有「接受 AI 判断」这个动作**（实测 U-002 调 approve → 403 `approval:decide`） |
| 批准后 `strong → 已邀约`、`ok → 原地不动`、`no → 已淘汰`（`engine.js`） | 「接受」不是统一前进，是三档分流 |
| 没有 `interviews` / `offers` 表，没有任何写入 `待面试 / 面试中 / 已入职` 的代码路径 | **「已邀约」是终点值，链路在这里断了** |
| `interviewer` 角色在 `rbac.js` 里有定义，但种子用户**无人担任** | 面试官是「有角色、没有真人」的幽灵 |
| 原型 23 页里 `invite` / `interview` / `offer` 三页画得最完整 | **全是静态演示**：面试官「王磊」在用户表里查无此人 |

一句话：**这条链的前 60% 是可信的（真鉴权、真审批、真审计），后 40% 是布景。**

### 9.3 状态机（唯一一份，写在 `hiring.js`）

```
已邀约 ──排期──▶ 待面试 ──面试官开场──▶ 面试中 ──┬─ 未通过 ─▶ 已淘汰
                                                   ├─ 待定   ─▶ 待复试
                                                   └─ 通过   ─┬─ 第 1 轮 ─▶ 待复试
                                                              └─ 第 2 轮 ─▶ 待发offer
待发offer ──招聘专员起草──▶ 待 HRD 审批 ──批准──▶ 已发offer ──候选人接受──▶ 已入职
                                        └─驳回──▶ 仍留 待发offer（可改后重起草）
                                        └─候选人拒绝──▶ 已淘汰
```

三条刻意的规则（都写在代码里、都有注释说明为什么）：

1. **一个人同时只能有 1 场未完成的面试**。否则「这一轮到底算不算过了」说不清，阶段流转会失真。要改约就先取消。
2. **轮次 = 已完成的面试数 + 1，取消不占轮次号**。否则「取消一次 → 重排」会把第 1 轮变成第 2 轮，于是「第 1 轮通过只进复试」这条规则被跳过 —— 人还没复面就直接进了 Offer。
3. **时间必须是 `YYYY-MM-DD HH:MM`**，模糊写法一律拒绝。排期是人的动作，时间不猜。

### 9.4 两条硬红线（代码级，不是提示词）

| 红线 | 实现位置 | 违反时 |
|---|---|---|
| **起草人不能批自己起草的 Offer** | `offer:create` 与 `offer:decide` 分离，HRD 独占后者；招聘专员在前端**看不到**批准按钮，即便手改 DOM 也会被服务端 403 | 403 `Forbidden` |
| **Offer 合规底线**：月薪 ≥ 北京市最低工资 **2,420 元**；试用期 ≤ **6 个月** | `hiring.checkOffer()` 在**创建前**校验，`block` 非空直接拒绝落库 | **422** `UNPROCESSABLE`，且**不产生** `offers` 记录 |

第 2 条是这一轮的「产品立场」样本：**合规不是「提示一下让人自己决定」，是校验失败直接不让创建**。
关键区分 —— *警告（warn）* 会返回给用户但仍创建；*阻断（block）* 则一行都不写。测试里专门验证了「1000 元被阻断后 `offers` 表仍为空」。

### 9.5 顺手修掉的两个真实缺陷

排查链路时发现的、与本轮同源的两个缺陷，一并修掉：

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **审批按钮没有能力守卫** | 招聘专员在「审核中心」看得见「✓ 批准并执行」，点下去才 403 —— 事后报错，不是权限设计 | 前端加 `canDo(ability)`，无能力时**隐藏按钮并显示锁定说明**；明确定位为「体验层，不承担安全职责」 |
| **403 文案把功能级当成行级** | 「缺少能力 interview:read」被说成「**数据范围**权限不足」，排查时误导 | 功能级 403 带 `details.level='ability'`（附 `need`/`role`）；行级 403 带 `details.level='scope'`；文案分别措辞 |

### 9.6 一致性收益：删掉 legacy 认证开关

M1 留下了 `AUTH_MODE=legacy` 作为「可回退」的对比模式，并且当时就自我标注了一句：
**「留开关 = 留后门」**。本轮把它**整个删掉**（`config.js` 里写死 `strict`，`server.js` 里删掉旧 `authenticate()` 分支）。

理由：一个「能让身份退化成可伪造」的开关，哪怕默认关闭，也是攻击面与被质疑点。**删掉它比守护它便宜。**

## 十、JD 生成口径修正：从「零散堆砌」到「自然行文」（2026-09-29）

### 10.1 现象与根因

HR 把一份 15 行的校招 JD **整段粘进「任职要求」**框，点「生成 JD」后拿到的是：

```
**（一）专业技能**
1. Agent产品经理我们在找一个对AI Agent充满热情的校招产品经理你是不是那种——Claude、Codex、Cursor一个不落
2. 天天琢磨"这玩意儿还能怎么用"?看到Agent自己规划、自己干活、自己交结果
...
6. • 从0到1定义一个真正"会思考、会干活"的Agent
7. • 把模糊的用户场景
8. 拆成能落地的产品方案
...
19. 有这些更香
20. AI产品实习经历 / 懂点技术能和工程对话 / ...
```

`20` 条碎片。根因不在排版，在**切条规则本身写错了**：

| 现象 | 根因 |
|---|---|
| 一句话被劈成两三条 | 切条表达式是 `split(/[,，;；\n]/)` —— **逗号、分号是句中标点，不是条目边界**。「和顶尖算法、工程团队并肩，把想法快速上线」因此在逗号处断成两条 |
| 行首多出一个 `·` | 原文里已有的 `•` 没被剥掉，渲染时又叠了一层编号（`6. ·从0到1…`） |
| 「你会做什么」自己成了一条 | 小标题没被识别，当成了普通要求 |
| 加分项内容混进「专业技能」 | 没有按小标题归位，所有内容都堆进第一个维度 |

### 10.2 三步改造（`shared/req-lib.js` 第七节，前后端共用一份）

| 步骤 | 做什么 |
|---|---|
| **A 还原** | 剥掉行首残留符号（`·` `•` `-` `1.` `（1）` `①` `##`）；把「上一行没说完」的断行合并回去（补上该有的逗号） |
| **B 归位** | 认出「你会做什么 / 我们想找这样的你 / 有这些更香 / 我们提供」这类小标题，内容分别落到 **职责 / 任职要求 / 加分项 / 福利** 四个桶；`≥2` 个小标题时，标题前的内容视为**引言** |
| **C 成段** | 同一维度不再逐条编号，用「；」串成一整段自然行文（`paragraphize`），维度名做粗体小标题 |

同时把「已填条目」的归位补了一路：软素质话术（热爱 / 同理心 / 主动…）单列一桶进「软技能」，
不再塞进「专业技能」。

### 10.3 关键取舍：条目边界 = 换行 + 行首符号

- **逗号、分号、顿号一律不再当分隔符。** 这条同时解决了「表单往返」问题：
  条目在入库前已被 `cleanReq` 剥掉尾部标点，只要表单从「用逗号拼接」改成「一行一条」，
  `载入岗位 → 保存` 就不会把多条要求黏成一条（实测往返条数不变）。
- **断行合并故意保守**：只在「上一行以句中标点结尾」或「上一行是列表项却没写完」时合并。
  若原文从**没有标点的地方**断开（`…会忍不住想这要是我来做` + `会做得更好。`），
  平台保持两条、用「；」衔接 —— **宁可少合，不可错合**。
- **小标题启发式收紧到 8 字以内**，并加了「要求句式」黑名单：
  `拆成能落地的产品方案`（10 字、无标点、下一行是条目）在开发过程中就曾被误判为小标题而**整条吞掉**，
  `有相关证书要求`、`3 年以上后端经验`、`熟悉Java` 同理 —— 这四条都已进回归用例。

### 10.4 落地清单

| # | 内容 | 文件 |
|---|---|---|
| 1 | 新增 `parseReqText / paragraphize / renderReqDims`，作为**前后端唯一一份**实现 | `shared/req-lib.js`（+147 行） |
| 2 | `toReqs` 不再按逗号切条；新增 `parseReqInput / splitReqInput`；维度归位加「软素质」桶；`renderReqs` 改为委托共用实现；`buildJD` 支持引言段 + 用户自写职责（≥3 条不再叠加模板） | `server/engine.js` |

### 10.6 还没做（诚实列表）

  这两项会退回模板（`must_have` 数组里已不含小标题结构）。彻底固化需给 `jobs` 加一列存结构，
  本轮判断属 YAGNI，未做。
- **小标题只认常见的十几种说法**：遇到没见过的写法会当普通条目处理（不会丢字），但不会归位。
- **断行合并的保守边界**（见 10.3）会在极端输入下留下两条，用「；」衔接。

## 十一、行业兜底口径修正：认不出职能时不得注入行业技能（2026-09-29）

### 11.1 问题：同一个 bug 换了条路又回来了

§十 修的是「JD 被逗号切成碎片」。紧接着查词库规模时发现，**「AI 产品经理带 Java」这个老 bug 并没有真正消失，只是被赶到了另一条路径上**：

```
输入：储备干部 / 互联网
fnKey = null（职能识别不出）→ 走行业兜底
专业技能维度：
   · 熟悉 Java，能独立应用于实际业务场景
   · 熟悉 Spring Boot，能独立应用于实际业务场景
   · 熟悉 Spring Cloud，能独立应用于实际业务场景
   · 熟悉 MySQL，能独立应用于实际业务场景
```

v0.9.2 引入「职能族优先」时，只堵住了「认出职能」的那条路；**认不出职能时仍然回落到行业库**，而行业库整份是按「该行业的主力职能」写的：

| 行业 | `INDUSTRY_SKILLS[行业].core` 实际内容 |
|---|---|
| 互联网 | Java · Spring Boot · Spring Cloud · MySQL · Redis · 微服务 · 高并发 · Kafka … |
| 医疗健康 | 护理管理 · 院感控制 · 护理质控 · 临床护理 · 急救技能 … |
| 制造业 | 精益生产 · 5S · 排产 · TPM · 标准工时 · 工艺优化 … |
| 金融 | 风险识别 · 信贷审核 · 反欺诈 · SQL · 尽职调查 · 反洗钱 … |

于是「城市经理 / 医疗健康」被补上「熟悉护理管理」，「跟单员 / 金融」被补上「熟悉反洗钱」—— 与「储备干部 / 互联网 → 熟悉 Java」是**同一个错误的三种表现形式**。

同一个错误的波及面更大：`INDUSTRY_REQ[行业]` 的 `majors / general / soft / nice` 同样是「该行业主力职能」的口径（互联网那一份写的是「技术方案」「技术栈」「开源 / 专利」），所以**综合素质、软技能、学历专业、加分项**都会被同一个错误污染。

**影响面实测**：现有 **21 个种子岗位全部命中职能族（21/21）**，所以这是**潜在缺陷而非活跃缺陷** —— 但只要新建一个「储备干部」「城市经理」就会触发。

### 11.2 改法：认出职能才允许用行业素材

用一条规则替换掉原先的「职能族优先、行业兜底」写法：

| 情况 | 专业技能 | 加分项 | 综合素质 / 软技能 / 学历专业 |
|---|---|---|---|
| **认出职能族** | 按职能族 `core` 补位（不变） | 按职能族 `nice`（不变） | 按职能族（不变） |
| **认不出职能族** | **一律不补硬技能**，写「掌握 {岗位} 所需的核心专业技能，能独立完成岗位交付」 | **不从行业库取**；空则 JD 写「暂无特别加分项，如有相关经历欢迎在面试中说明」 | 退回 `INDUSTRY_REQ['通用']` 的中性口径 |

**为什么行业维度没有被丢掉**：行业对 JD 的正当贡献是 `INDUSTRY_CTX` 那句「在什么赛道做、盯什么指标、说什么行话」（见 §三 行业语境句），由 `industryDuty()` 拼在**岗位职责**之后，与「补什么技能」是两条独立路径。丢掉的是「凭行业猜技能」，留下的是「凭行业说行话」。

**前后端同源**：`server/engine.js` 的 `expandRequirements` 与 `平台原型/src/agent.js` 的 `expandReqs` 是同构的两份实现，必须一起改 —— 否则离线演示态与真实后端态产出的 JD 会不一致。

|---|---|

**本轮追加（§十二 · 筛选质量评测 + 并发实测 + 工程化补齐）**：

起因：一次「面试官视角」的缺口审计发现，项目能证明「跑得通」，但答不出三件事 —— **判得准不准 / 扛不扛得住 / 能不能被别人一键跑起来**。本轮把这三块补上。

**① 筛选质量有了数字（新增 `tools/golden/golden_set.json` + `tools/test_eval.js`）**

- 黄金集：3 个岗位（高级 Java 工程师 / AI 产品经理 / 软件实施管培生）× 10 例 = **30 例人工标注**，每例带人工档位（strong/ok/no）与决定性因素说明。
- 评测口径：档位一致率 / ±1 档一致率 / **漏筛率**（该通过却被判 no）/ **误筛率**（该淘汰却被判 strong·ok）。口径在代码与文档里都写死，避免「一致率」被含糊解释。
- 实测：一致率 **90.0%**（27/30）、±1 档 **100%**、漏筛率 **0.0%**、误筛率 **25.0%**。
- 关键结构保证：评测调用的 `evaluateCandidate` 与线上筛选**是同一个函数**（本轮把硬性门槛抽成 `ruleGate`、合成判定抽成 `evaluateCandidate`），避免「评测一套、线上另一套」。
- 3 例分歧全部同向（AI 过宽），且都是**有意埋的边界探针**（前端技术负责人 / 资深算法工程师 / 资深销售）。它们不是「评测没过」，而是本轮 `override_code` 枚举的设计输入。

**② 「进入优化数据集」从承诺变成数据（迁移 v6 + `shared/override-codes.js` + `GET /api/metrics/agreement`）**

- 原状：`override_reason` 是自由文本，存得下、**统计不了**，所以那句承诺是空的。
- 现在：9 个可归因原因码（`keyword_fuzzy` / `keyword_miss` / `experience_lost` / `gate_too_strict` / `biz_overrated` / `plus_overrated` / `parse_failed` / `compliance` / `other`）；人工结论三态（**确认** / 推翻·推进 / 推翻·否决）。
- 一致率接口返回样本数、一致率、**过严次数 / 过宽次数**、以及 byCode 分布 —— 最后这个分布就是「下一步该修什么」的排序清单。
- 一个刻意的设计取舍：**只记录推翻，一致率恒为 0**（样本里全是分歧）。因此「确认 AI 结论」也被做成一次真实落库操作，它不是为了多一个按钮，而是**一致率分母成立的前提**。
- 不做演示假数据：样本为 0 时接口返回 `rate: null` 并说明原因，不编一个好看的比例。

**③ 并发实测（新增 `tools/test_load.js`，单进程 Node，并发 20）**

| 阶段 | n | P50 | P95 | P99 | 吞吐 | 错误 |
|---|---|---|---|---|---|---|
| 纯读 | 240 | 22ms | 35ms | 42ms | 822 req/s | 0 |
| 纯写 | 40 | 11ms | 12ms | 15ms | 816 req/s | 0 |
| 读写混合 | 120 | 24ms | 39ms | 50ms | 779 req/s | 0 |

混合阶段 0 错误即说明 **WAL 的「读不阻塞写」在真实并发下成立**。边界要一并说清：这是**单进程单写者**的数字，不代表多实例生产容量。

**④ WAL 不再无限增长**

`db.checkpoint()` 支持 PASSIVE/FULL/RESTART/TRUNCATE；维护定时器用 PASSIVE（不打扰在途请求），**关闭与重置用 TRUNCATE**；`/api/health` 暴露 `wal.dbBytes / walBytes / shmBytes`。压测中 WAL 从 288KB 涨到 2.87MB（未触及 4MB autocheckpoint 阈值），正是「只写不 checkpoint 会怎样」的现场证据。

**⑤ 工程化补齐**

`package.json`（engines ≥22.5 + 分套件脚本）、`server/start.sh` + `start.bat`（去硬编码 Node 路径、版本校验）、`平台原型/build.js`（构建不再需要 Python）、`tools/run_all.js`（拉起隔离实例一键回归，不碰演示库）。压测作为 `optIn` 套件，默认回归不含它。

**⑥ 无障碍最小集（并诚实标注「最小」）**

`role="dialog"` + `aria-modal`、打开移入焦点 / 关闭归还、Esc 关闭、`th scope="col"`、提示区 `aria-live="polite"`、`prefers-reduced-motion`、`:focus-visible`、跳转链接。`test_prototype.js` 新增 1 项专门断言（含键盘实操：打开抽屉 → 焦点在浮层内 → Esc 关闭）。**完整 WCAG 审计未做**，不要当合规凭证用。

**⑦ 本轮又被测试抓出来的真实缺陷**

- `agrees()` 方向分支写反：一度把「AI 判不适合 + 人工推进」算成**一致**。是单元断言（`AI=no + 人工推进 → 不一致`）把它抓出来的 —— 这正是「口径要写成函数+断言」而不是散落在 if/else 里的理由。
- `LIVE.authMode` 初值 `'legacy'`：该字段只写不读，但初值会让人误以为还有伪身份后门，已改 `strict` 并注明用途。
- 前端「推翻并推进」按钮实际写死 `rejected_by_human`（否决）—— 名实不符，已改为**方向由 AI 档位推出**，并在后端加方向自洽校验（反向不符直接 400，避免污染一致率样本）。

**本轮口径（面试可直接引用）**：筛选评测**错误全部落在安全侧** —— 漏筛率 0（不会静默杀掉合格的人），25% 的误筛只是「多进一轮人工」。这不是「做得很好」，而是「错的方向可以接受，且我们量过」。
