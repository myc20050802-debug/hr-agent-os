## 零、一句话结论

**这个项目最危险的不是缺功能，是它在三处「自己说自己」的地方说了不准确的话。**

项目的核心竞争力被反复表述为「不编硬数字」「留痕可追溯」「规则前置 0 token」。而我在代码里找到的三处，恰好各自违反了其中一条：

- 筛选链路**没有调用任何模型**，却记录 `llm.score_resume`、报 token 数、在页面显示模型成本（¥）；
- 审计日志写着「已进入优化数据集」，而**优化数据集不存在**；
- 打分核心是一组手调阈值，却**没有任何一条测试或指标衡量它准不准**。

面试官只要打开一次 DevTools 或点开一次 `tool_calls` 表，这三条会同时暴露。而它们全部是**半天内能修完的**。

## 二、三条「言行不一」（最高优先，必须先修）

### 缺口 1 · 没有评测集 —— AI 岗的第一道题

**现状证据**

- 打分核心 `server/engine.js:219 scoreOne()` 是一组**手调阈值**：
  ```js
  const r1 = coverage >= 0.7 ? 0.95 : coverage >= 0.5 ? 0.85 : coverage >= 0.35 ? 0.7 : coverage >= 0.2 ? 0.55 : 0.35;
  const r2 = bizN >= 4 ? 1 : bizN === 3 ? 0.9 : ...
  const W = { 技能匹配: 40, 业务匹配: 30, 稳定性: 15, 加分项: 15 };
  const score = s1 + s2 + s3 + s4;
  // grade: score >= 78 ? 'strong' : score >= 60 ? 'ok' : 'no'
  ```
- 权重 40/30/15/15、分档 78/60、覆盖率拐点 0.7/0.5/0.35/0.2 —— **全是拍出来的，没有一处有依据**。
- 5 套测试共 ~350 条断言，**全部是契约测试**（权限、状态机、格式、字段），**没有一条验证「判得准不准」**。
- 全库 grep `eval` / `golden` / `准确率` / `precision` / `recall`：只在文档里出现，**代码里零实体**。

**为什么这是致命伤**：AI 产品经理岗，面试官问的第一个技术问题通常是「你怎么衡量你的 AI 效果」。只要答「靠人工看感觉」，前面所有工程深度都会被折价 —— 因为**没有评测的 AI 产品，本质上是在猜**。

**修法（小，但必须做）**

1. 造一个 30 份的**黄金集**：每份简历 × 4 档人工标签（strong/ok/no/需人工复核），标签由你**自己**先看完简历再定，不看 `scoreOne` 的输出。
2. 写 `tools/test_eval.js`，输出三个数：
   - **档位一致率**（strict）与 **±1 档一致率**（lenient）
   - **漏筛率** = 人工判 strong 而机器判 no 的比例 ← **这是 HR 场景最贵的一类错误**
   - **误筛率** = 人工判 no 而机器判 strong 的比例
3. 把这三个数写进 README 与验收报告。
4. 附一句最有分量的收口：**「拿到数之后我把 78/60 这两个阈值调过一次，重跑一致率从 X 升到 Y」** —— 这一句证明你懂评测驱动的迭代，比任何架构图都值钱。

> 数字丑没关系。`漏筛率 12%` 是工程结论，`不知道` 是没做。

### 缺口 2 · 筛选链路虚报模型调用与成本

**这是本轮审计最严重的发现，且它比表面看起来更深。**

**证据链**

| 环节 | 位置 | 事实 |
|---|---|---|
| 模型网关 | `engine.js:47 llm()` | 已实现，读 `LLM_API_URL` / `LLM_API_KEY`，未配置时返回 `null` |
| 全文件调用点 | `engine.js` | **`llm()` 只被调用 1 次**：行 377（员工自助问答）。**筛选与 JD 链路一次都没调** |
| 筛选链路 | `engine.js:67 runScreening()`（194 行） | grep `llm(` → **0 次命中**。即使配了 API Key，筛选仍然是纯 if/else |
| 却记录了模型调用 | `engine.js:151-155` | 每个候选人 `tokens += 160`，写入 `tool_calls.tool_name = 'llm.score_resume'`，并 `push(..., { tokens: 160 * n })` |
| UI 据此翻牌 | `app.js:334-335` | 判定逻辑是 `rule: !(opt && opt.tokens)` —— **有 tokens 就不显示「规则/代码（0 token）」标签**，改为显示 `<N> tok` |
| 页面显示成本 | `app.js:598-599, 640` | `tokens = scored*160 + cs*180`；`cost = tokens * 0.0000357` → KPI 卡「本岗位模型成本 ¥0.06」 |

**同一张卡片上还有这句**（`app.js:615`）：

> ⚙️ 执行顺序：**规则前置过滤**（硬性条件用代码判，**不花模型钱**）→ 物理剔除受保护字段 → 模型逐维打分 → PII 脱敏 → 写回 ATS

**即：同一页面上方说「不花模型钱」，右下方显示「模型成本 ¥0.06」。**

**为什么这条最要命**

项目的对外立场里有一句反复出现的红线：**「不编硬数字 —— 补一个看起来合理的写进 JD，就是对外承诺。」**（见 `样例/AI产品经理JD_模板结构.md` §10 三条红线）

现在的代码，在**默认演示模式**（不配 LLM，也就是面试当天会跑的那一种）下，把一个**凭空来的常数** 160 token/份 × 假单价 ¥0.0000357 算成了页面上的金额。这是用自己的行为推翻自己的原则 —— 面试官不需要多懂技术，只要问一句「这个 ¥ 是怎么来的」。

**修法（2 小时，三条都要）**

1. **让 `rule` 与 `tokens` 互斥**：规则模式下 `tokens` 一律置 0/null，UI 标签照常显示「规则/代码（0 token）」。
2. **工具名不要撒谎**：规则模式下 `tool_name` 应为 `rule.score_resume`，而非 `llm.score_resume`。或者更诚实 —— 保留 `llm.score_resume` 这个名字，但把 `rule: true` 显式写进 `params`。**留痕的意义是让人看清真实发生了什么，不是让日志好看。**
3. **成本改成「试算」并标来源**：KPI 卡改标题为「模型成本（试算）」，副标题写明「按 ¥X/1k tokens 估算；当前为规则模式，实际调用 0 次」。要么就别显示金额，显示「本次未调用模型」。

**修完的收益不只是止损**：这反而是一个能主动讲的加分点 ——
> 「我一度在规则模式下也报了 token 和成本，因为想演示效果看起来完整。后来发现这违背了我自己定的『不编数字』原则，就改成规则模式一律显示 0，并在卡片上注明单价来源。**一个 AI 产品如果连自己的成本数字都不可信，业务方就不会信它的任何输出。**」

1. **把承诺收回来或兑现**，二选一。建议兑现，因为成本很低：
   - `override_reason` 加一个 `override_code` 枚举字段（如 `AI漏筛-确有经验` / `AI误判-技能不对口` / `AI评分偏高-软素质存疑` / `其他`）；

### 缺口 6 · WAL 从不 checkpoint

`server/db.js:387-388` 只设了两个 PRAGMA：

```js
try { db.exec('PRAGMA journal_mode = WAL;'); } catch { ... }
try { db.exec('PRAGMA busy_timeout = 5000;'); } catch { ... }
```

**没有 `wal_checkpoint`**。实测结果在磁盘上：主库 **376 KB**，`-wal` **4.2 MB** —— WAL 是主库的 **11 倍**，且只会继续涨。

**修法**：`db.js` 里加 2 行 —— 启动时 `PRAGMA wal_checkpoint(TRUNCATE)`，并按间隔（或按写入条数）定期 checkpoint。

> **更重要的价值**：这是个能**主动讲**的题。「SQLite WAL 只增不减，我压测时发现 4.2MB 的 WAL 配 376KB 的主库，加了两行 checkpoint。」—— 这句话的含金量在于它展示你知道存储引擎的生命周期，而不是只会调 API。

### 缺口 7 · 没有并发/压测

限流有（令牌桶，`config.js:105-109`：登录 10 次容量 / API 600 次容量），**但从没被压过**。SQLite 是单写者 + `busy_timeout 5000`，并发上限完全没有数据。

**修法（半天）**：`autocannon` 或裸 `node` 起 50/100/200 并发打 `/api/health` 与 `/api/bootstrap`，记录 P50/P95/P99 与错误率。哪怕结论是「50 并发后 P95 超 1s，单机 SQLite 的天花板在这」，**这个数字本身就是面试答案**。

## 四、演示现场风险（当场会尴尬的那几处）

### 缺口 8 · 一个死按钮：`resetJobScores`（**演示复跑必经路径**）

`app.js:1780`：

```js
$('#drawerFoot').innerHTML = `<span class="small muted">该岗位没有待处理简历（都已有评分）</span>
  <button class="btn ghost" data-act="closeDrawer">关闭</button>
  <button class="btn" data-act="resetJobScores" data-id="${esc(job.id)}">重置本岗位评分后重跑</button>`;
```

我用括号匹配解析了整张 `ACT` 分发表（46,329 字符）：**57 个处理器 vs 50 个页面动作，唯一缺失的就是 `resetJobScores`**。

**为什么这条虽小却该优先修**：它出现在「所有简历都已有评分」的状态下 —— **而这正是面试官第二次演示、或你自己彩排一遍之后再点「运行筛选 Agent」时的状态**。它是唯一的恢复路径，点下去毫无反应。演示卡住比功能缺失丢分得多。

### 缺口 9 · 两个装饰性下拉

`app.js` 筛选页有两个 `<select class="i">` **没有 id、没有 data-act**：「时间范围」与「模型路由（自动/强制推理模型）」。选了不生效。面试官随手一拉问「切到强制推理模型会怎样」，没法答。

**修法**：接上真实行为，或直接标 `disabled` + 「规划中」。**宁可标未实现，也不要留一个假装能用的控件** —— 与 §二 的三条同一个道理。

### 缺口 10 · 无障碍为 0

| 指标 | 实测 |
|---|---|
| `aria-` / `role=` 属性 | **0 处** |
| `@media` 查询 | **1 条** |

对 HR 系统这是**真实业务缺口**（政务、国企、大客户的采购评标普遍含无障碍要求）。作为面试加分项，最小改动是：所有图标按钮补 `aria-label`、表格补 `<th scope>`、弹窗补 `role="dialog"` + 焦点陷阱、加 `prefers-reduced-motion`。

### 缺口 11 · `LIVE.authMode` 默认值仍是 `'legacy'`

`app.js:129`：`const LIVE = { on: false, mode: 'rule', authMode: 'legacy' };`

而 `legacy` 认证模式**已从后端彻底删除**（`config.js` 里已硬编码 `AUTH_MODE = 'strict'`，`server.js` 里已移除分支）。上一轮的验收结论写的是「legacy 已删除」。**离线模式下前端仍会显示一个不存在的模式名** —— 自相矛盾的残留。

**修法**：1 行，改成 `'strict'`。或直接去掉这个字段。

## 五、叙事层（不是 bug，但影响评分）

### 缺口 12 · 「AI 含量」这一题，要主动讲，别等面试官发现

事实：`llm()` 已实现，但**全项目只在员工问答那一处被调用**。筛选、JD 生成全靠规则。默认演示模式下**零模型调用**。

这**不是缺点**，但**必须由你主动定义叙事**，否则会被理解成「其实没做 AI」：

> 「我刻意让它在**没有模型的情况下也能完整跑通**。因为 HR 场景的真正难点不是接一个 API —— 是权限落在出数据之前、是合规底线不能被模型绕过、是每条结论可追溯。**模型只负责规则做不了的那一步（语义理解与语言组织），我在架构上把它隔离成一个可插拔环节；接上模型是替换一个函数，不是改架构。**」

配套要说的一句（**且必须是真话** —— 现在筛选链路连调用点都没有，这是缺口 2 要修的）：
> 「筛选链路目前是规则模式，`llm.score_resume` 这一步是预留的插槽。」

**先修缺口 2，再说这句话。** 否则第二句就是假的。

### 缺口 13 · 单文件 436KB 前端 / 无 lint / 无类型

`平台原型/index.html` = **436,904 bytes**，`src/app.js` = 2,775 行。

有正当理由（**断网可演示**、零依赖分发、双击即开），但**要自己先说出代价**：
> 「单文件的代价是没法按需加载、没有构建期校验。我付这个代价是因为演示场景常常没网。如果是长期维护的项目，我会拆成模块 + 加构建。」

**主动承认取舍** 永远优于被问出来。

### 缺口 14 · 没有部署路径

无 Dockerfile、无 CI、绑定 `127.0.0.1`。私有化单租户部署正是这个产品的卖点，所以「怎么上生产」要有答案。`docs/05_从PoC到企业级的差距清单.md` 已经写了，**面试时把它当成路线图讲出来即可**（这份文档的存在本身就是加分项）。

### 缺口 15 · 产品边界未闭环（上轮已列，此处汇总）

## 六、三个必被问到的问题 & 建议答法

### Q1「你的筛选 Agent 准确率多少？」
- **现在**（不推荐）：『靠人工看，感觉挺准的。』→ AI 岗直接失分。
- **补完缺口 1 后**：『我做了 30 份人工标注的黄金集，档位一致率 X%、±1 档一致率 Y%。**漏筛率 Z% 是我最关注的** —— HR 场景里把好简历判死的代价，远高于把差简历放进面试。所以我后来把 `strong` 的阈值从 78 调到了 72，宁多勿漏。』

### Q2「这个 token 数和 ¥ 成本怎么来的？」
- **现在**（危险）：会暴露为常数。
- **补完缺口 2 后**：『规则模式下是 0，页面直接标「未调用模型」。只有配置了 LLM 才是真实用量 —— 我用的是**规则前置省调用**：硬门槛拦掉的简历根本不进模型，`tool_calls` 里能查到每次拦截省下的调用次数。』
- **加分收口**：『我一度在规则模式也显示了试算成本，后来觉得违背了自己「不编数字」的原则就撤了 —— **成本数字不可信的产品，业务方不会信它的任何输出。**』

### Q3「这是不是 AI 一次生成的？」
- **决定性证据是 `git log`**。补完缺口 4 之后，你可以直接展示：**「行业兜底把 Java 补进产品岗」这个 bug 从发现到修复的完整提交链**，以及 `docs/09` 里记录的「删库重启硬验证」。
- 附一句：**「我的工作方式是让 AI 写，但我必须能解释每一行为什么这么写 —— 所以我把每个坑都写成了回归用例。」** 然后打开 `tools/test_jd.js` 第 8 节给他们看那条**跨 5 个行业的零泄漏回归**。
