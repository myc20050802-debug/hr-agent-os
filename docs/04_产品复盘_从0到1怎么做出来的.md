# HR-Agent OS · 从 0 到 1 产品复盘

> **这份文档是「我作为这个产品的产品经理，从 0 到 1 是怎么做出来的」的完整叙述。**
> 写作口径：第一人称述职体，可直接用于面试陈述、项目答辩、晋升材料。
> 事实纪律：所有产出物都是本仓库里真实存在的文件；标注「目标值」的数字是设计目标，**未经 pilot 实测**，不冒充已验证结果。

---

## 开篇 · 30 秒说清我做了什么

> 「我负责的是一款面向 200～5000 人企业的 **HR 数字员工平台**。它把招聘筛选、入转调离、员工咨询、人力报表这四件事，从『HR 手工操作』升级为『AI 自主执行 + 人审核确认』。
> 我没有从功能清单出发，而是从 HR 真实的一天出发——他们 80% 的时间花在查资料、搬数据、催流程，只有 20% 在做判断。我做的就是把那 80% 交给 AI，把判断和签字权留给人。
> 目前交付到 **可运行 PoC**：完整 PRD、8 阶段落地教程、24 页可点击原型、以及一套真跑 SQLite 的本地全栈 MVP，双模式回归测试全绿。」

**一句话定位**：先有判断，再有功能；能用规则的绝不用模型，该人签字的绝不交给 AI。

| 7 · 合规与安全 | 把红线写进代码，不写进提示词 | 歧视 11 条 + 违法 9 条规则表 / 审计链 | 命中即阻断发布，每条带法条依据 |
| 8 · 能力迭代 | 从硬编码走向可运营 | 岗位库驱动 + 任职要求六维度 | 岗位可自建、跨 7 行业，回归全绿 |

## 阶段 0 · 立项判断：先决定这产品该不该存在

### 我做的动作

1. **写非目标（Non-goals）先于写功能** —— 我先花时间列清楚「不做什么」，因为 B 端产品的死法几乎都是「什么都做」。
2. **划定期客群边界** —— 一期锁定 200～1000 人企业（有 3～10 人 HR 团队、用飞书/钉钉、ATS 可能只是 Excel）。明确放弃两端：50 人以下付费能力弱但决策链一样长；超大型集团是定制化黑洞，会拖垮交付。
3. **画价值链路，不画功能清单** —— 先定北极星指标，再倒推要做什么功能。

### 关键决策：不做完整 HRIS，只做 AI 层

| | |
|---|---|
| **原方案** | 做一个完整的 HR 系统（含薪酬核算、组织架构、考勤） |
| **我否掉的理由** | 这是北森/Workday 的地盘。正面硬碰，我们既没有数据积累也没有交付能力。而且客户已经买了，不会为了 AI 换掉底座 |
| **改后方案** | **只做 AI 层，通过接口读写客户现有的 HRIS/ATS** —— 我们是「长在别人系统上的数字员工」，不是「替代别人系统的又一套系统」 |
| **影响范围** | 架构上多出「第三方对接层」，交付从「替换」变成「集成」，销售周期大幅缩短 |

### 其余四条「不做」

| 不做 | 理由 |
|---|---|
| 自动发 Offer / 自动辞退 | 高风险不可逆，法律与舆情成本远高于省下的工时 |
| 「全自动无人招聘」 | 招聘本质是人的判断，AI 只负责「排好序 + 备好材料」 |
| 简历爬虫抓取 | 数据来源必须合法授权，否则是给客户埋雷 |
| 一期做视频面试分析 | 反歧视合规风险高、技术不成熟，容易被投诉 |

**产出物**：`docs/01_产品需求草稿PRD.md` → 1.1 定位 / 1.3 客户分层 / 1.6 Non-goals

> 🎤 **面试这么说**：「我立项时写的第一个文档不是功能清单，是非目标清单。因为 B 端产品最常见的死法不是做得不对，是做得太多。我明确划掉了薪酬核算、自动发 Offer、视频面试分析——划掉它们，才腾出资源把招聘筛选这一件事做深。」

## 阶段 1 · 业务发现：把「痛」变成可证伪的问题

### 我做的动作

1. **不抄需求，先看场景** —— 我没有拿一份「HR 需要 AI」的行业报告就开工，而是先还原 HR 真实的一天（As-Is）。
2. **给每个痛点标耗时，并追问病根** —— 把「感觉效率低」这种不可证伪的抱怨，落成表里的耗时数字和 Root Cause。
3. **从病根归纳出一条共性判断**，这条判断后来成了整个产品的立论基础。

### As-Is 现状（真实还原）

| HR 的一天 | 耗时 | 病根 |
|---|---|---|
| 翻 80 份简历，逐个看学历/年限/技能，凭感觉分堆 | 3～4 小时 | 判断标准在脑子里，没有结构化，无法复用 |
| 挨个给候选人打电话约面试，来回改时间 | 1.5 小时 | 协调类工作无法批量处理 |
| 员工微信问「年假剩几天」「社保基数怎么算」，一天被打断 20 次 | 2 小时 | 制度文档写得全，但员工懒得翻、HR 懒得答 |
| 每月手工扒考勤、做招聘漏斗、拼周报 | 4 小时/月 | 数据散在 ATS、考勤机、Excel 里，靠人工搬运 |
| 入职材料催 8 遍收不齐，转正日期记错导致纠纷 | 隐性风险 | 流程靠人记，没有系统盯着 |

### 关键决策：价值主张不写「提效」，只写三个数字

| | |
|---|---|
| **原方案** | 价值主张写「AI 赋能 HR，全面提升人效」 |
| **我否掉的理由** | 客户听不懂、销售不会讲、上线后无法验收。「赋能」「提升」这类词，买的时候无法判断，交付时无法对账 |
| **改后方案** | 核心价值 = **三个可计数的数字**（见下表），每个都配销售话术 + 可量化指标 |
| **影响范围** | 这三个数字后来直接变成 MVP 的 Go/No-Go 验收指标 |

| 价值主张 | 客户语言 | 对应指标 |
|---|---|---|
| 省时间 | 「HR 每天花 3 小时筛简历，我们压到 20 分钟复核」 | 简历初筛人效提升 ≥ 70% |
| 少出错 | 「转正漏提醒、材料收不齐，系统替你盯着，出事有留痕」 | 流程逾期率下降 ≥ 60% |
| 能说清 | 「老板问上月招聘情况，30 秒出一张漏斗图」 | 报表产出时间 4 小时 → 5 分钟 |

> ⚠️ **诚实标注**：以上为**设计目标（Target）**，需 pilot 阶段实测验证，当前尚未取得真实客户数据。

### 关键决策：KPI 树里必须有「护栏指标」

大多数人的 KPI 树只往下拆增长指标。我在同一棵树里放了**必须为 0 的护栏指标**：

```
业务目标：让 HR 用同样人数，支撑更多员工 / 更快招聘
  └─ 北极星：每周由 AI 完成并被采纳的 HR 任务数（Accepted AI Tasks / Week）
       ├─ 业务 KPI：招聘周期 / 单人 HR 支持员工数 / 流程逾期率
       ├─ 产品指标：Agent 任务完成率 / 采纳率 / 人工接管率
       ├─ AI 指标：打分与人工判断一致率 / 问答有依据率 / 幻觉率
       └─ 护栏（必须为 0）：越权访问次数 / 敏感信息外泄次数 / 高风险动作未审批执行数
```

**为什么？** B 端 HR 系统一旦泄露简历或错发 Offer，客户会直接解约。**护栏指标不为 0，前面所有增长都是泡沫。**

**产出物**：`docs/01` → 1.2 As-Is / 1.4 三个数字 / 1.5 KPI 树

> 🎤 **面试这么说**：「我做的第一件事是把『效率低』这种抱怨，变成一张带耗时和病根的 As-Is 表。归纳出来的病根是——HR 80% 的时间在查资料、搬数据、催流程，只有 20% 在做判断。这 80% 恰好是 AI 最擅长也最容易被量化的部分。这个判断决定了整个产品的边界。」

## 阶段 2 · 产品决策：哪里用 AI，哪里坚决不用

**这是整个项目最关键的一步，也是我认为最能体现产品经理价值的一步。**

### 关键决策：四边界划分（Agent 决策 / Workflow 执行 / Rules 约束 / Human 治理）

我没有把「AI Agent」当成产品的答案，而是先问每一件事：**它到底该由谁来干？** 最后落成一张边界表：

| 业务模块 | 谁主导 | 为什么 | 反面做法（我否掉的） |
|---|---|---|---|
| 简历筛选打分 | **Agent** | 判断标准模糊、需要理解语义、路径动态 | 写死规则筛选器（招不到跨行业岗位） |
| ATS 写回 / 发通知 | **Workflow** | 步骤稳定、必须可重试、必须幂等 | 让 Agent 自由决定要不要写（不可控） |
| 年限/学历/金额校验 | **Rules（代码）** | 强约束、必须 0 误差、必须可审计 | 让模型判断「他算不算符合」（会漂） |
| 录不录用、发不发 Offer | **Human** | 高风险、不可逆、法律责任在人 | 自动发 Offer（舆情与法律成本不可承受） |
| 入转调离流程 | **Workflow（80%）** | 大部分是定时触发 + 状态流转，压根不需要 AI | 为了「AI 含量」强行让模型参与 |
| 人力报表取数 | **Rules（算）+ 模型（说）** | **模型只做翻译，不做算数** | 让模型算数（算错一次就没人信了） |

### 关键决策：能用规则的，绝不用模型

| | |
|---|---|
| **原方案** | 简历打分全部交给大模型，输入 Prompt 让它给分 |
| **我否掉的理由** | ① 分数不可复现，同一个候选人两次跑出两个分，HR 无法信任；② 每次筛选烧 token，成本随简历量线性上涨；③ 无法做回归测试，出了 bad case 只能改 Prompt 凭感觉 |
| **改后方案** | **规则前置（0 token）**：年限/学历这类硬门槛用代码判，**在打分之前就把不合格的物理拦掉**；模型只做它真正擅长的事 |
| **效果** | 硬性条件判定 100% 确定、可复现、零成本；同时把候选池先收敛一遍，后续模型/规则处理量下降 |
| **影响范围** | 引擎里多出一个 `rule.gate` 步骤，演示时能明确看到「这一步没花 token」 |

### 关键决策：LLM 网关可插拔 + 降级设计

| | |
|---|---|
| **原方案** | 直接调用大模型 API，失败就报错 |
| **我否掉的理由** | 演示现场断网/欠费/限流，产品直接白屏——这是 B 端演示的致命伤；而且客户私有化部署时未必要用同一家模型 |
| **改后方案** | 抽象 `llm()` 网关：未配置 key 时走**规则模式**（离线可跑），配置任意 OpenAI 兼容接口即切真实模型；**调用失败自动 fallback，页面不报错** |
| **影响范围** | 产品具备「无网可演示、单机可部署、模型可替换」三个能力，同时把「AI 不是必需品」这件事做成了架构事实 |

**产出物**：`docs/02_搭建实操教程.md` → 3.3 工具注册中心（只读免审 / 写操作确认 / 高风险必审）、4.4 入转调离（"大部分用 Workflow，不用 AI"）、4.5 报表（"模型只翻译，不做算数"）

> 🎤 **面试这么说**：「这个项目里我最坚持的一件事，是**不为了 AI 而 AI**。入转调离 80% 用 Workflow，报表里模型只做自然语言翻译、不参与算数，年限学历这类硬门槛用代码判、0 token。我把判断依据做成了一张四边界表——Agent 决策、Workflow 执行、Rules 约束、Human 治理。能讲清这张表，比多堆三个 Agent 更能说明我懂 AI 产品的边界。」

## 阶段 3 · 产品建模：先定对象，再画页面

### 我做的动作

1. **反着来设计** —— 不从页面开始，而从「系统里到底有哪些核心对象」开始。
2. **先定对象与关系，再定表结构，最后才是功能与页面**。顺序错了，后面每一层都要返工。
3. **把权限和状态在建模阶段就画清楚**，而不是等开发来问。

### 设计顺序（我实际执行的）

```
核心对象（岗位 / 候选人 / 员工 / 审批单 / 审计记录）
  → 对象关系与生命周期（候选人如何流转、审批单如何关闭）
  → 数据表结构（按对象建表，不按页面建表）
  → 业务规则（哪些条件不可绕过）
  → 状态机（谁能把对象从 A 推到 B）
  → 权限矩阵（Role → 资源 → 动作 → 数据范围）
  → 最后才是页面与交互
```

### 关键决策：反歧视靠「物理剔除字段」，不靠提示词

| | |
|---|---|
| **原方案** | 在 Prompt 里写「请勿参考候选人的性别、年龄、婚育状况」 |
| **我否掉的理由** | ① 提示词约束是「请求」不是「保证」，模型可能仍然隐式使用；② 审计无法证明它没看——出事时你拿不出证据；③ 换模型就得重测一遍 |
| **改后方案** | `gender` / `birth_date` **根本不进入任何打分查询语句**（在数据访问层就被排除），模型在物理上拿不到这些字段 |
| **影响范围** | 产品从「我承诺不歧视」变成「我**在架构上做不到**歧视」。这句话在销售和法务场景里是完全不同量级的分量 |

### 关键决策：高风险操作强制人工闸门（HITL）

| | |
|---|---|
| **原方案** | Agent 跑完直接把结果写回 ATS |
| **我否掉的理由** | 不可逆 + 影响候选人 + 一旦错判客户会追责，「自动化率好看」抵不过一次事故 |
| **改后方案** | 所有高风险写操作**排队进闸门**，人工批准后才真执行；**驳回必须填原因，且服务端硬校验（不填返回 400）** |
| **影响范围** | 产品里多出「审核中心」模块；同时驳回原因沉淀成优化数据集 —— **人工审批不只是风控，还是数据飞轮的入口** |

### 关键决策：审计链保护 —— 有候选人的岗位不能物理删除

| | |
|---|---|
| **原方案** | 删除就是 `DELETE` |
| **我否掉的理由** | 一个已经筛过 30 份简历的岗位被删掉，审计链就断了。合规场景下「这个决定当时谁做的」必须答得出来 |
| **改后方案** | 有候选人的岗位删除 → **转「已关闭」状态**，不物理删除；无关联数据才真删 |
| **影响范围** | 产品具备「操作可追溯」的底线能力，而不是等审计时才发现数据没了 |

**产出物**：`docs/02` → 2.1「设计表的顺序（不要按页面设计，按对象设计）」、2.2 建表 SQL、2.3 多租户隔离、4.6 HITL 闸门；`docs/01` → 4.4 权限隔离 / 5.4 多角色权限矩阵

> 🎤 **面试这么说**：「反歧视这件事，我没有写在提示词里，而是把性别、出生日期这类字段**从打分查询里物理剔除了**。区别在于：写提示词是『我请求模型别看』，物理剔除是『模型根本拿不到』。合规审查要的是后者——出事的时候，你得拿得出证据。」

## 阶段 4 · 方案设计：七部分 PRD，给业务方看的

### 我做的动作

1. **七部分结构** —— 定位 / 架构 / 模块 / 底座 / 合规 / MVP / 菜单，从「为什么做」一路推到「点哪个菜单」。
2. **第 0 部分先统一语言** —— 术语表（通俗版），让 HR 和法务也能读懂。
3. **把「不确定」写进正文** —— 附录 A 待验证假设清单、附录 B 开放问题（需拍板才能定稿）。
4. **主动写自我挑战** —— 2.6 架构自我挑战（必须承认的风险），不等评审来挑。

### 关键决策：PRD 里公开写「我可能错在哪」

| | |
|---|---|
| **原方案** | PRD 只写方案，风险留在评审会上口头讨论 |
| **我否掉的理由** | 口头讨论没有留存、容易被遗忘、出了事无人认账；而假设不写下来，就永远不会被检验 |
| **改后方案** | 专门设「6.4 关键假设与被否证的可能」+「附录 A 待验证假设清单」+「附录 B 开放问题」 |
| **影响范围** | 评审时讨论质量明显提升——大家不再论证「方案对不对」，而是直接攻击「假设成不成立」；同时也让这份 PRD 具备了迭代性 |

### 关键决策：Agent 底座六件事，一件不能少

我没有把「接个大模型 + 写个 Prompt」叫 Agent。底座单独成章（第四部分），六项能力必须齐：

| 能力 | 不做的后果 |
|---|---|
| 任务规划拆解（Planner） | Agent 变成一次问答，无法完成多步任务 |
| 工具调用（Tool Calling） | 只能聊天，不能动数据 |
| 长期记忆（Memory） | 每次对话从零开始，员工反复说同样的话 |
| 权限隔离 | 越权访问，B 端一票否决 |
| 敏感数据脱敏（PII Masking） | 简历信息泄露，直接解约 |
| 高风险操作人工审核（HITL） | 不可逆错误无人拦截 |

> **这六项是「B 端能用」与「Demo 很酷」的分界线** —— 也是最容易被跳过的部分，因为它们做出来「看不出效果」。

**产出物**：`docs/01_产品需求草稿PRD.md`（七部分 + 术语表 + 附录 A/B）；第 0 部分术语表 / 2.6 自我挑战 / 4.7 底座能力验收总表 / 6.2 Go-No-Go 指标 / 6.4 关键假设

> 🎤 **面试这么说**：「我的 PRD 里有一节叫『关键假设与被否证的可能』，还有一份待验证假设清单和开放问题清单。我坚持把『我可能错在哪』写进正文，因为假设不写下来就永远不会被检验。评审时大家不用再吵方案好不好，直接攻击假设成不成立就行——讨论效率完全不一样。」

## 阶段 5 · 原型验证：从纸面到可点击的 24 页

### 我做的动作

1. **做原型，不做 PPT** —— 判断类问题（这个入口放哪、这个状态怎么显示）用 PPT 讨论永远吵不出结论，点到手就知道。
2. **零依赖交付** —— 单文件 HTML，内联样式与脚本，**双击即开**，不装环境、不连网络。
3. **覆盖 24 个页面**，包括后台侧边栏菜单结构（`docs/01` 第七部分）全量落地。

### 关键决策：双模式架构（离线演示 / 在线真后端）

| | |
|---|---|
| **原方案** | 原型就是一堆假数据，给客户看个样子 |
| **我否掉的理由** | 客户会问「这是真的还是假的？」——一旦回答「假的」，前面所有可信度归零；而且假数据无法验证「闸门到底拦没拦住」 |
| **改后方案** | **同一份 `index.html` 双模式**：双击打开 = 离线演示（内置数据 + 内置 Agent 规则）；被 `server.js` 托管 = LIVE 模式，页面加载自动探测后端，探测成功即切换为真实链路 |
| **影响范围** | 一套前端两种用法：陌拜现场双击就演示（不怕没网），评审现场连后端真跑（不怕被质疑）。**这是解决真实约束的产品设计，不是技术炫技** |

### 关键决策：离线模式也不能说假话

| | |
|---|---|
| **原方案** | 离线模式的 JD 合规扫描直接返回写死的结论（「命中 3 处」） |
| **我否掉的理由** | 岗位内容已经可以由 HR 自由填写了，写死结论意味着**用户改了什么它都说同样的话**——这是在演示里撒谎，现场必翻车 |
| **改后方案** | 离线端也实现真实规则扫描（`src/agent.js` 内维护同源规则表），你写什么它就扫什么 |
| **影响范围** | 离线演示的结论可信；同时建立一条纪律：**演示态与真实态的结论必须同源** |

**产出物**：`平台原型/index.html`（**537,842 bytes（约 525KB）**，24 页，零依赖）+ `平台原型/src/`（app.css / data.js / agent.js / app.js / shell.html）+ `build.js`（打包脚本）

> 🎤 **面试这么说**：「我给原型做了双模式：双击打开是离线演示，不怕现场没网；被后端托管时自动探测、切成真实链路。客户问『这是真的假的』的时候，我可以直接把后端跑起来给他看。另外我定了一条纪律——离线模式的结论也必须是真扫出来的，不能写死。因为演示里的假话，现场一定会被戳穿。」

## 阶段 6 · 真后端 MVP：把「演示」变成「真跑」

### 我做的动作

1. **用零依赖技术栈把链路跑真** —— Node 原生 HTTP + 内置 SQLite，**不装任何一个 npm 包**。
2. **真库、真写、真拦、真留痕**：筛选打分真的写进数据库；高风险写操作真的被闸门拦下；批准/驳回真的改变数据并写审计日志；越权导出真的返回 403 并被记录。
3. **交付可复现的运行时** —— `start.bat` 双击启动，首次运行自动建库灌种子数据。

### 关键决策：零依赖技术选型

| | |
|---|---|
| **原方案** | 后端用常规框架（Express + ORM + 一堆中间件） |
| **我否掉的理由** | ① 面试/演示场景下，评审方不会帮你装环境，`npm install` 失败一次演示就废；② 依赖越多，「跑不起来」的不可控因素越多；③ 我的目标是证明**链路成立**，不是证明我会配框架 |
| **改后方案** | Node 22 原生 `http` + `node:sqlite`，前端单文件内联，**全仓库零 npm 依赖** |
| **影响范围** | 任何装了 Node 的机器，clone 下来就能跑；演示风险降到最低 |

### 关键决策：老库升级用「迁移」而不是「重建」

| | |
|---|---|
| **原方案** | 表结构变了就删库重建 |
| **我否掉的理由** | 删库意味着演示数据全丢（客户会记得上次演示的岗位）；而且在 Windows 上删库文件常被进程锁住（EBUSY），重置反而失败 |
| **改后方案** | 启动时读 `PRAGMA table_info`，缺列就 `ALTER TABLE ADD COLUMN` 补上，**不删库** |
| **影响范围** | 版本迭代对使用者无感，老数据保留；「重置」接口也不再删物理文件 |

**产出物**：`server/`（`db.js` 建表+种子+迁移 / `engine.js` Agent 引擎 / `server.js` HTTP+REST / `hr_agent.db` / `start.bat`）

> 🎤 **面试这么说**：「我把这套东西做成了零依赖——Node 原生 HTTP 加内置 SQLite，一个 npm 包都没有。原因很实际：演示的时候没人会帮我装环境，`npm install` 失败一次整个演示就废了。我要证明的是链路成立，不是我会搭框架。而且它**是真跑的**——打分真进库、闸门真拦截、越权真返回 403 还留了审计记录。」

## 阶段 7 · 合规与安全：把红线写进代码，不写进提示词

### 我做的动作

1. **把合规做成规则表，不是提示词** —— 歧视性表述 11 条 + 违法表述 9 条，**每条带法条依据和建议改法**。
2. **命中即阻断发布** —— `blockPublish: true`，不是「温馨提醒」。
3. **把合规扫描做成可回归的** —— 规则表意味着可以写测试集、可以跑回归、可以证明「拦截率 100%」。
4. **全链路留痕** —— 审计日志覆盖用户操作、Agent 操作、被拒绝的操作。

### 关键决策：合规检查用代码规则表，不用模型

| | |
|---|---|
| **原方案** | 让模型判断 JD 里有没有歧视性表述 |
| **我否掉的理由** | ① 漏检不可解释——你无法向法务说明为什么这条没扫出来；② 规则更新要重跑模型效果评估，成本高；③ 合规需要的是**可列举、可举证、可回归**，模型给不了 |
| **改后方案** | 结构化规则表（正则 + 法条依据 + 建议改法），命中即阻断；模型只在旁边做补充建议 |
| **影响范围** | 合规能力变成**可交付、可审计、可测试**的产品资产，能直接写进验收标准（如「歧视词拦截率 100%，回归集 ≥ 30 条样本」） |

### 合规覆盖的边界（我明确写出来的）

| 维度 | 覆盖内容 |
|---|---|
| 简历隐私 | 个人信息保护：受保护字段不进打分链路、展示脱敏 |
| 招聘反歧视 | 性别 / 年龄 / 婚育 / 户籍 / 地域 / 院校层级 / 外貌 |
| 操作留痕 | 谁、什么时候、对什么对象、做了什么、结果如何 |
| 权限矩阵 | 多角色 × 资源 × 动作 × 数据范围，含 Agent 的代理权限 |

**产出物**：`docs/01` 第五部分（5.1 简历隐私 / 5.2 反歧视 / 5.3 审计 / 5.4 权限矩阵）+ `docs/02` 3.5 脱敏网关、6.2 安全用例；代码侧 `engine.js` 的 `DISCRIMINATION`(11) / `ILLEGAL`(9) / `scanJd()`

> 🎤 **面试这么说**：「JD 合规检查我坚持用代码规则表做，不用模型。因为合规要的是三件事：可列举、可举证、可回归。模型漏检一条，我没法向法务解释为什么。规则表我写了 11 条歧视性和 9 条违法表述，每条都带法条依据和改法建议，命中直接阻断发布——这是能写进验收标准的，不是『温馨提示』。」

## 阶段 8 · 能力迭代：从三层硬编码走向岗位库驱动

**这一阶段是「产品上线后收到反馈 → 定位根因 → 重构」的真实样本，也是我认为最有说服力的一段经历。**

### 用户反馈

> 「为什么自动给我显示『高级 Java 工程师』？我想改成可以自己填写的。而且生成的岗位 JD 都是高级 Java 开发工程师，没有其他行业的。」

### 我的诊断：这不是默认值，是三层硬编码

| # | 位置 | 写死了什么 | 后果 |
|---|---|---|---|
| 1 | 筛选台页面 | 按标题过滤 `c.job === '高级 Java 工程师'` | 不管选谁，列表只出这个岗的人 |
| 2 | 后端 Agent | `runScreening` 里硬编码 `jobId: 'J-118'` | 点「运行 Agent」永远跑那个岗 |
| 3 | JD 生成函数 | 直接返回 Java 岗 JD + 写死的「命中 3 处」结论 | JD 全是 Java，且**扫描结论是假的** |

附带发现：岗位下拉框没绑事件，所以「换一个岗位」这个动作根本不生效。

### 关键决策：把岗位做成「唯一数据源」，而不是打补丁

| | |
|---|---|
| **原方案（本能反应）** | 把硬编码的岗位名改成另一个，或者多加几个 if |
| **我否掉的理由** | 打补丁只解决这一次；岗位是 HR 业务里变化最快的东西（新部门、新行业、季节性招聘），必须让 HR 自己维护 |
| **改后方案** | **岗位库驱动单一数据链**：<br>`岗位管理（HR 自建）→ 自动抽取打分关键词 → 筛选 Agent 的硬门槛与打分依据 → JD 生成与合规扫描` |
| **影响范围** | 产品从「只能演示一个岗位」变成「HR 可自建任意岗位、跨行业通用」；同时前端多出「岗位管理」页，后端多出岗位 CRUD 接口 |

**四个具体能力（都已落地）**

1. **岗位可自建** —— 岗位名、行业、部门、最低年限、学历、必须项、加分项、JD 全文全部可填，支持新建/编辑/关闭。
2. **跨行业，不再是 Java 一家** —— 先按**职能族**取技能（30 族：技术 / 产品 / 设计 / 数据 / 运营 / 市场 / 销售 / 实施交付 / HR / 财务 / 风控合规 / 供应链 / 生产 / 工程设备 / 工艺 / 质量 / 医疗 / 客服 / 零售门店 / 行政 / 法务合规 / 教育培训 / 建筑工程 / 传媒内容 / 物流运输 / 酒店餐饮 / 物业安保 / 医药健康 / 游戏 / 能源电力），识别不到才回落到 **18 类行业词库**（互联网 / 制造 / 零售连锁 / 医疗健康 / 教育培训 / 金融 / 销售 / 人力资源 / 建筑工程 / 物流运输 / 酒店餐饮 / 医药健康 / 游戏 / 能源电力 / 传媒文化 / 专业服务 / 物业管理 / 通用）；种子岗位扩到 **17 个行业 21 个岗位**（含「AI 产品经理」「软件实施管培生」两个关键回归用例，「风控专员 / 工艺工程师 / 门店店长」三个族拆分用例，以及后补的法务专员 / 数学教师 / 土建工程师 / 短视频编导 / 物流调度主管 / 厨师长 / 物业项目经理 / 医药代表 / 游戏数值策划 / 光伏运维工程师）。
3. **大类继续细分** —— 最容易被忽略的一类 bug：**两个岗位天天打交道，但每天做的事完全不同，却被塞进同一个族**。反馈说「风控专员补上了账务核算」「工艺工程师补上了设备点检」「门店店长补上了内容投放」，我把它们各自拆成独立族（风控合规 / 工艺工程 / 零售门店），并定下硬规矩：**一个识别词只能属于一个职能族，族的分界按「这个人每天做什么」划，不按行业或公司部门划。**
4. **打分与 JD 都跟着岗位走** —— 打分算法改为通用模型（关键词覆盖率 + 业务成果条数 + 年限倍数 + 加分项），不再 Java 专用。

### 连带修复：新建岗位没有简历，筛选就没数据

| | |
|---|---|
| **问题** | 岗位能自建了，但新岗位下面 0 份简历 → 筛选功能看起来「坏了」 |
| **改后方案** | 建岗时自动生成 **5 份演示简历**（四档分布：强推荐 / 可聊 / 不合格 / 被规则拦），并打上「演示简历」标签 |
| **为什么这么做** | 一是让链路立刻可验证；二是**标签必须打**——不能让演示数据混进真实候选人，这是产品诚信的底线 |

### 关键决策：任职要求扩充，但绝不改写 HR 的原句

| | |
|---|---|
| **反馈** | 「任职要求太单一了，帮我在原有基础上扩充」 |
| **原方案** | 按行业模板重新生成一整套任职要求 |
| **我否掉的理由** | 如果把 HR 写的那条冲掉了，他会认不出自己的岗位——**AI 的价值是补齐和专业化，不是替换** |
| **改后方案** | 六维度结构（专业技能 / 工作经验 / 学历背景 / 综合素质 / 软技能 + 独立的加分项）；**HR 填的原句一字不改地保留**，缺的维度自动补位 |
| **实测效果** | 只填 1 条要求 → 输出 **5 个维度 13 条**（硬性条件 7 + 综合素质/软技能 6）+ 加分项 3 条 |

### 一条容易犯错的边界：哪些内容不进打分通道

| | |
|---|---|
| **我的决定** | **综合素质 / 软技能只进 JD 正文，不进打分关键词** |
| **理由** | 它们包含「沟通协作」这类通用词。一旦进关键词，会稀释岗位关键词、让**所有候选人的得分趋同**，排序失去区分度 |
| **影响** | 硬性通道只收「专业技能 + 工作经验 + 学历背景」三类，保证打分的区分度 |

**产出物**：`server/engine.js`（`INDUSTRY_SKILLS` / `extractKeywords` / `synthCandidates` / `createJob` / `updateJob` / `deleteJob` / `expandRequirements`）、`server/db.js`（岗位 10 条种子 + 列迁移）、`平台原型/src/app.js`（岗位管理页 + JD 工作台重写）、`docs/03` 第五节「岗位库、JD 与打分关键词（三者是一条链）」

> 🎤 **面试这么说**：「这条反馈最有价值的地方不是需求本身，而是让我定位到三层硬编码——页面按标题过滤、Agent 写死 jobId、JD 函数返回固定内容。我的第一反应不是打补丁，而是把它重构成『岗位库驱动单一数据链』：HR 自己建岗 → 自动抽关键词 → 驱动打分和 JD 生成。因为岗位是 HR 业务里变化最快的东西，必须让他们自己维护。顺带我还定了一条边界——软技能只进 JD 正文、不进打分关键词，否则关键词被稀释，所有候选人得分会趋同。」

## 收口 · 验证与自省：我凭什么说它是对的

### 我做的验证

1. **双模式无头回归** —— 在线（真后端）与离线（双击 HTML）两套，各自覆盖 **24 个页面渲染** + 关键真链路（离线 23 项 / 在线 27 项），全部 0 异常、0 运行时错误。
2. **回归用例覆盖真实链路**，不是点开页面就算过：
   - 跨行业岗位切换后，筛选是否跟随该岗位
   - 自建岗位 → 自动生成简历 → 跑到人工闸门
   - JD 写「限男性，35 岁以下」→ 是否命中并阻断发布
   - 驳回不填原因 → 是否被服务端 400 拦下
   - 以员工身份导出全公司数据 → 是否 403 并留痕
   - 人工推翻 Agent 判断 → 是否生效并记录
3. **合规自检** —— 18 个行业生成文本误报 0；负向用例「限男性，35 岁以下」仍稳定命中（扩充后未漏报）。
4. **幂等性验证** —— 对已扩充结果再扩一次，条数不变。

### 我主动写下的已知边界（不等人问）

| 边界 | 现状 | 生产级要求 |
|---|---|---|
| 身份 | 请求头模拟 | 登录态 + 会话 + 租户隔离中间件 |
| 并发 | 单进程 SQLite | 连接池、写锁、迁移脚本 |
| 文件存储 | 简历只存结构化字段 | 对象存储 + 加密 + 访问水印 |
| 第三方集成 | 飞书/钉钉/Mail 为模拟 | 真实 SDK、限流、幂等键、失败重试 |
| 知识库 | 关键词检索 | 向量库 + 切片策略 + 引用定位 |
| **评测** | ~~无离线评测集~~ **已补**：30 例人工标注黄金集 + 一致率 / 漏筛率 / 误筛率口径（v16 后 96.7% / 0% / 8.3%） | 扩到 90 例、覆盖 9 个职能族（当前 30 例的区间下沿只有 83.3%） |
| 多租户 | 单租户常量 | 所有查询带 tenant_id 且不可由前端传入 |

> **这张表是我主动写的，不是被评审逼出来的。** 我认为一个产品经理的能力，很大一部分体现在**知道自己的产品现在停在哪一步、下一步要补什么**。

### 目前还缺的（我不打算掩饰）

- **评测集只有 30 例、3 个岗位**：已有一致率跑分（96.7% / 漏筛 0% / 误筛 8.3%），但 Wilson 95% 区间是 [83.3%, 99.4%]，下沿撑不住结论式表述 —— 下一步扩到 90 例。
- **没有真实客户数据**：候选人简历是按岗位画像合成的，业务价值数字（70%/60%/4h→5min）尚未实测。
- **没有真实用户验证**：还没跑过 pilot，采纳率、人工接管率都是空的。

**补齐方式**：Golden Set 已建（30 例，指标 / 阈值 / 基线三样齐）→ 扩到 90 例并把阈值写进 CI 阻断 → 接真实数据做 pilot → 用实测值替换设计值。

> 🎤 **面试这么说**：「我给自己写了一张已知边界表，七条，其中『无离线评测集』那条我已经补上了——30 例人工标注黄金集，一致率 96.7%。我主动写出来而不是等评审问，因为产品经理的能力很大一部分体现在——**你知道自己的产品现在停在哪一步**。这三条缺口的补齐路径我也写清楚了：先建 Golden Set，再接真实数据跑 pilot，用实测值替换设计值。」

## 附录 B · 三个长度的口播稿

### 30 秒版（自我介绍里带过）

> 「我做过一个 B 端 HR AI Agent 平台，从 0 到 1。核心判断是——HR 80% 的时间在查资料、搬数据、催流程，只有 20% 在做判断，我做的就是把那 80% 交给 AI，把判断和签字权留给人。交付上我没有停在 PPT：有完整 PRD、8 阶段落地教程、24 页原型，还有一套真跑 SQLite 的本地全栈 MVP。我最坚持的一条原则是——能用规则的绝不用模型，该人签字的绝不交给 AI。」

### 3 分钟版（项目陈述）

> 「这个项目的起点不是『我要做个 AI 产品』，而是一张 HR 真实一天的表。翻 80 份简历 3～4 小时、被员工问社保打断 20 次、每月手工拼周报 4 小时。归纳下来一句话：**HR 80% 的时间在做不需要判断的事**。
>
> 所以我第一版就写清了非目标：不做完整 HRIS、不做自动发 Offer、不做简历爬虫。B 端产品的死法通常不是做得不对，是做得太多。
>
> 真正关键的判断发生在第二步——**哪里该用 AI，哪里坚决不用**。我把系统拆成四个边界：Agent 决策、Workflow 执行、Rules 约束、Human 治理。入转调离 80% 用 Workflow；报表里模型只做翻译、不参与算数；年限学历这类硬门槛用代码判、**0 token**。这个判断省下的不只是成本，更是可信度。
>
> 设计上我做了一件我个人最满意的事：**反歧视没有写在提示词里，而是把性别、年龄这些字段从打分查询里物理剔除了**。区别在于，写提示词是『我请求模型别看』，物理剔除是『模型根本拿不到』。合规审查要的是后者。
>
> 落地层面，我没有停在原型。原型是 24 页、单文件、零依赖、双击即开，还做了双模式——离线可演示、连上后端就真跑。之后我把它做成了真后端：Node 原生加内置 SQLite，一个 npm 包都没有，打分真进库、闸门真拦截、越权真返回 403 还留了审计。两套模式的回归测试各覆盖 24 页 + 23/27 项真链路，全绿。
>
> 最后一轮迭代来自真实反馈：有用户说『为什么总是显示高级 Java 工程师』。我定位到三层硬编码——页面按标题过滤、Agent 写死 jobId、JD 函数返回固定内容。我没有打补丁，而是把它重构成『岗位库驱动』：HR 自己建岗、系统自动抽关键词、驱动打分和 JD 生成。现在支持 17 个行业 21 个岗位（含 AI 产品经理），任何行业都能自建。
>
> 紧接着又来一条更细的反馈：『我写的岗位是 AI 产品经理，为什么还是有 Java？』——这次暴露出抽词只看「行业」的先天缺陷：互联网行业的任何岗位都被加成技术栈。我把分类轴从「行业」升级成「职能族优先、行业兜底」（30 族），并把词库收敛成前后端共用的一份，再给老 JD 加了版本号自愈。这类反馈我特别看重：**它逼我把一个拍脑袋的简化模型，换成了对的分层。**
>
> 第三条反馈又补上一刀：『软件实施管培生』生成出来的却是客服岗的职责与技能。一查，是『实施』『交付』这两个词被放进了客服族的识别词里 —— 族与族的分界没按「这个人每天做什么」来划。我拆出独立的「实施交付」族，同时顺手把「管培生 / 实习 / 应届」识别成岗位层级：**同一职能下，层级决定「工作经验」怎么写**——社招写「N 年以上」，管培生写「无需经验 + 1–2 段对口实习」，并且筛选门槛同步放开，不出现「JD 欢迎应届生、门槛却全拦掉」的自相矛盾。
>
> 第四条反馈又补一刀：『风控专员被补上了账务核算、工艺工程师被补上了设备点检、门店店长被补上了内容投放。』这三条看起来各不相同，其实是同一个错误 —— **两个岗位天天打交道，但每天做的事完全不同，却被塞进了同一个族**。我把它们各自拆成独立族（风控合规 / 工艺工程 / 零售门店），并固化了一条硬规矩：**一个识别词只能属于一个职能族，族的分界按「这个人每天做什么」划，不按行业或公司部门划。** 四条反馈，一次比一次细，产品就是这样被一刀一刀修准的。
>
> 第五条其实是「同一类问题再往前推一步」：有反馈说『可选的职业太少了，JD 也还是有点片面』。我没去多写几个 if，而是做了一次**素材扩容 + 生成逻辑升级**：职能族 20 → **30**（补上法务、教育、建筑、传媒、物流、餐饮、物业、医药、游戏、能源十个行业侧岗位群），每族职责池 4 → **8 条（产品族 10 条）**、全平台 **242 句**；再把每句职责打上**子方向标签**，新增 `pickDuties()` 按岗位名「择优挑 6 条」—— 于是「AI 产品经理」和「B 端产品经理」的职责**不再一字不差**，而且全程零模型、可复现。顺带修了一个真会伤到生产的隐藏 bug：点「重置」会卡 6~7 秒，根因是 Node 内置 SQLite **每条语句自动提交**、Windows 每次提交都 fsync，120 条种子写库把事件循环堵死、把 keep-alive 连接拖断（`ECONNRESET`）；我把它改成**单事务批量提交**，重置降到 100 毫秒级。**这条 bug 我是在跑回归时撞出来的，不是用户报的 —— 但它恰恰证明「先跑真链路、再交货」这个顺序的价值。**
>
> 我知道它现在停在哪：**没有离线评测集、没有真实客户数据、没跑过 pilot**。这三条我写在了边界表里。下一步是建 Golden Set，接真实数据验证。」

### 如果被问「这个项目最大的价值是什么？」

> 「不是功能数量，是**一套可复用的产品判断顺序**：先看 As-Is 再定目标，先写非目标再写功能，先划 AI 边界再设计页面，先定对象再画界面。这套顺序我在这个项目里跑通了一遍，换个业务也能用。」
