# 03 · 本地全栈版运行说明（真后端 · 真数据库 · 真 Agent）

> 这一份是给「要动手把它跑起来」的人看的。前面的 PRD（01）讲**要做什么**，搭建教程（02）讲**怎么做成产品**，这一份讲**眼前这套已经在本地跑通的代码怎么启动、怎么验证、怎么改**。
> 现状：**零 npm 依赖**。后端只用 Node 22 内置模块（`http` + `node:sqlite`），前端是把 CSS/JS 内联后的单文件 HTML。

## 三、前端是怎么自动切换真后端的（以及登录闸门）

`平台原型/src/app.js` 里有一个 `LIVE` 开关，**页面加载时会主动探测后端**：

```js
const h = await fetch('/api/health');        // ① 探测后端是否在
if (h.authMode === 'strict') showAuthGate(); // ② 严格模式：先出登录层
await liveBootstrap();                       // ③ 有会话才拉 GET /api/bootstrap
```

- **请求成功且有会话** → `LIVE.on = true`，右上角亮起「🟢 真实后端 · SQLite · 已认证」，此后所有动作走真 API，数据来自 `hr_agent.db`。
- **请求成功但无会话**（`strict` 模式）→ 弹**登录闸门**（列出演示账号），登录后再进入真实态。**不会白屏，也不会静默降级成假数据。**
- **请求失败**（`file://` 直接双击）→ 保持离线模式，用内置演示数据，功能照常可点；**此时不发任何网络请求**，所以断网也能演示。

**结论**：同一份 `index.html`，直接双击 = 演示态；被 `server.js` 托管 = 真实态（需登录）。不需要两版前端。

### 3.1 身份不再由客户端指定（v0.10.0 的核心修复）

改造前：`server.js` 里 `DEMO_USER = req.headers['x-user'] || 'U-001'` —— **改一个请求头就能变成 HRD**，审计链、审批闸门、越权拦截全部建立在可伪造的身份上。

改造后：

| 项 | 做法 |
|---|---|
| 登录 | `POST /api/auth/login` 校验 `scrypt` 哈希（Node 内置，零依赖），失败文案统一（防用户枚举），连续失败 5 次锁定 |
| 会话 | 服务端 `sessions` 表 + 不透明令牌；校验 **HMAC 签名 + 指纹 + 过期时间 + 是否已吊销**（所以能「立即踢下线」，这是 JWT 做不到的） |
| 令牌下发 | `Authorization: Bearer <token>` **与** 服务端 Cookie 双通道 |
| 吊销 | 登出 / 改密 → 吊销该用户**全部**会话；管理员可主动吊销某用户全部会话 |
| `X-User` | **后端完全不读这个请求头**（任何模式下）。`legacy` 认证分支本轮**已彻底删除** —— 留一个能伪造身份的开关，本身就是攻击面 |

### 3.2 三层权限

| 层 | 判据 | 落点 |
|---|---|---|
| **功能级** | 24 个能力 × 7 个角色，**白名单**，新角色默认无能力 | 路由表上的 `need`；由 `http-kernel.js` 在进 handler 之前拦截 |
| **行级** | `all` / `dept`（部门**路径前缀**匹配）/ `self` | `routes.js` 的 `scopeSnapshot()` 与 `denyScope()` |
| **字段级** | 无 `pii:read` 能力即脱敏；读未脱敏明细**要写审计** | `rbac.maskRow()` / `needsPiiAudit()` |

> **为什么必须服务端裁剪**：代码注释里写得很直白 —— 「前端隐藏」只是视觉效果，**数据已经到浏览器了，抓包即得**。
> 前端那层「按能力过滤导航」只是**界面减负**（员工不该看到一堆点进去全是 403 的菜单），**不承担安全职责**。

## 四、接口清单

> 全部接口共 **45 条**。下表列常用项；**每条路由的权限要求见 `server/routes.js` 的路由表**（一眼可审：没标 `public` 的就一定标了 `need`）。
> 统一响应：`{ ok:true, ... }` / `{ ok:false, error:{ code, message, details }, requestId }`。

### 4.1 认证与权限

| 方法 | 路径 | 权限 | 关键行为 |
|---|---|---|---|
| POST | `/api/auth/login` | public | `scrypt` 校验 → 建会话 → 下发令牌（Bearer + Cookie）；失败 5 次锁定 |
| POST | `/api/auth/logout` | 任意登录 | 吊销当前会话 |
| GET | `/api/auth/me` | 任意登录 | 当前用户、角色、**能力列表**、数据范围 |
| POST | `/api/auth/change-password` | 任意登录 | 改密后**吊销该用户全部会话** |
| GET | `/api/permissions` | 任意登录 | 能力表与角色映射（供前端裁剪导航） |
| GET | `/api/bootstrap` | 任意登录 | **按角色裁剪后**的快照（员工只拿到自助所需的最小集） |
| GET | `/api/metrics` | `metrics:read` | 请求数 / 错误率 / 延迟分位 / 业务计数器 |

### 4.2 业务

| 方法 | 路径 | 权限 | 关键行为 |
|---|---|---|---|
| GET | `/api/health` | public | 返回 `mode`（rule/llm）、`authMode`、`schemaVersion`、运行时长 |
| POST | `/api/agent/screening/run` | `screen:run` | 8 步计划真实执行 → 打分写库 → 最后一步被闸门拦下 → 生成审批单 |
| POST | `/api/approvals/:id/approve` | `approval:decide` | 真实变更候选人阶段，返回 `changed` 条数，写审计 |

| POST | `/api/chat` | 任意登录 | 拒答规则 → 查本人数据 → 知识库检索 → 兜底记录 |
| POST | `/api/candidates/:id/override` | `screen:run` | 人工推翻 AI，原因必填，写入 `human_decision` + 审计 |

|---|---|---|---|
| GET | `/api/audit` | `audit:read` | 审计尾部 + 统计；**声明 `appendOnly: true`（由数据库触发器保证）** |

## 五、岗位库、JD 与打分关键词（三者是一条链）

**这是 v0.9.1 最重要的改动：平台里不再写死任何岗位。**

以前演示时一进「简历筛选台」就固定是「高级 Java 工程师」，原因是三处硬编码：页面按标题过滤候选人、运行 Agent 时 `jobId` 写死、下拉框没绑事件。现在全部去掉，改成「岗位库驱动」。

```
岗位管理（HR 自己填）
   │ 岗位名称 / 行业 / 部门 / 最低年限 / 学历 / 必须项 / 加分项
   ▼
先识别「职能族」，再抽打分关键词（detectFunction → extractKeywords）
   │ ① 拿岗位名称（权重×3）+ 必须项/加分项正文（权重×1）去命中职能关键词
   │ ② 命中即用该职能族的技能库；命中不到才回落到「行业词库」
   ▼
筛选 Agent 的硬性门槛 + 打分依据
   │ 规则前置用 must_years / must_edu_rank；打分用关键词命中率
   ▼
简历筛选台（按所选岗位运行，KPI 与列表都跟着岗位变）
```

**为什么先认职能，而不是只认行业？** 这是被一个真实 bug 逼出来的：以前只按「行业」取词库，于是凡是「互联网」行业的岗位——哪怕是**产品经理、设计师、运营**——都会被塞进 Java / Spring / 微服务这套技术栈。根因是「行业」和「职能」是两回事，混在一张表里必然串味。

现在改成**职能族（Function Family）优先、行业兜底**两层：

- **职能族词库**（`shared/req-lib.js` 的 `FUNCTIONS`，30 族）：技术研发、产品、设计、数据与算法、运营、市场品牌、销售与商务、实施交付、人力资源、财务会计、风控合规、供应链采购、生产制造、工程设备、工艺工程、质量、医疗护理、客户服务、零售门店、行政综合、法务合规、教育培训、建筑工程、传媒内容、物流运输、酒店餐饮、物业安保、医药健康、游戏、能源电力。每族带 `core`（核心技能）/ `biz`（业务语境）/ `plus`（加分项）/ `majors`（对口专业）/ `expHint`（经历特征）/ `general`（综合素质）/ `soft`（软技能）/ `nice`（加分项模板）/ `duties`（职责模板，8 条起，产品族 10 条）。
- **行业词库**（`server/db.js` 的 `INDUSTRY_SKILLS`，18 类）：互联网、制造业、零售连锁、医疗健康、教育培训、金融、销售、人力资源、建筑工程、物流运输、酒店餐饮、医药健康、游戏、能源电力、传媒文化、专业服务、物业管理、通用。**只在职能识别不出来时才兜底**。
- 识别函数 `detectFunction()` 命中不到族时返回 `null`，此时才回落到行业库 —— 所以「设备维保工程师」不会被当成软件工程师（`tech` 族的关键词里刻意不含「工程师 / 技术」这类泛词），「AI 产品经理」也不会拿到 Java。
- **强弱关键词**：`kw` 收强词（命中即计 3 分）；某些族的 `weak` 收弱词（命中只计 1 分）。例：`tech.weak = ['运维']`，于是「**光伏**运维工程师」被强词「光伏」拉去**能源电力**族，而纯「运维工程师」没有强词、只剩这 1 分弱命中，仍归**技术**族。
- 族与族的分界是**按「这个人每天做什么」划的，不是按行业划的**。例如「实施交付」与「销售」分开：前者是签约后把系统真正跑起来，后者是签约前的商机与谈判；「实施交付」与「客服」也分开：前者处理系统与业务落地，后者处理话务与客诉口径。这两个分界各对应一个真实 bug（「软件实施管培生」一度被误判为客服岗）。

> 词库只有一份：`shared/req-lib.js`。后端 `server/engine.js` 和离线原型 `src/agent.js` 都 `require` 它，避免两边各写一套、改一处漏一处。离线端由 `build.js` 把它内联进单文件 HTML（实测与旧 Python 脚本逐字节等价，只差构建时间戳）。

### 岗位层级：管培生 / 实习 / 应届不设工作年限门槛

同一个职能族下，**岗位层级**（社招 vs 管培 / 实习）决定「工作经验」这一维怎么写。

- `ReqLib.detectJunior()` 扫描岗位名与已填要求，命中 `管培生 / 培训生 / 实习生 / 应届 / 校招 / 储备干部 / 见习 / 学徒 / 经验不限` 即判定为初级岗。
- 命中后：
  - **工作经验维度** → 「无需相关工作经验，欢迎应届毕业生投递」+「有 1–2 段与岗位方向对口的实习经历者优先」（不再套用 `expHint` 那句「有独立负责过 X 项目的经历」）；
  - **筛选 Agent 的年限门槛同步放开**（`gateYears = null`）—— 否则会出现「JD 写着欢迎应届生、规则门槛却把应届生全拦掉」的自相矛盾。
- 未命中则维持原口径：`N 年以上 + 该职能的经历特征`。

> 例：「软件实施管培生」（互联网）→ 识别为**实施交付**族 + junior。生成的岗位职责是「系统实施与交付、部署配置、上线培训、问题闭环」，工作经验是「无需经验 / 对口实习」——**不会**出现客服话术，也不会出现「3 年以上」。

**新建岗位后能不能立刻跑筛选？能。** `/api/jobs` 创建岗位时会调 `synthCandidates()` 按该岗位画像自动生成 5 份演示简历，四档分布（强推荐 / 可聊 / 打分后不合格 / 硬性条件不符被规则拦截），所以新建完切到筛选台点运行就有结果。演示简历带 `synthesized=1` 标记，页面上会显示「演示简历」小标签 —— 不会和真实简历混淆。

**JD 扫描是代码，不是提示词。** `engine.js` 里两张规则表：`DISCRIMINATION`（11 条，性别/婚育/年龄/户籍/院校/身体状况/外貌/地域）和 `ILLEGAL`（9 条，社保/合同/押金/工时/离职扣薪/工伤免责/试用期工资/限制生育），每条都带法条依据与建议改法。命中即返回 `blockPublish: true`，前端按钮变成「⛔ 已阻止发布」。

> 离线模式（直接双击 `index.html`）也在 `src/agent.js` 里维护了同源的规则，同样做真实扫描 —— 不是写死几条结论给你看。

### 任职要求：从「一条」扩充到「六维度」

**以前的问题**：HR 在必须项里写一条「3 年以上采购经验」，生成的 JD 任职要求就只有这一条 —— 单薄、不专业、不像真实招聘启事。

**现在的做法**（`engine.js` 的 `expandRequirements()`，离线端 `src/agent.js` 同源）：

```
HR 已填的必须项 / 加分项
   │ ① 原样保留，只按语义归位（含「学历」→学历背景；含「经验」→工作经验；其余→专业技能）
   ▼
按「职能族」素材补齐缺失维度（识别不到职能才按行业兜底）
   │ ② 专业技能：该职能族的核心技能里没被提到的自动补位
   │ ③ 工作经验：年限 + 该职能的经历特征（管培 / 实习岗改为「无经验 + 对口实习」口径）
   │ ④ 学历背景：按岗位学历门槛 + 职能对口专业方向
   │ ⑤ 综合素质 / ⑥ 软技能：职能化表述（医疗看查对制度、金融看合规红线……）
   ▼
JD「二、任职要求」= 维度小标题 + **自然行文段落**（v0.9.8 起不再逐条编号）
```

真正让 HR 头疼的不是补不齐，而是**粘进去的东西被拆碎**。所以生成前先做一次原文还原：

```
任职要求框里粘一整份 JD
   ▼
① 剥符号     行首的 · • - 1. （1） ① 一律去掉（否则渲染时会叠成「6. ·从0到1…」）
   ▼
② 合并断行   上一行以句中标点结尾 → 这句话没说完，并回来并补齐逗号
   ▼
③ 小标题归位 「你会做什么」→ 职责；「我们想找这样的你」→ 任职要求；「有这些更香」→ 加分项
   ▼
④ 成段输出   同维度的若干要求用「；」串成一整段话，不再一条一个编号
```

**条目边界只由「换行」和「行首列表符号」决定**。逗号、分号、顿号是句中标点，不是分隔符 ——
旧版按 `[,，;；\n]` 切条，一句「和顶尖算法、工程团队并肩，把想法快速上线」会被劈成两条，
一份 300 字的 JD 能变成 20 个碎片。同一个判据也保证了表单往返无损：从「用逗号拼接」改成
**「一行一条」**，编辑岗位时不会把你写好的要求黏成一条。

三个刻意的设计：

- **绝不改写 HR 的原句**。HR 写的那条一定出现在 JD 里，AI 只做补齐和专业化 —— 否则 HR 会认不出自己写的岗位。
- **综合素质 / 软技能不进 `must_have`**，只进 JD 正文。因为它们含「沟通协作」这类通用词，若进入打分关键词会稀释岗位关键词、让所有候选人得分趋同。硬性条件通道（`must`）只收专业技能 + 工作经验 + 学历背景。
- **软素质不会塞进「专业技能」**。「对 AI 是真热爱 / 有同理心」这类句子单列一桶归到「软技能」，否则整段读起来不着调。

一句话验证（本机已跑通）：输入 **1 条**要求 → 输出 **5 个维度 13 条**任职要求（硬性条件 7 条 + 综合素质/软技能 6 条）+ 加分项 3 条，原句完整保留。

> 幂等：对已扩充过的结果再扩一次，条数不变（不会无限膨胀）。

### 老 JD 的自我修复（jd_ver）

改了词库或职能族，**已经存库的老 JD 不用手动改**。`jobs` 表有 `jd_ver` 列，`engine.js` 里有个常量 `REQ_LIB_VER`。服务启动 `bootstrap()` 时逐个岗位比对：

```
岗位.jd_ver < REQ_LIB_VER
   │ 说明这条 JD 是用旧词库生成的（比如还含 Java）
   ▼
用当前 expandRequirements + buildJD 重算
   ▼
回写 must_have / nice_have / keywords / jd_text / jd_ver
```

所以升级后第一次启动，历史上那些「非技术岗被塞了技术栈」的脏数据会被自动洗一遍。同时 `stripMisfitAutoFill()` 会把**误填进非技术岗 `must_have` 的自动补位技能**清掉（靠自动补位句式的正则识别，不会误伤 HR 手写的原句）——双保险。

> 判定「同一句要求」用 `similarReq()`（bigram 相似度 ≥ 0.28，可调），避免「需求分析」和「需求分析与技术方案设计」被当成两条重复塞进去。HR 原文已覆盖的维度用 `coveredByUser()` 跳过，不重复补。

### JD 职责：同族不同岗不再一字不差（pickDuties）

**以前的问题**：每族只有 4 条职责，`buildJD()` 把本族 `duties` **全部输出**，于是「AI 产品经理」和「数据产品经理」生成的职责**一字不差** —— JD 看着就不是这个岗。

**现在的做法**（v0.9.6）：

- 每句职责从纯字符串升级成 `{ t: '句子', k: ['子方向标签'] }`，例如产品族里「设计 AI 能力的产品化方案」带标签 `['AI','模型','大模型']`、「参与商业化方案设计」带 `['商业化','定价','B端']`。
- 新增 `ReqLib.pickDuties(fn, title, texts, max)`：拿**岗位名（权重×3）+ 必须项/加分项正文（权重×1）**去命中每句的子方向标签，**命中数降序**取前 `max` 条（`engine.js` 里 `DUTY_MAX = 6`），命中不足则用本族其余的句子补齐。
- 于是招「AI 产品经理」优先取 AI / 数据向的句子，招「B 端产品经理」取商业化向的句子，**两份 JD 立刻不同**；同一族下 8 条池子有几十种组合，且**全程无模型、结果可复现**。
- 前后端同源：后端 `engine.js` 的 `dutiesFor()`、离线端 `src/agent.js` 的 `expandReqs()` 都调同一个 `pickDuties()`。

> 例：「光伏运维工程师」生成 JD 时，职责首条是「**负责光伏／风电／储能项目的运行监视与发电量分析**」，而不是技术族的「保障线上服务稳定性」—— 既证明职能族选对了，也证明子方向挑句生效了。

## 七、接大模型（可选）

默认是**规则模式**：打分、问答全部由确定性代码实现，离线可跑、结果可复现——这也是产品里「能用规则就别用模型」那条原则的落地。

要接模型，启动时给三个环境变量（任意 OpenAI 兼容接口）：

```bash
# Windows PowerShell
$env:LLM_API_URL="https://your-endpoint/v1/chat/completions"
$env:LLM_API_KEY="sk-xxx"
$env:LLM_MODEL="your-model"
node --experimental-sqlite server.js
```

引擎会走 `engine.js` 里的 `llm()` 网关：

- **调用成功** → 回答由模型组织，但**事实来源仍是数据库/知识库**，模型只负责遣词。
- **调用失败** → 自动回退规则输出，**页面不会报错**。这条 fallback 是刻意的：模型挂了产品还得能用。

> 注意：即便接了模型，**反歧视脱敏、权限校验、金额/年限这类硬判断仍在代码里**，模型拿不到受保护字段，也不参与硬规则判定。

## 八、已知边界（别把它当生产系统）

> **v0.10.0（M1）已补上的**：身份认证（口令 + 服务端可吊销会话）、三层权限（功能/行/字段）、审计数据库层 append-only、PIPL 数据治理（留存/授权/删除权/导出）、版本化迁移、统一错误契约 + requestId + 结构化日志 + 限流 + 指标 + 优雅关闭。
> **仍未做到的**（诚实清单，完整版见 `docs/09` §七）：

| 边界 | 现状 | 说明 |
|---|---|---|
| 数据库形态 | 单文件 SQLite，单写入者 | 生产要 PostgreSQL/MySQL + 连接池 + 备份 + 只读副本（**M1 特意顺延，理由见 `docs/09` D1**） |
| 并发 | 单进程 + WAL | 多实例需外部化会话/限流（Redis） |
| 多租户 | 单租户常量 `T-001` | 注意它是**服务端常量、永不从请求读取**（这是安全的默认值），但不是真隔离 |
| 字段加密 | **只做脱敏 + 访问留痕，未加密存储** | 生产要 KMS/密钥文件 + 加解密中间层 |
| 文件存储 | 简历只存结构化字段 | 生产要对象存储 + 加密 + 访问水印 |
| 集成 | 飞书/钉钉/Mail 是模拟 | 生产要真实 SDK、限流、幂等键、失败重试 |
| 知识库 | 关键词检索 | 生产要向量库 + 切片策略 + 引用定位 |
| 评测 | **无离线评测集**（最硬短板） | 生产要 Golden Set + 回归门槛（见 02 教程第 6 阶段） |
| 模型 | 未接任何真实模型 | 设计已就位（可插拔网关 + 失败降级），属「接线」工作 |
| legacy 认证模式 | **已删除** | 原用于对比演示「身份可伪造有多危险」；本轮彻底移除 —— 一个能让身份退化成可伪造的开关，即使默认关闭也是攻击面与质疑点 |
| CI | 无 | 三套测试目前手动跑；接 CI 后即可设「低于阈值阻断合并」 |

## 九、排障速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 打开页面只有登录框 | v0.10.0 起 `strict` 模式必须登录 | 选演示账号登录（口令见登录页提示栏）。想跳过：直接双击 `平台原型/index.html` 走离线态 |
| 接口全是 `401` | 没登录 / 令牌过期或被吊销 | 重新登录；若刚改过密码，**旧会话会被全部吊销**（这是设计如此） |
| 接口返回 `403` 且提示「缺少能力 xxx」 | 当前角色的能力白名单里没有该能力 | 换用有权限的账号（如 HRD `U-001` 或管理员 `U-000`）。**403 会写审计，属正常留痕** |
| 更新了后端代码但行为没变 | 旧 node 进程仍在跑 | 停掉旧进程重启（Windows：`netstat -ano \| findstr 8788` 找 PID，或 `taskkill /F /PID <pid>`） |
| `EADDRINUSE 8788` | 旧进程还占着端口 | 同上 |
| `EBUSY: hr_agent.db` | 上一个进程没释放文件锁 | 同上；重置接口已改成不删库文件，正常不会出现 |
| 空库首次启动报 `table users has N columns but M values were supplied` | 老版本种子用了位置化 INSERT，迁移加列后列数不匹配（**只有全新库才会暴露**） | 已修（改为显式列名）。若在旧分支上遇到：检查 `db.js` 的种子 INSERT 是否带列名 |
| 上传超大请求体时客户端报「网络错误」而非 413 | 老版本 `readBody` 超限即 `req.destroy()`，连接被重置 | 已修（读干剩余字节再返回 413）。排障时用 `fetch` 看响应体而不是只看「连接失败」 |
| 候选人库页面报 `Cannot read properties of null (reading 'split')` | 库里有被**匿名化**过的候选人，其 `edu_text` 已被置为 NULL | 已修（前端空值防御 + 后端显式返回「已匿名化」）。这是治理功能与展示功能之间的隐式契约 |
| 点「♻ 重置」后页面卡一下 / 报 `ECONNRESET` | 旧版逐条写库：Node 的 `node:sqlite` **每条语句自动提交**，Windows 上每次 commit 都 fsync，120 条种子写库阻塞事件循环约 **6.8 秒**，期间 keep-alive 连接被拖到空闲超时断开 | 已修：`db.js` 引入 `inTx()`，`seed()` / `reseedRuntime()` / 首次建库全部**包在一个事务里**批量提交；启动时老 JD 自愈的 UPDATE 也并入一个事务。重置 **~6.8s → 70–160ms** |
| 页面显示离线模式 | 后端没起，或改了 `src` 没重新打包 | 先查 `/api/health`，再看是否需要 `npm run build`（改了 `平台原型/src/` 必须重新打包） |
| `seedRuntime is not defined` | 改 `db.js` 时函数名对不上 | 检查 `seed()` / `reseedRuntime()` 是否完整 |
| 测试报「未进入 LIVE 模式」 | 后端没起，或测试脚手架注入的令牌把前端自己的令牌顶掉了 | 确认 server 在跑；检查注入 `window.fetch` 的地方**是否只在未显式设置 `Authorization` 时才注入**（详见 `docs/09` §六 R3） |
| 打分全是 0 或「不合适」 | 规则门槛把人全拦了 | 这是预期行为：先跑规则再跑模型，看第 5 步输出即可 |
| 打分关键词是空的 | 岗位的「必须项/加分项」里没有词库里认识的词 | 到「岗位管理」编辑该岗位，把技能词直接写进必须项（如「熟悉 TPM」「供应商开发」） |
| 新岗位筛选时提示「该岗位暂无简历」 | 该岗位名下还没有候选人 | 点「🧪 生成 5 份演示简历」或从 ATS 同步真实简历；用 API 建岗时会自动生成 |
| 老库启动报错/字段缺失 | 之前的 `hr_agent.db` 是旧结构 | 启动时 `migrations.run()` 会自动补到最新版；实在异常就删掉 `hr_agent.db`（`-wal`/`-shm` 一起）重启，空库会自动重建 |
| 问答答不上来 | 知识库确实没这条 | 去「知识库管理」看未解答问题清单——这是产品的自我修复入口 |
| 任职要求看起来还是「很通用」 | 学历选了「不限学历」，该维度只能输出「学历不限，以实际能力与项目经验为主要评估依据」 | 到「岗位管理」编辑岗位，把学历改成「本科及以上」；行业选对，「综合素质/软技能」会跟着换成该行业的表述 |
| 改了岗位但 JD 没变 | JD 是保存时按最新任职要求重新生成的 | 编辑并保存后会重新生成（含六维度重排）；只有当你在 JD 正文框里**手填了内容**才不会被覆盖 |
| JD 出现与本岗位不相干的内容（如实施岗写出客服话术） | 职能族识别错了 —— 岗位名里的关键词被别的族抢先命中 | 到 `shared/req-lib.js` 检查该词的归属：一个识别词只应属于一个族（如「实施 / 交付」属 `delivery`，不属 `service`）；改完记得把 `engine.js` 的 `REQ_LIB_VER` 加一，老 JD 会自动重算 |
