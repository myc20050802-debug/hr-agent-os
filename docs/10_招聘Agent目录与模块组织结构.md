# 招聘 Agent 目录与模块组织结构

> 版本 v1 · 2026-09-29 · 适用范围：`平台原型/src/app.js` 导航层
> 一句话：把散落的 5 个招聘 Agent 收进一个**招聘 Agent 目录**，内部按**招聘流程阶段**分成 4 个模块。

---

## 一、为什么要动这个结构

改动前，5 个招聘 Agent 和「入转调离 / 员工自助 / 人力报表 / Agent 编排」平铺在同一个「智能体中心」分组里：

```
智能体中心
  📝 招聘 Agent · JD 工作台
  🎯 招聘 Agent · 简历筛选台
  📨 招聘 Agent · 邀约与调度
  🎤 招聘 Agent · 面试辅助
  📄 招聘 Agent · Offer 前置
  🔄 入转调离 Agent
  💬 员工自助 Agent
  📊 人力报表 Agent
  🧩 Agent 编排
```

三个具体问题：

| 问题 | 表现 | 后果 |
|---|---|---|
| **前缀重复** | 「招聘 Agent ·」在一列里出现 5 次 | 侧边栏信噪比低，扫读时眼睛要跳过同样的 8 个字才能看到区别 |
| **层级缺失** | 招聘是唯一成体系的域，却和单点 Agent 同级 | 看不出「这 5 个属于同一条业务链」，也看不出它们的先后顺序 |
| **扩展无处安放** | 新增 Agent 只能继续往这一列里塞 | 侧边栏迟早变成一条谁也不敢动的长名单；且没有「该放哪」的判断依据 |

> **一个补充发现**：`docs/01_产品需求草稿PRD.md` 第七部分的菜单结构里，招聘 Agent 本来就写成「招聘 Agent → JD 工作台 / 简历筛选台 / 邀约与调度 / 面试辅助 / Offer 前置」的两级形态。也就是说这次改动**不是发明新结构，而是让实现对齐回 PRD 的设计**，并在中间补上「模块」这一层——此前的实现为了省事把两级压成了一级，PRD 里的层级关系在界面上丢失了。

---

## 二、目标结构：三层导航模型

**分组（group） → 目录（catalog） → 模块（module） → Agent（页）**

```
智能体中心                                    ← 分组（原有概念）
└ 🎯 招聘 Agent                    [目录]     ← 可折叠的一级容器
   ├ 岗位与需求                              ← 模块（本模块的标题）
   │  └ 📝 JD 工作台
   ├ 筛选与评估
   │  └ 🎯 简历筛选台
   ├ 面试与协调
   │  ├ 📨 邀约与调度
   │  └ 🎤 面试辅助
   └ 录用与入职
      └ 📄 Offer 前置
  🔄 入转调离 Agent                           ← 非目录节点，仍按叶子渲染（行为不变）
  💬 员工自助 Agent
  📊 人力报表 Agent
  🧩 Agent 编排
```

三个设计选择，都是有理由的：

1. **目录只做一层**。没有做无限嵌套——一层目录 + 一层模块已经能表达「域 → 阶段 → 工具」，再深就变成文件树，侧边栏不是资源管理器。
2. **只把招聘做成目录**。其余 4 个 Agent 目前是单点能力（每个只对应一个页面），硬拆成目录只会得到 4 个各含 1 个模块的空壳。**目录是给「成体系、会继续长」的域准备的**。
3. **页面 id 一个都没改**。`jd / screen / invite / interview / offer` 原样保留，所以权限、路由、测试、深链全部零回归。

## 三、模块划分依据

划分标准只有一条：**按招聘业务流的时间顺序**，不按技术实现、不按前端文件名、不按公司部门。

> 为什么：按流程划分时，业务同事和工程师能对着同一张表说话。新人要加一个 Agent，只需要回答一个问题——「它落在招聘的哪个阶段」。

| 模块 | 业务阶段 | 归类判据（一句话） | 现有 Agent | 可预见的扩展位 |
|---|---|---|---|---|
| **岗位与需求** | 提出用人需求 → JD 成稿 | 产出物是「岗位要什么」 | 📝 JD 工作台 | 岗位画像、职级带宽评估、招聘需求审批 |
| **筛选与评估** | 收到简历 → 给出排序结论 | 产出物是「人对岗位的匹配结论」 | 🎯 简历筛选台 | 笔试/测评编排、背景调查前置、人才库激活 |
| **面试与协调** | 约面 → 面试结论落库 | 产出物是「面试这件事本身」（日程 + 结论） | 📨 邀约与调度、🎤 面试辅助 | 面试题库、面试官评分校准、面试官排期约束 |
| **录用与入职** | 决定录用 → 入职前置 | 产出物是「Offer 与入职动作」 | 📄 Offer 前置 | 薪酬测算、Offer 谈判建议、入职材料收集 |

**边界示例**（拿不准时用这个判）：

- 「简历打分」→ 筛选与评估 ✓；「面试评分表」→ 面试与协调 ✓（前者评的是纸面材料，后者评的是当面表现）
- 「薪酬测算」→ 录用与入职 ✓，不放筛选与评估——它依赖的是录用决策，不是匹配结论
- 「背调」→ 筛选与评估 ✓（它发生在发 Offer 之前，结论反过来影响录用）

## 四、归类结果与代码层映射

侧边栏显示名做了**去前缀**处理（前缀收进目录名），但面包屑把前缀补了回来——否则用户只看得到「JD 工作台」，不知道自己站在哪个 Agent 里。

| 页面 id | 目录 | 模块 | 侧边栏显示名 | 面包屑 | 权限码 | 渲染函数 | 后端接口 |
|---|---|---|---|---|---|---|---|
| `jd` | 招聘 Agent | 岗位与需求 | JD 工作台 | 招聘 Agent · JD 工作台 | `job:write` | `PAGES.jd` | `POST /api/agent/jd/generate` |
| `screen` | 招聘 Agent | 筛选与评估 | 简历筛选台 | 招聘 Agent · 简历筛选台 | `screen:run` | `PAGES.screen` | `POST /api/agent/screening/run` |
| `invite` | 招聘 Agent | 面试与协调 | 邀约与调度 | 招聘 Agent · 邀约与调度 | `interview:schedule` | `PAGES.invite` | `POST /api/interviews` |
| `interview` | 招聘 Agent | 面试与协调 | 面试辅助 | 招聘 Agent · 面试辅助 | `interview:read` | `PAGES.interview` | `POST /api/interviews/:id/start` · `/feedback` |
| `offer` | 招聘 Agent | 录用与入职 | Offer 前置 | 招聘 Agent · Offer 前置 | `offer:read` | `PAGES.offer` | `GET /api/offers` · `POST /api/offers/:id/decide` |

权限码定义在 `server/rbac.js`，接口定义在 `server/routes.js`。**前端 `perm` 只做界面减负，不承担安全职责**——真正的拦截永远在服务端。

## 五、代码落点：改结构只需要动一处

| 层 | 文件 | 职责 | 加 Agent 时要改吗 |
|---|---|---|---|
| 导航数据 | `平台原型/src/app.js` → `RECRUITING` 常量 | 声明「哪个 Agent 属于哪个模块」 | **要**（加一行） |
| 渲染逻辑 | `app.js` → `renderNav` / `flatNav` / `nodeVisible` / `catalogOpen` | 通用渲染与状态 | 不用 |
| 样式 | `平台原型/src/app.css` → `.navcatalog` / `.navmodule-title` / `.navcaret` | 通用样式 | 不用 |
| 页面实现 | `app.js` → `PAGES.<id>` | 页面内容 | 要（新页才需要） |
| 打包产物 | `平台原型/index.html` | 单文件成品 | 打包一次 |

导航数据的形状（唯一需要理解的结构）：

```js
const RECRUITING = {
  id: 'recruiting', ico: '🎯', name: '招聘 Agent', catalog: true,
  modules: [                                  // 顺序 = 招聘流程的时间顺序
    { name: '岗位与需求', items: [ { id: 'jd', ico: '📝', name: 'JD 工作台', perm: 'job:write' } ] },
    { name: '筛选与评估', items: [ { id: 'screen', ico: '🎯', name: '简历筛选台', perm: 'screen:run' } ] },
    { name: '面试与协调', items: [
      { id: 'invite',    ico: '📨', name: '邀约与调度', perm: 'interview:schedule' },
      { id: 'interview', ico: '🎤', name: '面试辅助',   perm: 'interview:read' }
    ]},
    { name: '录用与入职', items: [ { id: 'offer', ico: '📄', name: 'Offer 前置', perm: 'offer:read' } ] }
  ]
};
```

## 六、新增一个招聘 Agent 的 checklist

按顺序过，缺一项就会留下隐患：

1. **归类**：先回答「它落在哪个阶段」→ 写进 `RECRUITING.modules[?].items`，一行：`{ id, ico, name, perm }`。
   - 若都不属于现有 4 个阶段 → 在 `modules` 里新增模块，**插在流程顺序对应的位置**（不要追加在末尾）。
2. **页面**：在 `app.js` 里实现 `PAGES.<id> = () => ...`。
3. **权限**：先在 `server/rbac.js` 的能力清单里加码，再用它填 `perm`。
   - 只有新能力属于既有角色时，同步更新该角色的能力数组；否则新页对所有角色都不可见。
4. **接口**（需要真后端时）：在 `server/routes.js` 注册，`need` 用第 3 步的同一个能力码。
5. **测试**：把新 id 加进 `平台原型/test_prototype.js` 顶部的 `ids` 数组——**不加就不会被逐页渲染用例覆盖**，这是最容易漏的一步。
6. **打包**：`node 平台原型/build.js`。
7. **回归**：跑下面三条（见第八节）。

## 七、设计决策与取舍

| 决策 | 理由 | 代价 |
|---|---|---|
| **目录不挂 `perm`，可见性由子项聚合** | 若目录按自己的 `perm` 判可见，只有 `screen:run` 的招聘专员会连目录带「简历筛选台」一起消失——丢的是功能，不是权限 | 目录可见性判断多一层递归（已在 `nodeVisible` 里封装） |
| **模块下全部页面不可见时，模块标题一起隐藏** | 避免留下一个点不开任何东西的空标题 | 无 |
| **折叠状态持久化到 `localStorage`** | 只跑「简历筛选台」的人不想每次都被整列招聘菜单占地方 | `file://` 双击演示时 `localStorage` 不可用 → 已用 `try/catch` 兜底，退化为「本次会话内有效」 |
| **跳转到目录内页面时自动展开该目录** | 否则当前页在侧边栏里是「隐身」的，用户会觉得导航坏了 | 用户手动折叠的意图可能被覆盖——只在跳到该目录内页面时覆盖，可接受 |
| **侧栏收起 / 窄屏时目录恒展开** | 只剩图标的情况下还要求先点开目录才见得到子项，等于把「一步进入」变成「两步」 | 窄屏下模块标题隐藏，层级感减弱（可用空间换的） |
| **页面 h2 标题保留全名** | 页面内部没有目录上下文，去掉前缀反而不清楚 | 与侧边栏短名存在表述差异，属有意为之 |
| **目录头也是 `.navitem`（`role=button` / `tabindex=0` / `aria-expanded`）** | 键盘用户必须能用 Enter 收起它；无障碍最小集里「导航项必须可聚焦」对它同样成立 | 无 |

## 八、验收

| 项目 | 结果 |
|---|---|
| 导航结构专项（`tools/test_nav.js`） | **15 项全绿**：目录与模块归属、短名与面包屑、折叠/展开、状态记录、跳转自动展开、只重绘侧栏、`flatNav` 覆盖全页、按能力裁剪 |
| 离线回归（`平台原型/test_prototype.js`） | **23 页 0 异常 · 22 项交互 0 错误** |
| 在线回归（`平台原型/test_live.js`） | **23 页 0 异常 · 26 项真实链路 0 错误** |
| 全量套件（`tools/run_all.js`） | **9 套件全部通过**（后端 5 + 自包含 1 + 前端 3） |

导航结构已经作为正式套件并入 `tools/run_all.js`（套件 id `nav`），不再是一次性脚本——否则「菜单少了一项、但页面不报错」这类问题永远不会被自动发现。

复现命令：

```bash
# 打包（改了 平台原型/src/ 就必须重新打包，否则页面还是旧的）
node 平台原型/build.js

# 导航结构专项（需 jsdom）
NODE_PATH='<node 工作区>/node_modules' node tools/test_nav.js

# 只跑前端三套件（离线渲染 + 导航结构 + 在线渲染）
node tools/run_all.js --only frontend

# 全量
node --experimental-sqlite tools/run_all.js
```

## 九、后续可做的事（未做，供决策）

1. **「智能体中心」下其余 4 个 Agent 的归位**：`入转调离 / 员工自助 / 人力报表 / Agent 编排` 目前仍是平铺。PRD 里它们各自也有 3–5 个子页，若将来真正展开，应各建目录（如「员工服务 Agent」目录含入转调离 + 自助 + 报表）。
2. **侧边栏搜索**：Agent 数量到 15+ 时，纯靠层级浏览会变慢，应支持按名称过滤。
3. **代码层的目录化**：`app.js` 已 3100+ 行，5 个招聘页面仍住在同一个文件里。若继续增长，可按模块拆成 `平台原型/src/agents/recruiting/*.js`（现有 `build.js` 的内联机制支持扩展脚本列表）。
