20 · 黄金集标注口径与扩样方案（SOP）

一句话：口径 = 先拍死 7 个选择 + 冻结一份档位定义，标注时只手拿材料、不碰算法，标完才跑评测。 本文是规程，不是结果；结果在 tools/golden/golden_set.json，指标在 tools/golden/baseline.json。 为什么值得单独写一篇：现有的 30 例已经有一套口径（写在 golden_set.json 的 method 字段里）， 但那是叙述不是规程 —— 换个人标、或隔一周再标，就会漂。扩到 60+ 例之前必须先把口径钉住， 否则拿到的是一堆互不可比的标签，指标再漂亮也没有意义。

零、先分清两件事：扩样 ≠ 改口径

扩样（本次要做的）改口径（本次不做的）
动作样本数 30 → 60+，同一套定义改档位定义 / 改档数 / 改阈值
影响指标置信区间变窄，结论更稳历史指标不可比，必须全量重标
类比多抽几个样本换一把尺子

建议：这一轮只做扩样。改口径是另一件事，混在一起会让「指标为什么变」无法归因。

一、口径 = 你要先拍死的 7 件事

#要决定的选项推荐为什么
1标注粒度（几档）三档 strong/ok/no ／ 五档（加 borderline、no-go）三档现有指标（漏筛/误筛/±1 档）全建在三档上；扩样不加粒度
2判定顺序先看分数 ／ 先过门槛先门槛后档位否则「技能全命中但年限不够」会被误标成 strong
3证据来源可参考规则实现 ／ 只看材料只看材料 + 岗位要求原文看一眼系数/门槛就等于把规则抄成答案（循环论证）
4标注者人数1 人 ／ 2 人独立1 人 + 隔期重标；有第二人则算 κ单标注者拿不到「同一人两次」以外的一致性证据
5难度配额随机抽 ／ 分层配额分层：清晰 40% / 边界 40% / 陷阱 20%全是容易的例，指标虚高且测不出失效模式
6分歧处置改标签迁就算法 ／ 保留分歧保留分歧，不改标签改了就是向算法妥协，评测失去独立性
7冻结时机边标边改 ／ 先冻结开标即冻结（rubricVersion）中途改定义 = 前后批不可比

下面逐条给可执行的定义。

二、冻结的档位定义（rubric v1）

2.1 判定顺序（必须按顺序，前一步不过就不进下一步）

text
第 1 步 · 硬性门槛（任一不过 ⇒ 直接 no，不再看后面）
  ├─ 年限：材料年限 < 岗位要求 → no
  ├─ 学历：学历位阶 < 岗位要求   → no
  └─ 相关性：岗位核心技能**一个都沾不上** → no
              （注意：是「沾不上」，不是「没写全」；
                岗位没给关键词、或材料没列技能 → 视为「判不了」，不拦）

第 2 步 · 档位（门槛全过，按证据强度定档）
  ├─ strong（优先安排面试）
  ├─ ok（可聊 / 备选）
  └─ no（不推进 —— 门槛全过但证据明显不足）
为什么顺序不能反：年限不满足的候选人技能可能很全（现在的 G-J07 就是）， 先看技能会把他标成 strong。顺序错了，标注本身就先坏了。

2.2 三档的证据定义

档位含义判定要件（门槛全过的前提下）
strong优先安排面试核心技能覆盖 ≥ 2/3 ＋ 至少 1 段对口业务（对得上岗位的行业/业务域）＋ 无硬伤
ok可聊 / 备选门槛过，但存在一项明显不足：技能覆盖 1/3~2/3 ／ 业务不对口 ／ 经验刚卡线
no不推进① 门槛不过；② 或方向不对口（跨岗，即使词面命中）；③ 或证据显示明确不匹配

注意：ok 与 no 的区别是「有救 vs 没救」——ok 是「聊一轮可能发现亮点」，

no 是「聊了也是浪费时间」。这条边界最容易漂，标注时每例都要问自己这一句。

2.3 只能用「材料 + 岗位原文」推证据

允许的依据：

  • 候选人材料里写的事实（年限、学历、技能、过往业务语境、加分项）
  • 岗位要求原文（年限/学历门槛、核心技能、职责方向）

禁止的依据（出现任何一条，这例标注作废重标）：

  • 规则实现的任何细节：维度权重（技能 .35 / 业务 .2…）、档位阈值（78 / 60）、门槛触发条件、词表内容
  • 算法的输出：test_eval 的结果、页面上的分数/档位、_eval_result.json
  • 「某某算法会给它多少分」这类反向推断

三、标注规程（照做即可）

  1. 一例一标，边标边写 labelNote —— 写明决定性因素（哪一条证据把它推进某档），

不是复述材料。labelNote 是复核标注本身是否合理的唯一凭据。

  1. 盲标：标注期间不打开 tools/test_eval.js、不看 engine.js、不跑评测。
  2. 不查重：不要去看「这一例上次标成什么」，避免锚定。
  3. 卡住怎么办：若某例「按 rubric 推不出确定档位」，说明 rubric 有洞，

记进「rubric 待改清单」，本批仍按现行 rubric 强制定档（选更保守的那档），

定义修订留到下一批。不要为了这一例临时改定义。

  1. 顺序建议：先按 difficulty 分层（清晰 → 边界 → 陷阱），不要按岗位顺序标 ——

同一岗位连续标 20 例会产生「参照漂移」（越标越松或越紧）。

四、难度分层与配额（60+ 例怎么分布）

4.1 三层难度

层定义占比作用
clear 清晰一眼能定，无歧义~40%验证「正常情况不出错」（回归护栏）
borderline 边界卡在档位线上（年限刚够/刚差、技能刚好 1/3、经验略浅）~40%最有信息量：规则的判定边界在这里被压出来
trap 陷阱词面命中但方向不对（前端含 Java、测试投开发、销售投实施）~20%暴露规则的失效模式

4.2 扩到 60 例的配额（当前 30 例为基线）

维度现在（30 例）扩样目标（60 例）硬性底线（可断言）
每岗位例数10 × 320 × 3≥ 10
档位分布strong 9 / ok 9 / no 12各档 ≥ 15 且 ≤ 50%每档占比 ∈ [20%, 50%]
陷阱探针3 例（每岗 1）每岗 ≥ 2 例每岗 ≥ 1（含 probe: true）
边界例未单独标记≥ 24 例（40%）新增例必须带 difficulty
「硬性底线」会写进 tools/test_eval.js 的黄金集结构校验，现在就在跑 —— 扩样时它会盯着你别把分布标歪。

4.3 覆盖要补的失效模式（从现有分歧与规则缺口反推）

失效模式现有承接扩样时要补
跨词族词面巧合（JavaScript↛Java）G-J09每岗至少 1 例跨词族陷阱
年限卡线（差 0.5 年 / 刚好够）G-J07各岗至少 2 例
学历卡线1 例补到 2~3 例
技能零命中但业务极对口G-M09（已知分歧）补 2~3 例，确认规则边界是否要改
技能全命中但方向不对有补 1~2 例
材料残缺（技能没解析出 / 岗位没关键词）无补 2 例，验证「不把判不了当不匹配」

五、一致性怎么证明

标注者方法判据
1 人（现状）隔期重标：全部标完后隔 ≥ 3 天，打乱顺序再标一遍（不看第一遍）两次一致率 ≥ 90%；不一致的例进「rubric 待改清单」
2 人各自独立盲标同一批算 Cohen's κ；目标 κ ≥ 0.6（substantial）

单标注者的现实：拿不到跨人 κ，就必须做隔期重标 —— 否则「标注一致性」是无证据的。

隔期重标不需要第二个人，只需要你忘掉第一遍（所以要先标完第一遍再隔期）。

六、分歧怎么处置（不许向算法妥协）

标完第一遍后，才跑 node --experimental-sqlite tools/test_eval.js 对比。会出现三类分歧：

分歧类型处置
算法过宽（人工 no / 算法 ok）记录为规则缺口 → 进难例台账 → 下一版规则的输入。不改标签
算法过严（人工 ok / 算法 no）最严重（漏筛红线）→ 立即排查是不是门槛卡死 → 进台账
标注疑似有误（对照 labelNote 发现当时想错了）允许改标签，但必须在 labelNote 里写明「修订原因 + 依据」

红线：任何情况下都不得因为「算法这么判好像也有道理」而改标签。那是循环论证，

会让一致率变成自证。分歧是有价值的产品输入，不是失败。

七、冻结与版本

字段位置作用
rubricVersiontools/golden/golden_set.json档位定义的版本号；本文（docs/20）是它的人类可读快照
versiontools/golden/golden_set.json数据集版本（增删样本时递增）
n / 指标tools/golden/baseline.json指标唯一源

规则：

  1. rubric 一旦开标冻结；标注中途发现洞 → 记清单，本批标完再说。
  2. 改 rubric ⇒ rubricVersion +1，且全量重标（新旧标签不能混）。
  3. 样本数变化 ⇒ 必须跑 --write-baseline 刷新基线，否则 test_eval 的「样本数与基线一致」会红。
  4. 样本变难导致一致率下降 ≠ 回归失败：若一致率下降、但漏筛率仍 = 0，属正常；

此时应下调基线里的一致率（说明理由），而不是把难例删掉。

八、验收（扩样完成后跑这些）

bash
# 1. 结构 + 配额校验（含在评测里，随 npm test 一起跑）
node --experimental-sqlite tools/test_eval.js

# 2. 刷新指标唯一源（样本数变了必须做）
node --experimental-sqlite tools/test_eval.js --write-baseline

# 3. 文档数字与代码对齐（README 等会被守卫检查）
npm run check:docs

# 4. 全量回归
npm test

要看的：

  • 漏筛率仍然 = 0（红线，一条都不放松）
  • 一致率若下降 → 归因：新样本更难（正常）还是规则退步（要修）
  • 难例台账（现在只有 G-M09）→ 扩样后会变长，这就是下一轮规则迭代的待办

九、工作表怎么用

配套模板：tools/golden/labeling_worksheet.csv —— 13 列。前 3 行是已有案例（G-J01 / G-J04 / G-J09，

仅作格式示例 —— 不要重复录入，重号会被 A5 的「case id 唯一」断言抓住）；其下 30 行待标空行（G-J11…G-M20，每岗 10 行）。

列填什么
case_id唯一例号（岗位前缀 + 序号，如 G-J11）
job_id岗位（必须已存在于 golden_set.json 的 jobs）
difficultyclear / borderline / trap
skills / business_tags / plus_tags用 ` 分隔（如 JavaSpring BootMySQL`）
labelstrong / ok / no（盲标，不填 AI 档位）
label_note决定性因素一句话（复核用，别复述材料）
probetrue（陷阱探针）/ 留空
labeled_at标注日期（北京时间 YYYY-MM-DD）
rubric_version标注时用的 rubric 版本（当前 1）

标完把工作表人工合并进 golden_set.json 的 cases 数组（保持 JSON 格式），再跑第八节的验收。

十、口径速查卡（打印版）

标注一例时，只问三个问题： 1. 门槛过了吗？（年限 / 学历 / 技能沾不沾边）—— 任一不过 ⇒ no，收工。 2. 有救吗？ —— 有（聊一轮可能有亮点）⇒ ok；没有 ⇒ no。 3. 够不够抢手？ —— 技能 ≥2/3 + 有对口业务 + 无硬伤 ⇒ strong；否则 ok。 三条禁令：不看系数 / 不看分数 / 不改标签去迁就算法。 一条纪律：卡住 → 记进「rubric 待改清单」，本批照旧标，别临时改定义。 版本：rubric v1 · 2026-10-03 · 快照见本文；机器可读字段 tools/golden/golden_set.json:rubricVersion
