一、项目定位与目标形态

1.1 一句话定位

一个可私有化部署的「HR 数字员工平台」：HR 在系统里建立岗位库，AI Agent 承接简历初筛、JD 生成、审批留痕、员工自助问答四类高频工作；所有涉及判断的环节都给出可追溯的证据，所有涉及合规的环节都由确定性代码兜底。

1.2 目标形态（已与你确认）

维度结论说明
产品形态单租户 · 可私有化部署的产品不背多租户 SaaS 与计费的包袱
使用目的求职作品集 / 面试演示结论：技术纵深与「讲得清取舍」优先于运营完备度
身份体系自建账号 + RBAC不接企业 SSO，不做组织架构同步
部署方式单机 / 单容器，数据不出本机（私有化）与「简历属敏感个人信息」的定位自洽

为什么这个组合是自洽的：作品集要的是「能被追问的深度」，不是「能扛多少租户」。因此把工程量投在可信（身份/权限/审计）、可控（确定性规则边界）、可讲（架构分层与取舍）三件事上，而不是多租户计费。

1.3 与现有资产的关系

现有资产现状在目标形态里的角色
平台原型/index.html✅ 已实现：单文件 366KB、23 页、零依赖、双击即开演示主入口（离线可演示，不怕现场没网）
server/ 零依赖后端✅ 已实现：Node 22 原生 http + node:sqlite、13 张表、真写库/真闸门/真审计演进基座（保留其「零依赖可交付」的卖点，逐步换骨架）
shared/req-lib.js✅ 已实现：30 职能族 / 242 句职责 / 18 类行业词库，前后端唯一来源核心资产，产品差异化所在（详见 §4.2）
双模式回归测试✅ 已实现：离线 / 在线各 23 页 + 16 项，0 错误质量证据，面试可直接演示

口径提醒：上表右列凡标「设计目标」者均为未实测值，面试时应说「我设定的目标是 X，验证方式是 Y」，不要当成已达成结果。

2.3 产品原则（这四条决定了后面所有取舍）

  1. 能用规则就别用模型 —— 年限、学历这类硬门槛由代码判定，0 token，结果可复现。
  2. 物理剔除 > 提示词请求 —— 反歧视不是「请求模型别看性别」，而是让模型根本拿不到该字段。
  3. AI 的判断必须带证据 —— 每一条打分都要能指回原文片段，否则不可信。
  4. 演示态与真实态结论同源 —— 离线模式的合规扫描也是真扫，不写死结论。

三、范围与非目标

  1. 岗位库与 JD 生成（含合规扫描）✅ 已有，待打磨

  3. 审批中心与审计日志
  4. 员工自助问答（HR 业务库查询 + 知识库检索 + 拒答转人工）
  5. 身份认证与 RBAC（本期最大新增，见 §6-M1）
  6. 报表与问数（现状为 mock，需接真查询）
  7. 数据治理（候选人授权、留存期、删除权）

3.2 非目标（Out of Scope，明确不做）

不做理由
多租户 SaaS 与订阅计费与「求职作品集」定位不符，且会稀释工程量
薪酬 / 考勤 / 绩效 / 社保代办等全 HRMS 模块那是另一条产品线（对标 Frappe HR / OrangeHRM），本产品聚焦「招聘 + 自助」
自动发 Offer、自动拒信高风险决策必须有人在场，产品原则不容许
简历爬虫 / 与外部 ATS 双向同步合规与工程量双重不可控
生产级 K8s 编排与 SLA 承诺本期交付到「单容器可部署 + 可观测」为止
为什么非目标要写死：B 端产品的死法通常不是做得不对，而是做得太多。这一节同时是面试里最容易被追问的点——「你为什么不都做」比「你做了什么」更能看出判断力。

4.2 核心资产：岗位与 JD 的确定性生成

这是本产品最不可替代的部分，也是面试最值得展开的技术亮点：

  • 职能族优先、行业兜底：30 个职能族（技术/产品/设计/数据/运营/市场/销售/实施交付/HR/财务/风控合规/供应链/生产/工程设备/工艺/质量/医疗/客服/零售门店/行政/法务合规/教育培训/建筑工程/传媒内容/物流运输/酒店餐饮/物业安保/医药健康/游戏/能源电力）。
  • 解决的真实 bug：「互联网行业的 AI 产品经理被补上 Java」——根因是把「行业」当成「职能」。
  • 一识别词只属一族：族的分界按「这个人每天做什么」划，不按行业或公司部门划。
  • 职责子方向择优：242 句职责池带子方向标签，pickDuties() 按岗位名择优取 6 条 → 同族不同岗不再一字不差，且纯规则、可复现、0 token。
  • 行业语境词接回：17 个行业各有「指标 + 行话」口径句（如「以 DAU、留存与转化漏斗为核心指标，结合埋点与 A/B 实验验证迭代效果」），拼入前做 LCS + bigram 双重去重。
  • 版本自愈：REQ_LIB_VER + jobs.jd_ver，启动时自动重算历史 JD，老脏数据不用手工洗。
面试价值：这一段能同时回答「你怎么处理幻觉」「怎么保证可复现」「规则和模型怎么分工」三个高频问题。

本节的架构启示（已吸收进 docs/08）： ① 适配器模式隔离模型供应商 —— 换模型不改业务代码； ② 分层要按「变化频率」切：模型、检索、规则三者的变化频率完全不同，不该混在一层； ③ RAG 与规则引擎是并列的能力，不是「RAG 取代规则」； ④ 企业能力的落点是 SSO / RBAC / 审计日志（Dify 企业版清单与 OrangeHRM 安全三件套相互印证）。

5.4 我们与对标的差异（面试必答）

主流开源项目要么偏求职者侧（career-ops、ai-job-search），要么偏简历解析工具（Resume-Matcher、hiring-agent），要么偏全 HRMS 套件（Frappe HR、OrangeHRM）。 我们的位置是它们之间的空档：HR 侧、以「岗位库驱动的确定性生成 + 可信 Agent 流程」为核心——不是简历解析器，也不是 HR 大套件。 并且已有别人没有的东西：30 职能族 / 242 句职责 / 18 类行业词库这套跨行业岗位语义资产，以及双模式（离线可演示 / 在线真跑）的交付形态。

一、架构目标与约束

1.1 架构目标（按优先级）

  1. 可信：身份不可伪造、权限不可绕过、审计不可篡改。
  2. 可控：凡涉及硬判断（年限/学历/合规），必须由确定性代码执行且可复现。
  3. 可讲：每一层有明确职责边界，每个关键决策有对标依据与取舍说明。
  4. 可演：断网可演示，单文件可分发，数据不出本机。
  5. 可演进：不追求一步到位的生产级规模，但不允许出现无法回退的设计。

1.2 硬约束

约束来源对架构的影响
简历属敏感个人信息（PIPL）法律字段级加密、留存期清理、删除权、演示数据全合成
招聘决策不得有歧视劳动法/就业促进法受保护字段物理剔除；合规扫描带法条依据
单人维护你的真实约束组件数最少、单语言优先、零依赖演示包必须保留
目标形态为单租户私有化你已确认不做租户管理 UI；但所有查询仍带 tenant_id（低成本预留）
身份为自建账号 + RBAC你已确认自建会话/令牌；不引入 SSO 中间件

四、关键设计决策（ADR）

每条含：决策 / 背景 / 备选 / 取舍 / 状态。这一节是面试追问的靶心。

ADR-001 · 分类轴用「职能族优先、行业兜底」

  • 决策：先用岗位名识别职能族（30 族），识别不到才回落行业词库。
  • 背景：曾出现真实 bug——「互联网行业的 AI 产品经理被补上 Java/Spring」。根因是把「行业」当成「职能」：互联网行业的技能库里第一条就是 Java。
  • 备选：① 只用行业（原始方案，已被证伪）；② 用 LLM 做语义分类。
  • 取舍：LLM 分类更灵活但不可复现、有成本、会漂移；规则分类可复现、0 成本、可回归。选规则，且把 detectFunction 的命中规则设计为与职责选取同构（岗位名 ×3、正文 ×1）。
  • 状态：① 已实现（shared/req-lib.js）。

ADR-002 · 规则先行、模型兜底（硬判断永不下放）

  • 决策：年限、学历、合规、权限四类硬判断由确定性代码执行；模型只负责表达与语义理解。
  • 对标依据：sliday/resume-job-matcher（硬约束先淘汰、再打分、分数引用原文）与 interviewstreet/hiring-agent（规则快筛 + LLM 语义打分双后端）独立收敛到同一设计，说明这是行业共识而非个人偏好。
  • 取舍：牺牲一部分「智能感」，换来可复现、可审计、0 token。
  • 状态：① 已实现（规则门槛 0 token）。

ADR-003 · PII 物理剔除，而非在提示词里请求

  • 决策：性别、年龄、婚育等受保护字段在 SQL 查询层就不被 SELECT。
  • 备选：在提示词里写「请不要考虑性别年龄」。
  • 取舍：提示词方案在合规审查面前不成立——「我请求模型别看」与「模型根本拿不到」是两种证据强度。
  • 状态：① 已实现。

ADR-004 · 词库前后端同源（UMD 单文件）+ 版本自愈

  • 决策：shared/req-lib.js 是唯一词库源，后端 require、前端由构建脚本内联为 __REQLIB__。
  • 背景：曾出现「离线说的和在线说的不一样」——同一个 JD，离线模式与在线模式结论不同。
  • 配套：REQ_LIB_VER（前后端共享的素材版本号）+ jobs.jd_ver，服务启动时把落后版本的 JD 自动重算回写。
  • 取舍：引入了「版本自愈」的隐性副作用（启动时批量写库），因此必须包在单事务里（见 ADR-005）。
  • 状态：① 已实现（当前 REQ_LIB_VER = 7）。

ADR-005 · 批量写库必须单事务（一次真实的线上级故障）

  • 现象：/api/reset 耗时 6.8 秒，紧随其后的 keep-alive 请求稳定 ECONNRESET。
  • 根因：node:sqlite 每条语句自动提交，Windows 上每次 commit 触发 fsync；约 120 条种子写库 = 120 次 fsync，阻塞事件循环数秒，期间空闲连接被断开。
  • 决策：inTx() 把 seed() / reseedRuntime() / 首次建库全部包进单事务；启动时的老 JD 自愈 UPDATE 也并成一个事务。
  • 结果：重置 6.8s → 70–160ms（约 70×），双模式回归转绿。
  • 价值：这是「先跑真链路、再交货」的价值证明——该 bug 是我跑回归时撞出来的，不是用户报的。
  • 状态：① 已实现。迁移到 PostgreSQL 后此问题自然消失，但事务边界设计保留。

ADR-006 · 技术栈选「单一 TypeScript + pgvector」（我的推荐）

  • 决策：Next.js + NestJS/Fastify + PostgreSQL + pgvector + Redis + BullMQ + S3 兼容存储。
  • 备选：② Python 后端（对齐 Resume-Matcher / hiring-agent 生态）；③ 保留零依赖 Node。
  • 取舍：
  • 选 ① 的理由：可复用核心资产（req-lib.js 已是 JS，直接 TS 化即可保住「前后端同源」亮点）；组件最少（pgvector 让向量与业务同库，少一个中间件对单人项目意义重大）；面试市场最熟悉。
  • 选 ① 的唯一硬伤：Node 侧 PDF/DOCX 解析与中文 NLP 弱于 Python。
  • 折中（待你选）：① + 一个可选 Python 解析 sidecar（只做「文件 → 文本/结构化字段」），两头都要。
  • 状态：⏳ 待你拍板（详见 docs/07 §9-①）。

ADR-007 · 审计日志 append-only

  • 决策：审计表只允许 INSERT，禁止 UPDATE/DELETE（数据库权限层约束，而非应用层自觉）。
  • 对标依据：OrangeHRM 的「审计追踪」与 Dify 企业版的「审计日志」都把审计列为不可省的企业能力。
  • 状态：① 已实现（应用层只插不改）；数据库层约束为 ② 设计目标。

ADR-008 · 离线 / 在线双模式同源

  • 决策：同一份 index.html，双击 = 离线演示态，被后端托管 = 真实态；两态的结论必须同源（合规扫描在离线端也是真扫，不写死结论）。
  • 理由：作品集的核心场景是现场演示——断网、无后端、临时换机器都不能翻车；同时不能为了演示效果撒谎。
  • 状态：① 已实现（双模式回归各 23 页 + 16 项全绿）。

ADR-009 · 权限做三层，注册即最小权限

  • 决策：功能级（能否访问该 API）× 行级（只能看本部门/本人的数据）× 字段级（PII 字段默认不返回，需显式提权 + 留痕）。
  • 对标依据：OrangeHRM 的「角色最小权限 + 行级限制 + 字段级防护」；Dify 企业版的 SSO/RBAC/审计三件套。
  • 状态：⏳ ③ 尚未具备（M1 交付）。

ADR-010 · 模型走适配器，业务不感知供应商

  • 决策：Llm.complete() 统一接口 + 供应商适配器；业务层只声明「要什么能力」，不声明「用谁」。
  • 对标依据：Dify 的适配器模式（换模型只改配置，不重构业务逻辑）。
  • 配套：超时、重试退避、失败降级到规则模式、token 记账、输出审计、Prompt 版本化。
  • 状态：🟡 ② 部分（可插拔与降级已有；记账/审计/额度未有）。

  ── 字段映射：JSONB ↔ TEXT(JSON)、UUID ↔ TEXT
  ── 顺带清理无租户过滤的查询
  ── 保留 SQLite 模式作为「离线演示」后端（双后端，按开关切换）
