19 · 平台从 0 到 1 全流程与风险台账

本文回答两个问题： ① 一个平台从 0 到 1 该怎么走 —— 每个阶段的关键节点、出口判据、以及在这个阶段必然出现的问题； ② 怎么把成果整理成一份经得起交叉核对的面试作品并传到 GitHub。 写法：不是通用方法论清单，而是拿本项目（HR-Agent OS）当样本 —— 每条风险都标注了它在本仓库里 是「已实证发生过」「已提前规避」还是「仍未解决」。凡结论都可在仓库里定位到文件。 通用方法论谁都能说；能说出「我们当时真栽在这条上、后来在哪个文件里修掉」才有说服力。 事实纪律：沿用本项目既有口径 —— ① 已实现（有代码、有实测、可当场复现）／ ② 设计目标（有设计未实测，明确标注）／③ 尚未具备（诚实列出）。数字以 node tools/check_docs.js 为准。

〇、一页速览

项结论
全流程9 个阶段：立项 → 调研 → 决策 → 建模 → PRD → 原型 → 真后端 → 合规 → 上线运营（+ 贯穿全程的「评测与自省」）
最容易死人的三步立项不写非目标（什么都做）· 决策不划 AI 边界（为 AI 而 AI）· 测试没断言（假绿）
本项目的真实事故文档数字漂移（5 篇现状类文档残留 14 处旧页面数）· 空断言（看起来在检查、其实观测不到）· 测试测的是旧产物
风险台账规模39 条，按阶段分为产品 / 技术 / 协作 / 合规四类，每条给「触发信号 → 对策」
作品化仓库结构 / 文档三层 / README 首屏 / 5 个展示重点 / 上传与发布步骤 见第四部分
一句话0→1 的胜负不在「功能做得多」，在每个阶段有没有一个能被验证的出口判据 —— 没有判据的阶段必然返工

贯穿全程的一条横线：评测与自省 —— 每个阶段都要能回答「我凭什么说这个阶段做完了」。

三、风险台账（39 条）

读法：触发信号是「怎么知道自己正在踩这个坑」——比风险本身更有用。

阶段 0 · 立项

#风险 / 常见问题触发信号对策与规避本项目处置
1什么都想做：功能清单越写越长PRD 里没有一节叫「不做」先写 Non-goals，再写功能；每个「不做」必须给理由✅ 立项先否掉完整 HRIS / 自动发 Offer / 简历爬虫 / 视频面试分析
2拿行业报告当需求说不清「谁的一天变短了」需求必须落到「谁的哪个动作」✅ As-Is 表按 HR 的一天写，每条标耗时
3定位靠形容词（赋能、提效）上线后无法验收定位必须是可计数的数字✅ 价值主张改成三个数字（人效 / 逾期率 / 报表时长），并标注为设计目标未实测
4只写增长 KPI 不写护栏KPI 树里没有「必须为 0」的项护栏指标与增长指标同树✅ 越权次数 / 敏感信息外泄 / 未审批执行数 = 0
5立项文档只有结论没有假设评审时无人可攻击立项即列「可能错在哪」⚠️ 立项阶段未列，到 PRD 阶段才补（见 #16）

补一条：跨阶段的「文档漂移」（本项目 2026-10-03 刚修）

表现触发信号影响已采取的对策
同一事实在多个文档里各写一个值交叉核对时两个数字对不上面试官会因此怀疑全部材料① check_docs.js 正向锚点：现状句必须与代码一致，写错会指名道姓告诉你该改成什么；② 新增负向锚点：旧值不得在现状类文档里复活；③ 评测数字以 tools/golden/baseline.json 为唯一源

实测规模：页面数 23 → 24 之后，5 篇现状类文档残留 14 处旧值，而正向锚点当年只钉住了其中 2 句（另有 22 处落在历史类文档里，按口径豁免）。

补上负向锚点后，验收方式变成「破坏 → 必红（并给出 文件:行号）→ 还原 → 必绿」。

历史类文档（CHANGELOG / 项目计划书 / 架构设计 / 验收报告的实跑记录 / 时点评估快照）豁免不改 ——

它们保存的是「当时是多少」的证据，改掉才是篡改。

四、GitHub 作品化：怎么整理、怎么上传、怎么展示

前提认知：面试官平均只会花 90 秒看你的仓库。前 30 秒看 README 首屏，后 60 秒决定点不点第二个文件。 所以作品化的目标不是「资料多」，是让价值在最前面被看见，且经得起抽查。

bash

git grep -nIE 'C:[\\/]Users|密码|api[_-]?key|sk-[A-Za-z0-9]{16,}'  # 本机路径与凭证零命中

# ② 提交（提交信息写"改了什么 + 为什么"，别写 "update"）
git add -A && git commit -F _msg.txt

# ③ 推送
git push -u origin main

# ④ 打开 GitHub Pages（零安装 demo）
#    Settings → Pages → Source = GitHub Actions（或直接 POST /repos/{owner}/{repo}/pages）

受限网络下的三条通道（本项目踩过 5 次，结论已写成技能 github-upload-restricted-network）：

① 先量代理是否整体挂掉（env | grep -i proxy + git ls-remote 双向测），别把「单次失败」当「通道不通」；

② 代理不可用时 env -u https_proxy -u http_proxy … git push 直连反而通；

③ git credential fill 在网络不可达时会挂起而不是报错（表现为脚本卡死、日志空白），

改从系统凭据管理器直读令牌（references/read-gcm-token.ps1），用 GIT_CONFIG_* 环境变量传鉴权头（不进 argv）。
