JD 粘贴解析口径 v14 修复说明

版本：REQ_LIB_VER 13 → 14　|　修复时间：2026-10-02（北京时间） 影响面：前后端共用 shared/req-lib.js，改一处两端同时生效；离线原型需 npm run build 重内联。 触发：用户把整段 JD 粘进表单生成后，发现三处排版/语法问题。

1 · 问题现象

三条，都出现在「整段 JD 粘进表单 → 生成 JD」这条路径上。

#现象（用户所见）问题
11. 职位职责1、对接售前/商务，承接ToB客…编号叠加：模板的 1. 和内容自带的「职位职责1、」重复
2（一）专业技能 段开头只剩一个「目」字断行把一句话切成两半，尾部落成了独立条目，上文丢失
3（五）软技能 下直接跟 5、逻辑清晰、沟通顺畅、板块内序号没有剥掉，也没从 1 重新开始

2 · 根因（全部在 shared/req-lib.js::parseReqText）

根因 A — 小标题词表不全 + 判标题条件过严

RE_HEAD_ANY 里没有「职位职责」「职位要求」这类变体；且判标签要求「整行 ≤ 12 字」。

用户写的是 职位职责1、对接售前/商务…——标签与内容挤在同一行，两个条件都不满足，整行被当成一条职责落进正文，再被模板套上序号 → 现象 1。

根因 B — 行首序号剥离要求「标点后必须跟空格」

RE_LI_NUM = /^\d{1,2}\s*[.、)）:：]\s+/ 末尾是 \s+。

中文写法 5、逻辑清晰 不带空格，正则不匹配 → 序号残留 → 现象 3。

根因 C — 序号未剥导致断行碎片独立成条

5、逻辑清晰、沟通顺畅，能独立推进跨团队落地项 因序号没剥而 marked=false，

下一行 目。 不满足合并条件，断开成独立条目「目」 → 现象 2。

三个根因互为因果：B 不修，C 就修不掉。

3 · 修法（共 6 处，shared/req-lib.js）

  1. RE_HEAD_ANY 补词：加入 职位职责 / 职位描述 / 工作职责 / 职务职责 / 职位要求 / 岗位描述 / 工作要求 / 职务要求 / 任职资格 / 应聘要求 / 招聘条件 / 我们希望你 等变体。
  1. 新增 RE_HEAD_LEAD：行首标签剥离，专治「标签与内容同行、无冒号」。

只在标签后紧跟 行尾 / 冒号 / 列表编号 / 列表符号时才认标题，

所以「负责岗位职责梳理」这类以标签词开头的正文句不受影响。

该步骤必须在「编号剥离循环」之前执行，剥出来的 1、对接… 才能被去掉序号。

  1. RE_LI_NUM 放宽：中文编号符（、)）:：）后空格改为可选；

西文句点仍强制要求空格 —— 避免「1.5 年经验」被误剥成「5 年经验」。

  1. 收紧 numHead：带编号的行不再无条件当标题。

原逻辑 isHead = mdHead || numHead || … 会把 1、对接售前… 整行 return 掉，

用户粘的内容静默消失（JD 里只剩模板补位句）。

现在要「剥掉编号后仍命中标签词且 ≤12 字」（如 1. 岗位职责）才认标题。

  1. 断行还原区分「短尾」：下一行去掉标点后 ≤2 字时直接拼接、不插分隔符

（…交付经验优 + 先； 实为「优先」，补逗号会插进词中间）；

其余情况沿用原规则补逗号（• 把模糊的用户场景 + 拆成能落地的产品方案）。

  1. 新增行内条目切分：仅在「； + 1~2 位数字 + 编号符」处切开。

复制来的 JD 常把多条挤在同一行（…业务流程；2、独立完成…；3、跟进…），

只按换行切会整段粘成一条。普通分号一律不切，保持「表单一行一条 → 往返无损」。

另：server/engine.js 的 REQ_LIB_VER 由 13 递增到 14 —— 解析口径变了，已存岗位的 JD 需按新口径重算（懒触发，登录拉一次快照时执行）。

5 · 未修的部分（源文本损坏，不猜）

用户原文是从某处复制来的，本身顺序错乱，例如孤立行 化为完整产品设计;

实际属于下一条要求，却被粘到了上一条的末尾。

这类问题解析层无法可靠还原（任何猜测都可能把 A 条的内容搬到 B 条）。

处理原则：宁可保留原始错位，也不臆造归属 —— 这类内容需要人工校正后再粘贴。

6 · 维护提醒

  • 加小标题变体时，RE_HEAD_ANY 与 RE_HEAD_LEAD 两张表都要加，只加一处会漏。
  • 动 parseReqText 前先跑 node tools/test_jd.js；改完必须跑全量 npm test。
  • 改了 shared/req-lib.js 必须 npm run build（离线原型内联同一份词库），随后跑 npm run check:docs。

7 · 补充（同日）：整段 JD「分栏回填」—— 让「岗位职责」栏不再静默丢内容

起因

上面第 4 节给出的使用建议是「整段 JD 请粘到任职要求栏」。用户据此反问：

那岗位职责的栏还有必要存在吗？

实测证实这不是「多了一栏」，而是两栏能力不对称：

粘进去的东西粘「岗位职责」栏（parseDutyInput）粘「任职要求」栏（splitReqInput）
整段 JD（职责+要求）只取 p.duty，must/nice 静默丢弃职责 + 要求 全归位
只有职责heads=0 → 整段归 duties ✅✅
只有要求（误用）⚠️ 要求被当成职责落库，污染 duties✅

根因就是 engine.js 里这一行：parseDutyInput = p.heads ? p.duty : p.must ——

一识别出小标题，就只挑职责，其余当没看见。于是「别粘这栏」的建议本质是绕开缺陷，

而不是修它 —— 用户以为平台吞了内容，这个怀疑完全合理。

「岗位职责」栏不能删：它是 jobs.duties 的显式入口（职责不进打分关键词，但必须落库，

否则编辑 / 版本自愈会静默换成模板），也是「只改职责」的唯一通道。

修法（方案 A：补齐不对称，而非删栏）

在前端加一层「分栏回填」—— 用户在任一 JD 输入框粘入整段 JD 时，

按结构拆开并把任职要求 / 加分项分派到各自输入框：

  • 平台原型/src/agent.js：新增 splitJdFields(text)（与后端 splitReqInput 同源），

返回已清理（去序号、去尾标点）并去重的 lead / duty / must / nice / heads，并导出。

  • 平台原型/src/app.js：新增 paste 事件委托，监听 #jdDuty / #jdMust / #jdNice 三栏。

仅当 heads ≥ 2（确实是一份完整 JD）才介入，否则交回浏览器默认粘贴 ——

「一行一条」的手工填法完全不受影响。

  • 合并策略一律「追加 + 去重」，绝不覆盖已填内容：宁可多一条，不可丢一条。

未改 REQ_LIB_VER：本次只动前端输入辅助，不改解析口径、不影响打分，已存岗位无需重算。

用户操作修复前修复后
