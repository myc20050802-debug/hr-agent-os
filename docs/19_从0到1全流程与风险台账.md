# 19 · 平台从 0 到 1 全流程与风险台账

> **本文回答两个问题**：
> ① 一个平台从 0 到 1 该怎么走 —— 每个阶段的关键节点、出口判据、以及**在这个阶段必然出现的问题**；
> ② 怎么把成果整理成一份**经得起交叉核对的面试作品**并传到 GitHub。
>
> **写法**：不是通用方法论清单，而是**拿本项目（HR-Agent OS）当样本** —— 每条风险都标注了它在本仓库里
> 是「已实证发生过」「已提前规避」还是「仍未解决」。凡结论都可在仓库里定位到文件。
> 通用方法论谁都能说；**能说出「我们当时真栽在这条上、后来在哪个文件里修掉」才有说服力**。
>
> **事实纪律**：沿用本项目既有口径 —— **① 已实现**（有代码、有实测、可当场复现）／
> **② 设计目标**（有设计未实测，明确标注）／**③ 尚未具备**（诚实列出）。数字以 `node tools/check_docs.js` 为准。

## 〇、一页速览

| 项 | 结论 |
|---|---|
| 全流程 | **9 个阶段**：立项 → 调研 → 决策 → 建模 → PRD → 原型 → 真后端 → 合规 → 上线运营（+ 贯穿全程的「评测与自省」） |
| 最容易死人的三步 | **立项不写非目标**（什么都做）· **决策不划 AI 边界**（为 AI 而 AI）· **测试没断言**（假绿） |
| 本项目的真实事故 | 文档数字漂移（5 篇现状类文档残留 14 处旧页面数）· 空断言（看起来在检查、其实观测不到）· 测试测的是旧产物 |
| 风险台账规模 | **39 条**，按阶段分为产品 / 技术 / 协作 / 合规四类，每条给「触发信号 → 对策」 |
| 作品化 | 仓库结构 / 文档三层 / README 首屏 / 5 个展示重点 / 上传与发布步骤 见第四部分 |
| 一句话 | 0→1 的胜负不在「功能做得多」，在**每个阶段有没有一个能被验证的出口判据** —— 没有判据的阶段必然返工 |

## 一、全流程一张图

```
0 立项判断 ──▶ 1 业务发现 ──▶ 2 产品决策 ──▶ 3 产品建模 ──▶ 4 PRD 方案
   │              │              │              │              │
 要不要做       痛在哪         谁来做        对象是什么      怎么讲清楚
 出口：非目标   出口：可证伪   出口：四边界  出口：表结构    出口：非技术读者读懂
                                                              │
                                                              ▼
9 上线运营 ◀── 8 合规安全 ◀── 7 真后端 ◀── 6 测试 ◀────────── 5 原型
   │              │              │            │
 出口：         出口：         出口：        出口：
 preflight 0    红线在代码     真库/真拦/    断言全绿 +
 + 可回滚       不在提示词     真留痕        能反向验证

**贯穿全程的一条横线：评测与自省** —— 每个阶段都要能回答「我凭什么说这个阶段做完了」。
本项目里它落成了 `tools/check_docs.js`（文档与代码一致）+ `tools/golden/`（筛选质量）+ `tools/run_all.js`（回归）。

## 二、阶段表：关键节点 + 出口判据

> 出口判据 = **Go 的条件**。写不出判据的阶段，等于没定义「做完」。

| 阶段 | 关键节点 | 必须产出的物 | 出口判据（Go 条件） |
|---|---|---|---|
| **0 立项** | 写非目标 · 划客群 · 定北极星 | 一句话定位 / 目标客群 / Non-goals | 能说清**不做什么**及理由 |
| **1 调研** | 看场景不抄需求 · 给痛点标耗时 · 归纳病根 | As-Is 现状表 / 病根 / KPI 树（含护栏指标） | 病根一句话能概括，且指向可量化指标 |
| **2 决策** | 四边界划分 · 能用规则不用模型 · 网关可降级 | Agent / Workflow / Rules / Human 边界表 | 每个模块能回答「为什么必须是它」 |
| **3 建模** | 先定对象再画页面 · 权限与状态先画 | 对象关系 / 表结构 / 权限矩阵 / 状态机 | 表按**对象**建，不按页面建 |
| **4 PRD** | 先统一语言 · 写假设与开放问题 · 写自我挑战 | 七部分 PRD + 术语表 + 假设清单 | 非技术读者一次读懂；假设可被证伪 |
| **5 原型** | 判断类问题用可点原型 · 零依赖交付 · 离线不说假话 | 单文件原型（本项目 **24 页 / 545,169 bytes**） | 全页可点、关键链路可走通、离线结论与真实同源 |
| **6 测试** | 断言即功能 · 反向验证 · 隔离实例回归 | 套件（本项目 **12 套件**）+ 黄金集 | **全绿 + 破坏态必红 + 没跑的套件不许算通过** |
| **7 真后端** | 零依赖选型 · 迁移不重建 · 真写/真拦/真留痕 | 可运行全栈（HTTP + SQLite + 引擎） | 打分真进库、闸门真拦、越权真 403 且留痕 |
| **8 合规安全** | 红线写成代码 · 物理剔除字段 · 高风险进人工闸门 | 规则表（歧视 11 + 违法 9）+ 审计链 + 权限矩阵 | 命中即阻断；每条规则带法条依据 |
| **9 上线运营** | preflight 只读自检 · 备份可验可恢复 · 回滚演练 | 上线手册 + 备份脚本 + 发布路径 | `npm run preflight` 退出码 0 才可以把链接发出去 |

## 三、风险台账（39 条）

> 读法：**触发信号**是「怎么知道自己正在踩这个坑」——比风险本身更有用。

### 阶段 0 · 立项

| # | 风险 / 常见问题 | 触发信号 | 对策与规避 | 本项目处置 |
|---|---|---|---|---|
| 1 | **什么都想做**：功能清单越写越长 | PRD 里没有一节叫「不做」 | 先写 Non-goals，再写功能；每个「不做」必须给理由 | ✅ 立项先否掉完整 HRIS / 自动发 Offer / 简历爬虫 / 视频面试分析 |
| 2 | **拿行业报告当需求** | 说不清「谁的一天变短了」 | 需求必须落到「谁的哪个动作」 | ✅ As-Is 表按 HR 的一天写，每条标耗时 |
| 3 | **定位靠形容词**（赋能、提效） | 上线后无法验收 | 定位必须是可计数的数字 | ✅ 价值主张改成三个数字（人效 / 逾期率 / 报表时长），并标注为**设计目标未实测** |
| 4 | **只写增长 KPI 不写护栏** | KPI 树里没有「必须为 0」的项 | 护栏指标与增长指标同树 | ✅ 越权次数 / 敏感信息外泄 / 未审批执行数 = 0 |
| 5 | 立项文档只有结论没有假设 | 评审时无人可攻击 | 立项即列「可能错在哪」 | ⚠️ 立项阶段未列，到 PRD 阶段才补（见 #16） |

> 以及下面这条「文档漂移」—— 它们都不是「技术难题」，是**纪律问题**。

### 补一条：跨阶段的「文档漂移」（本项目 2026-10-03 刚修）

| 表现 | 触发信号 | 影响 | 已采取的对策 |
|---|---|---|---|
| 同一事实在多个文档里各写一个值 | 交叉核对时两个数字对不上 | **面试官会因此怀疑全部材料** | ① `check_docs.js` 正向锚点：现状句必须与代码一致，写错会指名道姓告诉你该改成什么；② **新增负向锚点**：旧值不得在现状类文档里复活；③ 评测数字以 `tools/golden/baseline.json` 为**唯一源** |

实测规模：页面数 23 → 24 之后，**5 篇现状类文档残留 14 处旧值**，而正向锚点当年只钉住了其中 2 句（另有 22 处落在历史类文档里，按口径豁免）。
补上负向锚点后，验收方式变成「破坏 → 必红（并给出 `文件:行号`）→ 还原 → 必绿」。
历史类文档（CHANGELOG / 项目计划书 / 架构设计 / 验收报告的实跑记录 / 时点评估快照）**豁免不改** ——
它们保存的是「当时是多少」的证据，改掉才是篡改。

## 四、GitHub 作品化：怎么整理、怎么上传、怎么展示

> 前提认知：**面试官平均只会花 90 秒看你的仓库**。前 30 秒看 README 首屏，后 60 秒决定点不点第二个文件。
> 所以作品化的目标不是「资料多」，是**让价值在最前面被看见，且经得起抽查**。

### 4.1 三条整理原则

| 原则 | 反例（会扣分） | 本案做法 |
|---|---|---|
| **根目录只留门面** | 根目录躺着 20 个 md、几个 `.log`、一份 `备份.db` | 根目录只有 README / LICENSE / CHANGELOG / CONTRIBUTING / SECURITY + 目录 |
| **一份事实只有一个源** | 页面数在 4 篇文档里 4 个值 | 数字由代码算出，文档守卫校验；指标由基线文件唯一提供 |
| **生成物与源码分开** | 手改打包产物，改完两边不一致 | `平台原型/index.html`、`docs/html/*` 全部标记 `linguist-generated`，GitHub 自动折叠 diff |

### 4.2 仓库结构（本项目实际结构，可直接套用）

```
.
├── README.md                  ← 首屏：一句话定位 + 在线 demo + 截图 + 能力表 + 实测数字

### 4.6 上传步骤（本项目实际执行过的路径）

```bash
# ① 先做「可上传」体检：确认没有 PII / 密钥 / 大文件混进来
cat .gitignore                      # 库文件、.env、密钥、备份、日志、临时脚本必须都在里面
git status --short                  # 未跟踪文件逐个确认
git grep -nIE 'C:[\\/]Users|密码|api[_-]?key|sk-[A-Za-z0-9]{16,}'  # 本机路径与凭证零命中

# ② 提交（提交信息写"改了什么 + 为什么"，别写 "update"）
git add -A && git commit -F _msg.txt

# ③ 推送
git push -u origin main

# ④ 打开 GitHub Pages（零安装 demo）
#    Settings → Pages → Source = GitHub Actions（或直接 POST /repos/{owner}/{repo}/pages）
```

**受限网络下的三条通道**（本项目踩过 5 次，结论已写成技能 `github-upload-restricted-network`）：
① **先量代理是否整体挂掉**（`env | grep -i proxy` + `git ls-remote` 双向测），别把「单次失败」当「通道不通」；
② 代理不可用时 `env -u https_proxy -u http_proxy … git push` 直连反而通；
③ `git credential fill` 在网络不可达时会**挂起而不是报错**（表现为脚本卡死、日志空白），
改从系统凭据管理器直读令牌（`references/read-gcm-token.ps1`），用 `GIT_CONFIG_*` 环境变量传鉴权头（不进 argv）。

## 附 · 术语与口径速查

| 术语 | 口径 |
|---|---|
| 四边界 | Agent 决策 / Workflow 执行 / Rules 约束 / Human 治理 |
| 漏筛率 | 人工认为该通过（strong/ok）却被 AI 判 no 的比例 —— **安全红线，必须为 0** |
| 误筛率 | 人工认为该淘汰（no）却被 AI 判 strong/ok 的比例 —— 成本问题（多进一轮人工） |
| Wilson 区间 | 小样本比例的正确置信区间；30 例下 96.7% 的 95% CI 是 [83.3%, 99.4%] |
| 空断言 | 断言存在但没有真正观测到目标行为（破坏源码仍绿）—— **比没有断言更危险** |
| 反向验证 | 故意把 bug 放回去，确认断言变红；不红说明这条断言没有判别力 |
| preflight | 只读上线自检，退出码 0 才允许把链接发出去 |
