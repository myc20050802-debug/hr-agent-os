# HR-Agent OS · 从 PoC 到企业级的差距清单

> **这份文档回答一个问题：这个已经能跑的产品，离「企业级」还差什么，以及先补哪一件。**
> 写作口径：第一人称述职体，可直接用于面试陈述、项目答辩、架构评审。
> **事实纪律**：所有「现状」都标注了可核验的出处（文件 / 行号 / 实测数据）；所有「企业级要求」是行业通行标准，不含本产品专属假设。本文**不含任何未实测的性能或规模数字**。

---

## 结论先行（30 秒）

> 「我的判断是：**这个项目不缺数据库，也不缺数据。** 它已经有 13 张表、真写库、审计链、审批闸门。
> 缺的是**「可信」**——可信身份、可信权限、可信审计、可信恢复。
> 所以下一步的第一优先级**不是灌更多数据**，而是把 `x-user` 请求头换成正经验签的会话。
> **因为没有可信身份，审计链再完整也证不了「是谁做的」。**」

**一句话定位**：企业级 ≠ 数据多；企业级 = **可信 + 可运维 + 可审计 + 可扩展**。

## 一、先纠正一个误解：数据库不是缺的

很多人在这个阶段的第一反应是「要先建库、灌数据」。但实测下来，这一步**已经过了**。

**实测**（`server/hr_agent.db`，SQLite，159,744 bytes，13 张表）：

| 表 | 行数 | 作用 |
|---|---|---|
| `tenants` | 1 | 租户（含 `plan` / `region` 字段） |
| `users` | 5 | 用户 + 角色（hrd / recruiter / hrbp / employee） |
| `jobs` | 11 | 岗位（8 行业 / 11 岗位，含 JD / 关键词 / 编制 / 薪资） |
| `candidates` | 40 | 候选人（含 PII 字段、`consent_given`、`retain_until`） |
| `kb_documents` / `kb_chunks` | 5 / 9 | 知识库（RAG 检索用） |
| `audit_logs` | 5 | 审计链（**只插入、不更新**） |
| `agent_tasks` / `tool_calls` / `approvals` | 0 / 0 / 0 | Agent 任务 / 工具调用 / 审批闸门 |
| `leave_balance` / `unanswered_questions` | 2 / 0 | 假期余额 / 未答问题池 |

**而且它是真在写的**（不是只读的假数据）：

| 行为 | 落库位置 | 出处 |
|---|---|---|
| 跑一次筛选 Agent | `agent_tasks` + `tool_calls`，含 token 成本 | `engine.js` `runScreening()` |
| 高风险动作（ATS 写回） | 进 `approvals` 排队，**等人批才执行** | `engine.js` 闸门 |
| 审批驳回 | **服务端硬校验**必须填原因，否则 400 | `server.js:122` |
| 越权导出 | 写 `audit_logs`（result=blocked）并返回 403 | `server.js:146-151` |
| 人工推翻 AI 结论 | 推翻原因入库，进优化数据集 | `server.js:128-137` |

种子数据也不是写死的假数据——是**确定性随机生成**（`db.js:140` `rng(seedStr)`，同一 `job.id` 每次生成同一批人），所以可复现、可回归。

> **结论：**「建库、存数据」不是待办项。把它当成待办项，是把「工程问题」误判成「数据问题」。

## 二、企业级的判据

我给「企业级」定的四条判据（这也是企业采购时会逐条问的）：

| 判据 | 要回答的问题 | 反例（做到功能≠企业级） |
|---|---|---|
| **可信** | 数据给谁看、谁能改，是不是**可证明**的？ | 有登录页，但身份能被客户端指定 |
| **可运维** | 数据丢了能不能恢复？出问题能不能定位？ | 能跑，但无备份、无监控、无告警 |
| **可审计** | 事后能不能说清「谁、在什么时候、做了什么」？ | 有日志，但日志本身可被篡改 |
| **可扩展** | 从 1 个客户到 100 个客户，架构要不要推倒？ | 单机单库，多租户靠「约定」不靠约束 |

## 三、差距清单（按优先级）

### P0-1 · 身份认证 —— 最大的缺口

**现状（可核验）**

```js
// server/server.js:39
const DEMO_USER = req => (req.headers['x-user'] || 'U-001');   // 演示态：当前登录人由请求头指定
```

**当前登录人由请求头决定。** 任何人发一句 `X-User: U-001`，就变成了 HRD 李静，能看到全公司候选人。

全库检索确认：**没有任何认证逻辑**——没有登录接口、没有密码、没有会话、没有 token 校验。唯一出现 `Authorization` 的地方是 `engine.js:48`，那是**调用外部 LLM 时带的 Bearer**，与用户认证无关。

**为什么它是 P0**：现有全部「企业级感」——审计链、审批闸门、403 拦越权——**都建立在这个可伪造的身份之上**。身份是假的，审计就证明不了任何事。

**企业级要求**
- 接入企业身份源（企业微信 / 钉钉 / LDAP / OIDC），**不自己存密码**
- 服务端签发会话（HttpOnly + Secure + SameSite Cookie，或短期 JWT）
- 身份**只能由服务端从会话里取**，客户端不可指定
- 会话可失效（登出 / 权限变更即踢下线）

**改法（最小实现）**
1. 加 `POST /api/auth/login`：接企微/钉钉回调或 OIDC 授权码
2. 服务端签发 HMAC 签名 Cookie（密钥放环境变量，不进代码库）
3. 加一个中间件：`const uid = sessionOf(req)`，把全库 `DEMO_USER(req)` 替换为它
4. 删掉对 `x-user` 请求头的信任

**验收口径**
- 伪造 `X-User: U-001` **不再生效**（回归用例：无 Cookie 时所有写接口 401）
- 审计日志里的 `actor_id` 来自会话，不由请求方指定
- 登出后旧 Cookie 立即失效

### P0-2 · 权限（授权）

**现状**：`users` 表有 `role` 字段，产品里也有 403 演示页，但**没有真正的权限校验**——403 是硬编码的演示路径（`server.js:146-151`，只有员工导出全公司数据这一条被拦）。

**企业级要求**，三层都要：

| 层级 | 要控制什么 | 例子 |
|---|---|---|
| **功能级（RBAC）** | 能不能做这个动作 | 只有 `hrd` 能改薪资区间 |
| **行级** | 能看到哪些行的数据 | HRBP 只能看自己支持的部门 |
| **字段级** | 能看到哪些字段 | 普通 HR 看不到身份证号 / 薪资 |

**改法**
1. 定义权限矩阵（角色 × 动作），落成配置表，**不散落在代码里**
2. 所有读接口加行级过滤：`WHERE tenant_id = ? AND dept_path LIKE ?`
3. 敏感字段在**查询层就剔除**（而不是前端隐藏）——这条产品里已做对一半：`db.js:40` 注释写明 PII「存储保留，但送入打分前物理剔除」
4. 把演示用的 403 升级成**通用拦截中间件**

**验收口径**
- 权限矩阵每条有对应回归用例
- 用 employee 身份调任意管理接口 → 403 + 写审计
- 行级：HRBP A 查不到 HRBP B 部门的候选人

### P1-1 · 数据库形态

**现状**：SQLite（`node:sqlite` 的 `DatabaseSync`），**单文件、单写入者**。

**问题**：两个 HR 同时点「运行筛选 Agent」，第二个会遇到 `database is locked`。这不是 bug，是 SQLite 的架构特性——它适合单机/嵌入式，不适合多用户并发写。

**企业级要求**：PostgreSQL（或 MySQL）+ 连接池 + 备份 + 只读副本。

**好消息**：迁移路径是现成的。`db.js:1-8` 注释已写明「表结构与 `docs/02_搭建实操教程.md` 第 2 步的 PostgreSQL 版本**同源**，字段做了 SQLite 适配（JSONB → TEXT，UUID → TEXT）」。也就是说**表结构不用重新设计，只需把适配层换回去**：

| SQLite 写法 | PostgreSQL 写法 |
|---|---|
| `TEXT` 存 JSON | `JSONB` |
| `TEXT` 存 ID | `UUID` |
| `datetime('now')` | `now()` |
| `INTEGER 0/1` 布尔 | `BOOLEAN` |

**改法**：加一层 `db.js` 的 PG 适配实现（保持同名导出），SQL 用参数化占位符差异抹平（`?` → `$1`）。

**验收口径**
- 双模式回归脚本在 PG 上全绿（23 页 + 16 项）
- 并发压测：10 个并发筛选请求，0 个 `locked` 错误
- 备份恢复演练：破坏数据后能恢复到上一备份点

### P1-2 · 多租户隔离

**现状**：`tenants` 表已建（`db.js:17`），但**只有 1 行**，且**多数查询没带 `tenant_id` 过滤**。

可核验的例子：
- `server.js:150` —— `SELECT COUNT(*) FROM users`（无租户条件）
- `server.js:67` —— `/api/jobs` 的查询 `SELECT * FROM jobs ORDER BY ...`（无租户条件）

**风险**：真做 SaaS，**任何一个漏掉租户条件的查询 = 客户之间的数据泄漏**。这是企业采购的必查项，也是 SaaS 最典型的事故来源。

**企业级要求**
- 查询层强制租户过滤（ORM 全局 Scope / 数据库行级安全 RLS）
- 跨租户查询必须**显式声明**并留审计
- 租户隔离要有**自动化测试**（用 A 租户身份去查 B 租户数据，必须查不到）

**改法**：推荐用 PostgreSQL 的 **RLS（Row Level Security）**——把隔离约束下沉到数据库，而不是靠每个开发者「记得加 WHERE」。这是「靠约束不靠约定」的典型做法。

**验收口径**
- 隔离测试：每个读接口都有「A 租户查 B 租户」的负向用例
- 审计：跨租户访问全部落 `audit_logs`

### P1-3 · 数据治理（HR 数据是敏感个人信息）

**现状**：**字段设计是对的，但逻辑没实现**。

表里已经有这两个字段（说明设计时想到了）：
- `db.js:46` —— `consent_given INTEGER DEFAULT 1`（告知同意）
- `db.js:46` —— `retain_until TEXT`（留存期限）

但代码里**没有读取/执行它们的逻辑**：没有到期自动清理、没有 PII 加密、没有数据主体权利接口。

**企业级要求**（对齐《个人信息保护法》）

| 要求 | 现状 | 要做 |
|---|---|---|
| 告知同意 | 有字段，默认 1 | 记录同意来源、时间、版本；未同意不进入处理 |
| 最小必要 | 已做（打分前剔除 PII） | 保持，并扩展到导出/日志 |
| 留存期限 | 有字段，无逻辑 | 定时任务按 `retain_until` 清理 |
| 数据主体权利 | 无 | 提供查询 / 更正 / 删除接口 |
| 存储安全 | 明文 | 敏感字段加密（含备份加密） |

**改法**：先在 `candidates` 上做闭环——同意校验 + 到期清理（一个定时任务）+ 删除接口。

**验收口径**
- 到期的候选人被自动清理，且清理本身留审计
- 未同意的候选人不进入打分链路
- 删除接口生效，且删除动作不可逆但可追溯（留审计摘要，不留 PII）

### P2-1 · 数据库迁移

**现状**：手写 `ALTER TABLE`（`db.js:90-104` `migrate()`）。

```js
const add = (name, ddl) => { if (!cols.includes(name)) db.exec(`ALTER TABLE jobs ADD COLUMN ${ddl}`); };
```

**问题**：没有版本号、没有回滚、没有顺序保证。多人协作时会冲突。

**企业级要求**：版本化迁移工具（Prisma Migrate / Flyway / Alembic），每个变更是一个**有序、可追溯、可回滚**的文件。

**验收口径**：空库能从 0 跑到最新；能从任意历史版本升到最新；迁移有 dry-run。

### P2-2 · 可运维

**现状**（诚实盘点，不夸大）：

| 项 | 现状 | 说明 |
|---|---|---|
| 健康检查 | ✅ 有 | `server.js:51` `/api/health` |
| 请求体大小限制 | ✅ 有 | `server.js:36` 上限 1MB |
| 路径穿越防护 | ✅ 有 | `server.js:163` `startsWith(STATIC_ROOT)` 否则 403 |
| 备份 | ❌ 无 | 库文件被删即全丢 |
| 监控 / 指标 | ❌ 无 | 无 QPS、延迟、错误率采集 |
| 告警 | ❌ 无 | 出错只在控制台打印 |
| 限流 | ❌ 无 | 单机可被刷 |
| 优雅关闭 | ❌ 无 | 重启会中断在途请求 |
| 结构化日志 | ❌ 无 | `console.log`，不可检索 |

**企业级要求**：结构化日志（JSON）+ 指标（Prometheus 口径）+ 告警 + 每日备份 + 限流 + 优雅关闭（`SIGTERM` 处理）。

**验收口径**：能回答「过去 24 小时失败率多少、最慢的接口是哪个」。

### P2-3 · 模型层

**现状**：规则模式运行（`/api/health` 实测 `mode: "rule"`）。`LLM_API_URL` / `LLM_API_KEY` / `LLM_MODEL` 三个环境变量已预留，`engine.js:44-52` 有调用骨架，但**未接入**。

需要说明的是，骨架里**已经做对了两件事**（不是全空白）：

```js
// engine.js:44-52
if (!url || !key) return null;                       // 无配置 → 规则模式（降级）
signal: AbortSignal.timeout(20000)                   // 调用有超时
...
if (!r.ok) return null;                              // 失败 → 返回 null 由上层兜底
```

**已有**：超时（20s）、失败降级（返回 null 让调用方回退到规则路径）、可换模型（走环境变量，不写死）。

**接入后仍必须要补的**：

| 项 | 为什么 |
|---|---|
| 模型网关（多供应商可切） | 私有化客户要求换模型；现在是单 URL，缺供应商级抽象 |
| 重试 + 退避 | 现在一次失败即降级，没有重试；限流抖动会直接掉到规则路径 |
| 成本核算 | `agent_tasks.token_cost` 字段已建，需真实累加并对账 |
| 输出审计 | 模型输出要留痕，否则出问题无法复盘 |
| 提示词版本化 | Prompt 改了要能回归 |

**验收口径**：拔掉网络，产品降级到规则模式而不是报错；每次调用都有 token 记账；换供应商只改配置不改代码。

## 四、实施顺序与理由

| 阶段 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **① 认证 + 权限** | SSO + 会话验签 + RBAC/行级/字段级 | **没有它，数据灌到 10 万条也只是一个「更多数据的裸奔 demo」。** 且它不动数据层，改动可控 |
| **② PostgreSQL + 迁移 + 备份** | 换库、版本化迁移、每日备份、恢复演练 | 解决并发写；同时给数据兜底。表结构同源，成本比想象低 |
| **③ 多租户 + 数据治理** | RLS 强制隔离、PII 加密、留存清理 | 到这一步才敢卖给第二个客户 |
| **④ 规模化** | 对象存储（简历 PDF）、监控告警、限流、模型网关 | 性能与运营问题，最后一个做 |

**为什么认证排在换库前面？** 两个原因：
1. **风险**：换库是高风险动作（数据迁移可能丢数据），认证是叠加式的（不改数据结构）
2. **门槛**：换库之后如果身份还能伪造，你依然是「一个有更好数据库的裸奔 demo」——**门槛没有降低**

## 五、如果只做一件事

**做认证。**

因为它是**唯一一个「不做就不成立」的项**——其余所有项（审计链、审批闸门、403、数据治理）的价值，都建立在「身份是真的」这个前提上。

一个具体的最小闭环：**删掉对 `x-user` 请求头的信任**（这一步甚至不需要接 SSO，先用服务端签发的最小会话即可），然后跑一遍回归验证：

```
回归用例：无有效会话时
  - POST /api/agent/screening/run   → 401
  - POST /api/jobs                  → 401
  - POST /api/employees/export      → 401（而非 403）
  - audit_logs 中 actor_id 不再出现 'U-001'（除非真登录为 U-001）
```

## 六、面试口径（可直接背）

**问：「你这个项目离企业级还差什么？」**

> 「差的不是数据库和数据——那两块我已经是真跑的了：13 张表、真写库、审计只插入不更新、高风险动作真的挂在审批闸门后面。
> 差的是**可信**。具体说，我的身份认证现在是这样的（`server.js:39`）：当前登录人由请求头 `x-user` 决定。也就是说任何人加一个请求头就能变成 HRD。
> 所以我下一步的第一优先级不是扩数据，是把请求头换成正经验签的会话——**因为没有可信身份，审计链再完整也证不了「是谁做的」**，这条链的价值会归零。
> 之后才是换 PostgreSQL 解决并发写（现在两人同时点筛选会锁库），再做多租户隔离和数据治理。
> 顺序上我把认证排在换库前面，是因为换库是高风险的数据迁移，而认证是纯叠加；而且换完库如果身份还能伪造，我的门槛其实一点没降低。」

**为什么这段话值钱**：它证明你能**分清「功能」和「工程」**——这是 AI 产品经理和「会做 demo 的人」之间最本质的差别。

## 附录 A · 已经做对的部分（不该被「企业级」否定）

做差距分析时容易全盘否定自己，但这些是**真正的加分项**，评审时要主动说：

| 已做对的 | 出处 | 为什么这是对的 |
|---|---|---|
| 审计日志**只插入不更新** | `db.js:77-82` | 审计链不可篡改是合规底线 |
| 高风险动作**必须人工审批**才执行 | `approvals` 表 + `engine.js` 闸门 | 责任不可转移，产品形态由责任设计决定 |
| 驳回**必须填原因**（服务端硬校验） | `server.js:122` | 把「数据飞轮」变成强制流程，而非靠自觉 |
| 删岗位**不物理删除**，有候选人则转「已关闭」 | `engine.js` `deleteJob` | 保护审计链的完整性 |
| PII **在打分前物理剔除**，而非前端隐藏 | `engine.js:117-120` + `db.js:40` 注释 | 前端隐藏 = 没有防护；查询层不 SELECT 才是 |
| 合规规则**带法条依据**（歧视 11 + 违法 9） | 规则表 | 能向法务举证，不是「模型觉得不行」 |
| 种子数据**确定性可复现** | `db.js:140` `rng(seed)` | 可回归、可演示、可复现缺陷 |
| 岗位库**驱动单一数据链**，不硬编码 | `jobs` 表 → 关键词 → 打分 → JD | 岗位是 HR 业务里变化最快的对象 |
| 路径穿越防护 | `server.js:163` | 零依赖手写 HTTP 也没漏这个 |
