# JD 粘贴解析口径 v17 修复说明

> **版本**：`REQ_LIB_VER` 16 → **17**　|　**修复时间**：2026-10-09（北京时间）
> **触发人**：产品负责人（粘贴一份在招 JD 后，生成结果的「岗位职责」栏出现明显语序问题）
> **改动文件**：`shared/req-lib.js`（唯一改动点 —— 前后端共用同一份解析库，改一处全端生效）

---

## 1 · 现象

把一份正在招聘的「AI 产品经理」JD 整段粘贴进 JD 工作台后，生成的**岗位职责**栏长这样：

```
1.1.跟随业务团队对接B端客户，参与业务访谈，理解客户业务流程，识别显性需求，主动挖掘潜在业务痛
2.点；2.结合大模型应用能力，判断AI是否可以解决客户痛点，设计初步落地思路，预判方案实施效果与边界；
  3.将客户业务痛点转化为AI应用需求……5.轮岗学习业务、产品、AI应用相关知识，成长为懂客户业务、
  懂AI落地的复合型产品人才。任职要求：1.学历背景：211或985本科及以上……3.AI认知：了解大模型等
  AI应用的能力与局限，理解AI应用落地基本逻辑
3.4.产品思维：具备良好的需求拆解、归纳抽象能力，能够把业务问题转化为可落地方案；5.软性素质：
  学习能力强，自驱力足，善于跨团队协作，能接受业务外出客户沟通
```

四种症状同框出现：**编号重复**、**词被劈开**（「业务痛」与「点」分处两行）、
**多条挤成一坨**、**任职要求混在职责里**。

**先说结论：这不是输入文本写得差，是解析器有四处分栏/断行处理没做。** 原始 JD 本身是合规的：
它是一份「段落型」写法 —— 条目用「；2.」「；3.」在段内相连，中间被排版硬换行切过，
且把「任职要求：」写在了职责段的末尾。这四点都需要解析器接住，而不是原样透传。

---

## 2 · 四处根因

四处都在 `parseReqText()`，症状不同，根因是同一类：**只处理了「行首 + 中文编号符」这一种规范写法**。

| # | 症状 | 根因 |
|:-:|---|---|
| **D1** | 正文里留着「1.跟随业务团队…」 | `RE_LI_NUM` 的西文句点分支写作 `\d{1,2}\s*\.\s+` —— **强制要求点号后带空格**。中文 JD 写「1.跟随」几乎不留空格，正则不命中，序号原样留在正文里 |
| **D2** | 「…潜在业务痛」与「点；2.…」变成两条 | 断行还原只有两条判据：①上一行以句中标点收尾（`，,、；;：:`）②上一行是带列表符号的项。原始行以汉字「痛」收尾、又没有列表符号，两条都不满足 |
| **D3** | 5 条职责连 6 条要求整段粘成一条 | 行内切分只认 `；` + 数字 + `、/）`（中文编号符），**不认西文句点**，于是「；2.」「；3.」全不切 |
| **D4** | 「任职要求：1.学历背景…」留在职责栏 | `RE_HEAD_LEAD` 是 `^` 行首匹配，而标签写在**段落中间**（「…复合型产品人才。任职要求：」）；更麻烦的是它后面**换行**的内容（「4.产品思维」「5.软性素质」）也跟着留在职责栏 |

> D4 是铁律 12「职责栏不许静默丢内容」的**反向症状**：这次不是丢内容，是职责栏把要求栏的内容吞了 ——
> 结果是要求栏空着、职责栏肿着，比丢内容更难被发现（内容确实一条没丢，只是全部站错了队）。

## 3 · 修法

### D1 · 序号剥离：把「必须有空格」换成否定前瞻

```js
// 旧：\d{1,2}\s*\.\s+      —— 「1.跟随」剥不掉
// 新：\d{1,2}\s*\.(?!\d)\s*
```

防误伤不再靠空格，而靠**点号后不能是数字**：`1.5 年经验` 点号后是 `5` → 不剥；
`1.跟随业务` 点号后是汉字 → 剥。

> ⚠️ 这里有个**必须避免的重复实现**：行内切分原本另写了一份编号剥离正则。
> 两份并存时，改一份、另一份会兜住，反向验证抓不到退化（实测：把 `RE_LI_NUM` 收回旧写法，断言照样全绿）。
> 现在行内切分直接复用 `RE_LI_NUM`：`new RegExp('[；;]\\s*(?=' + RE_LI_NUM.source.slice(1) + ')')`。

### D2 · 断行还原：新增第三条判据

```js
const RE_END_CN = /[\u4e00-\u9fa5]$/;              // 上一行以汉字收尾
const cnCont = !!cur && !marked && RE_END_CN.test(cur.text)
  && /^[^\s]{0,2}[。；，、：]/.test(s)               // 下一行以「残片 + 标点」开头
  && !RE_ITEM_START.test(s);                       // 且不像「负责 / 配合 / 了解」这类新条目开头
```

三条合取：中文句子的结束必有终止标点，没有就是话没说完；下一行以「点；」这种**残片 + 标点**开头，
是尾巴掉下来的直接证据；起始词表挡住真正的新条目。

合并时**一个分隔符都不插** —— 否则「…业务痛」+「点；」会被拼成「…业务痛，点；」，
把「断行错误」升级成「标点错误」，越修越像病句。

> ⚠️ **踩过的坑**：第一版判据是「上一行够长（≥12 字）+ 以汉字收尾」，结果 5 条既有断言同时变红 ——
> 表单式「一行一条」的条目（「3 年以上 AI 产品经验」「执行采购订单跟催与交期管理」）同样长、同样以汉字收尾，
> 被两两合并。这条判据破坏了铁律 8 的「一行一条 → 提交 → 再载入往返无损」。收紧后才同时成立。

### D3 · 行内切分：认西文句点

复用 D1 修好的编号正则做切点：`；1、` 与 `；1.` 现在都能切。
**没加宽的部分**：没有编号的裸分号一律不切 —— 铁律 8 的边界仍然成立。

### D4 · 行内分栏：切点处一分为二，并把 key 交给后续行

```js
for (;;) {
  const mIn = cur && cur.text ? cur.text.match(RE_INLINE_HEAD) : null;   // 「。任职要求：」
  if (!mIn) break;
  const before = cur.text.slice(0, mIn.index + 1).replace(/[。；;]+$/, '').trim();
  const after  = cur.text.slice(mIn.index + mIn[0].length).trim();
  if (before) b[key].push(before);        // 前半留在原桶（职责）
  key = keyOf(mIn[1]);                    // 后半改派（要求）
  cur = after ? { text: after, marked: !!cur.marked } : null;
}
```

两个要点，缺一不可：

1. **必须切内容，不能只改 key** —— `flush()` 用的是**当时**的 key，而 `cur` 可能已经累积了很多行；
   只改 key 会把整段职责一起搬进要求栏。
2. **必须把 key 状态交给后续行** —— 否则标签**之后**换行的「4.产品思维」「5.软性素质」仍会留在职责栏
   （它们不在同一行，靠的是 key 状态而不是行内切分）。

`RE_INLINE_HEAD` 由 `RE_HEAD_ANY` 的词表拼出，并要求标签**前面有句末标点**，避免误切正文里的同名词。

## 5 · 已知边界（没解决的）

原始 JD 里有一处**自身缺标点**：`…计算机、软件工程、金融专业优先2.业务沟通能力：…`
——「优先」与「2.」之间没有分号。解析器现在只在**有分隔符**的地方切，所以这一条会把
「2.业务沟通能力」吞进「学历背景」那条里。

**没有为此加规则**：仅凭「汉字 + N. + 汉字」无法区分「编号」与「版本号 / 数值」
（如「提升3.倍」「第2.章」），放宽切分点会引入误切，收益不足以抵掉风险。
这类缺失标点的输入，正确做法是补标点后重粘，而不是让解析器猜。
