JD 工作台 · 「任职要求 / 加分项」已填内容润色口径（v12）

平台：HR-Agent OS · 本地全栈 PoC（仓库根目录） 场景：招聘 Agent · JD 工作台 → 「生成 JD 并做合规扫描」 需求提出：2026-09-29（北京时间） 词库版本：REQ_LIB_VER 11 → 12（老 JD 启动时自动重算）

一、需求原文

在 JD 工作台中生成岗位 JD 时，请按以下规则处理「任职要求」和「加分项」两栏内容： 若「任职要求」栏已有内容，则在保留其核心信息的基础上进一步丰富和润色生成 JD； 若该栏为空，则按原有默认逻辑生成。若「加分项」栏已有内容，则依据这些内容进行 美化和完善后再生成；若为空，则按原有默认逻辑处理。请确保最终生成的 JD 语言流畅、 表述专业，并忠实于已有的输入内容，不要凭空添加未提供的信息。

二、差额：缺的是「润色」，不是「丰富」

改之前先把现状摊开看，避免改错地方：

栏目改动前实际行为与需求的差额
任职要求（已填）原样保留、按六维度归位；缺失维度用职能族素材补齐「丰富」已有，「润色」缺失
任职要求（空）按职能族生成完整六维度一致，无需改
加分项（已填）已填优先，≥3 条不再叠加模板原样输出，未「美化完善」
加分项（空）职能族加分项补齐到 4 条一致，仅统一句式

结论：要补的是「已填内容的书面化改写」这一层，其余逻辑不动。

三、实现分三层

第 1 层 · 规则润色（默认，离线可用）

落在 shared/req-lib.js 新增的第八节，前后端共用同一份 —— 后端 server/engine.js

与离线原型 平台原型/src/agent.js 都调 ReqLib.polishMustItem / polishNiceItem。

零依赖、确定性、可回归。

三条硬约束写进了代码注释：

  1. 只改表述，不改语义，绝不新增 HR 没提供的事实；
  2. 全部白名单：口语词命中才替换，不命中一律原样透传（宁可少润色，不可改跑偏）；
  3. 幂等：同一段文字润色两次结果一致（runJD → buildJD 会连着展开两次）。

第 2 层 · 结构锁（防止「润色」变成「创作」）

润色环节不许增删条目。维度名、维度顺序、每维条目数、条目顺序，全部要求与规则层产物

逐条对齐；对不上就整单作废。这条锁是刻意加的：只要给「润色」留出走样空间，它就会

开始替你「补两条更专业的」—— 那就违反了「不要凭空添加未提供的信息」。

第 3 层 · LLM 增强（可选，配了模型才走）

条件行为
未配 LLM_API_URL / LLM_API_KEY纯规则层产物，离线原型与本地 PoC 照旧可用
配了模型 + HR 填过内容规则层产物作为底稿交模型做流畅度加工，返回结果过结构校验
配了模型但返回结构对不上整单作废，退回规则层结果，并在执行轨迹里写明原因

模型用量一律取真实 usage，不编造 token 数（沿用项目既有约定：用量要么是真的，要么不显示）。

  • 句尾删语气词：吧 哦 啦 哈 嘛 哟 哒 呢（仅当删完还剩得下一个词）

六、顺手修掉的两个真 bug

这两个都不是润色引入的，是被新用例逼出来的旧账：

#问题根因修法
1硬性条件里出现两条一模一样的要求expandRequirements 被 runJD → buildJD 连着调用两次；「有 1–2 段对口实习经历者优先」在二次展开时匹配不上 REQ_EXP，落进专业技能桶，而判重只扫 s2 → 又补一遍判重改为扫全部已填内容；REQ_EXP 补上「实习」（它本来就属于工作经验维度）
2JD 正文的加分项与存库 nice_have 对不上buildJD 二次展开时把模板补位项当成「HR 新填的内容」又润了一遍，正文带「者优先」而库里不带传入 dims 时（即已展开产物）加分项直接取传进来的那份；同时统一由一道工序美化，避免同一岗位在新老数据上出现两种排版
关于「加分项栏为空」：模板的选取逻辑（选哪几条、补到几条）一字未动， 只是渲染时统一成「…者优先」的对外句式。这么做是为了消除一个真实的不一致 —— 老岗位经版本自愈重算时，库里的 nice_have 已分不清哪条是 HR 写的、哪条是模板补的， 若只美化「用户那几条」，同一个岗位换次版本就换一副面孔。 若你希望留空时保持模板原样（不带「者优先」），说一声，改一行即可。

新增的 6b 节用行为断言锁死三件事：

① 口语被书面化；② 核心信息一字不丢、不新增（技术栈词不得混入加分项）；

③ 二次展开幂等（不叠「者优先者优先」、硬性条件条数与顺序不变）。

断言刻意不写死具体文案 —— 将来扩白名单时不会因为换了个词就误报。

九、边界（还没做）

  • 白名单是保守的：只收「命中后一定更专业、且语义等价」的词。

没见过的口语写法会原样透传，不会丢字 —— 宁可少润色，不可改跑偏。

  • 不做中英之间加空格：那会改动一堆既有断言的字符串，收益低于风险，这轮不做。
  • 软技能段可能出现同义重复：HR 写的「表达清晰」与模板句里的「表达清晰」会同时出现。

属模板与用户内容的既有重叠，本轮未处理。

  • LLM 层在当前环境未实跑（本机未配 LLM_API_URL），只做了结构校验的代码路径与

降级分支；实跑证据待配模型后补。
