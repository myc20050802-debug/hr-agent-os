## 一、架构目标与约束

### 1.1 架构目标（按优先级）

1. **可信**：身份不可伪造、权限不可绕过、审计不可篡改。
2. **可控**：凡涉及硬判断（年限/学历/合规），必须由确定性代码执行且**可复现**。
3. **可讲**：每一层有明确职责边界，每个关键决策有对标依据与取舍说明。
4. **可演**：断网可演示，单文件可分发，数据不出本机。
5. **可演进**：不追求一步到位的生产级规模，但**不允许出现无法回退的设计**。

### 1.2 硬约束

| 约束 | 来源 | 对架构的影响 |
|---|---|---|
| 简历属**敏感个人信息**（PIPL） | 法律 | 字段级加密、留存期清理、删除权、演示数据全合成 |
| 招聘决策**不得有歧视** | 劳动法/就业促进法 | 受保护字段物理剔除；合规扫描带法条依据 |
| **单人维护** | 你的真实约束 | 组件数最少、单语言优先、零依赖演示包必须保留 |
| 目标形态为**单租户私有化** | 你已确认 | 不做租户管理 UI；但**所有查询仍带 `tenant_id`**（低成本预留） |
| 身份为**自建账号 + RBAC** | 你已确认 | 自建会话/令牌；不引入 SSO 中间件 |

## 三、目标架构：分层设计（② 设计目标）

### 3.1 分层总览

**分层原则：按「变化频率」切层。** 变化最慢的在底层（基础设施），变化最快的在上层（业务界面）；**模型、检索、规则三者变化频率完全不同，必须分属不同能力**，不能混成一个「AI 模块」。

```
┌───────────────────────────────────────────────────────────────────────┐
│ L0 接入层  Access                                                     │
│   反向代理 / TLS · 静态资源 · 全局限流 · 会话解析 · CORS · 请求日志      │
├───────────────────────────────────────────────────────────────────────┤
│ L1 应用层  Application                                                │
│   REST/JSON API · DTO 校验(Zod) · 鉴权守卫 · 错误契约 · SSE 流式输出    │
│   ── 只做「协议与编排」，不含业务规则 ──                                │
├───────────────────────────────────────────────────────────────────────┤
│ L2 领域层  Domain                                                     │
│   岗位 · 候选人 · 审批 · 审计 · 员工自助 · 授权治理(PIPL)               │
│   领域服务 + 状态机 + 仓储接口（不依赖具体数据库）                       │
├───────────────────────────────────────────────────────────────────────┤
│ L3 能力层  Capability   ← 本产品的差异化全部在这一层                    │
│  ┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐        │
│  │ 规则引擎    │ │ AI 编排    │ │ 模型网关    │ │ 检索/RAG   │        │
│  │ 确定性      │ │ Agent 计划 │ │ 适配器      │ │ 切片/向量   │        │
│  │ 门槛/打分   │ │ 工具调用   │ │ 重试/降级   │ │ 混合检索    │        │
│  │ JD 生成     │ │ 人工闸门   │ │ 限流/成本   │ │ 重排/引用   │        │
│  │ 合规扫描    │ │ 轨迹记录   │ │ 输出审计    │ │            │        │
│  └────────────┘ └────────────┘ └────────────┘ └────────────┘        │
│  ┌────────────┐                                                      │
│  │ 文档处理    │  PDF/DOCX 抽取 · OCR 兜底 · 结构化字段映射            │
│  └────────────┘                                                      │
├───────────────────────────────────────────────────────────────────────┤
│ L4 数据层  Data                                                       │
│   PostgreSQL（业务）· pgvector（向量）· 对象存储（简历原件）             │
│   Redis（会话/缓存/队列）· 审计库（append-only）                        │
├───────────────────────────────────────────────────────────────────────┤
│ L5 基础设施层  Infra                                                  │
│   容器化 · CI/CD · 配置与密钥 · 备份恢复 · 日志/指标/追踪               │
└───────────────────────────────────────────────────────────────────────┘

横切关注点（贯穿所有层）
  安全：认证 / 授权 / 传输与静态加密 / 字段级脱敏
  合规：授权留痕 / 留存期 / 删除权 / 合规扫描
  可观测：结构化日志 / 指标 / 链路追踪 / Agent 轨迹回放
  工程：幂等键 / 事务边界 / 配置开关 / 特性降级
```

### 3.2 各层职责与关键接口

| 层 | 职责 | 关键接口（示意） | 不该做的事 |
|---|---|---|---|
| **L0 接入** | TLS、限流、静态资源、会话解析 | — | 不写业务逻辑 |
| **L1 应用** | 协议转换、入参校验、鉴权、错误契约 | `POST /api/screenings`、`GET /api/jobs` | 不直接访问数据库 |
| **L2 领域** | 业务规则、状态机、事务边界 | `ScreeningService.run()`、`ApprovalService.approve()` | 不关心 HTTP、不关心用哪个模型 |
| **L3 能力** | 规则 / 编排 / 模型 / 检索 / 文档 | `RuleEngine.gate()`、`Agent.run()`、`Llm.complete()`、`Retriever.search()` | **不含具体业务语义**（岗位、候选人概念不进来） |
| **L4 数据** | 持久化、检索、缓存 | `JobRepo`、`AuditRepo`、`VectorStore` | 不写业务规则 |
| **L5 基础设施** | 运行环境与可运维性 | — | — |

> **这条边界的价值**：`L3 规则引擎` 是**语言无关的纯函数**（现有 `shared/req-lib.js` 已是纯函数 + UMD）。因此**技术栈迁移时它可以整体保留**，只需换一层壳 —— 这是把「重写」降级为「搬运」的关键设计。

### 3.3 关键数据流（以「简历筛选」为例）

```
HR 在筛选台选择岗位
   │
   ▼ L1  校验入参 + 鉴权（是否为本租户、是否有该岗位权限）
   ▼ L2  开启筛选任务（写 agent_tasks，状态 pending）
   ▼ L3  Agent 编排 8 步：
        ① 载入岗位画像（L2 读 jobs）→ ② 识别职能族（规则引擎，
           30 族，0 token）→ ③ 取候选人池
        ④ 【安全】PII 物理剔除：受保护字段在 SQL 里就不出现
        ⑤ 【确定性】规则门槛过滤（年限/学历，0 token）→ 被拦者标原因
        ⑥ 【模型】仅对通过者做证据化打分（每条分数引用原文片段）
        ⑦ 汇总排序 → ⑧ 【人工闸门】停止，生成审批单
   ▼ L2  写入打分结果 + 审计（append-only）
   ▼ L1  返回 SSE 逐步推送的 8 步轨迹
```

**注意第 ④ 步的位置**：**在查询层剔除，而不是在返回前过滤**。前者是「模型拿不到」，后者是「模型拿到了但被要求别看」——这是本项目最核心的合规设计（见 ADR-003）。

## 四、关键设计决策（ADR）

> 每条含：**决策 / 背景 / 备选 / 取舍 / 状态**。这一节是面试追问的靶心。

### ADR-001 · 分类轴用「职能族优先、行业兜底」

- **决策**：先用岗位名识别**职能族**（30 族），识别不到才回落行业词库。
- **背景**：曾出现真实 bug——「互联网行业的 AI 产品经理被补上 Java/Spring」。根因是把「行业」当成「职能」：互联网行业的技能库里第一条就是 Java。
- **备选**：① 只用行业（原始方案，已被证伪）；② 用 LLM 做语义分类。
- **取舍**：LLM 分类更灵活但不可复现、有成本、会漂移；规则分类可复现、0 成本、可回归。**选规则**，且把 `detectFunction` 的命中规则设计为与职责选取同构（岗位名 ×3、正文 ×1）。
- **状态**：① 已实现（`shared/req-lib.js`）。

### ADR-002 · 规则先行、模型兜底（硬判断永不下放）

- **决策**：年限、学历、合规、权限四类硬判断由确定性代码执行；模型只负责**表达与语义理解**。
- **对标依据**：`sliday/resume-job-matcher`（硬约束先淘汰、再打分、分数引用原文）与 `interviewstreet/hiring-agent`（规则快筛 + LLM 语义打分双后端）**独立收敛到同一设计**，说明这是行业共识而非个人偏好。
- **取舍**：牺牲一部分「智能感」，换来可复现、可审计、0 token。
- **状态**：① 已实现（规则门槛 0 token）。

### ADR-003 · PII 物理剔除，而非在提示词里请求

- **决策**：性别、年龄、婚育等受保护字段**在 SQL 查询层就不被 `SELECT`**。
- **备选**：在提示词里写「请不要考虑性别年龄」。
- **取舍**：提示词方案在合规审查面前不成立——「我请求模型别看」与「模型根本拿不到」是两种证据强度。
- **状态**：① 已实现。

### ADR-004 · 词库前后端同源（UMD 单文件）+ 版本自愈

- **决策**：`shared/req-lib.js` 是唯一词库源，后端 `require`、前端由构建脚本内联为 `__REQLIB__`。
- **背景**：曾出现「离线说的和在线说的不一样」——同一个 JD，离线模式与在线模式结论不同。
- **配套**：`REQ_LIB_VER`（前后端共享的素材版本号）+ `jobs.jd_ver`，服务启动时把落后版本的 JD 自动重算回写。
- **取舍**：引入了「版本自愈」的隐性副作用（启动时批量写库），因此**必须包在单事务里**（见 ADR-005）。
- **状态**：① 已实现（当前 `REQ_LIB_VER = 7`）。

### ADR-005 · 批量写库必须单事务（一次真实的线上级故障）

- **现象**：`/api/reset` 耗时 **6.8 秒**，紧随其后的 keep-alive 请求稳定 `ECONNRESET`。
- **根因**：`node:sqlite` **每条语句自动提交**，Windows 上每次 commit 触发 fsync；约 120 条种子写库 = 120 次 fsync，阻塞事件循环数秒，期间空闲连接被断开。
- **决策**：`inTx()` 把 `seed()` / `reseedRuntime()` / 首次建库全部包进**单事务**；启动时的老 JD 自愈 UPDATE 也并成一个事务。
- **结果**：重置 **6.8s → 70–160ms**（约 70×），双模式回归转绿。
- **价值**：**这是「先跑真链路、再交货」的价值证明**——该 bug 是我跑回归时撞出来的，不是用户报的。
- **状态**：① 已实现。迁移到 PostgreSQL 后此问题自然消失，但**事务边界设计**保留。

### ADR-006 · 技术栈选「单一 TypeScript + pgvector」（我的推荐）

- **决策**：Next.js + NestJS/Fastify + PostgreSQL + pgvector + Redis + BullMQ + S3 兼容存储。
- **备选**：② Python 后端（对齐 Resume-Matcher / hiring-agent 生态）；③ 保留零依赖 Node。
- **取舍**：
  - 选 ① 的**理由**：可**复用核心资产**（`req-lib.js` 已是 JS，直接 TS 化即可保住「前后端同源」亮点）；**组件最少**（pgvector 让向量与业务同库，少一个中间件对单人项目意义重大）；面试市场最熟悉。
  - 选 ① 的**唯一硬伤**：Node 侧 PDF/DOCX 解析与中文 NLP 弱于 Python。
  - **折中（待你选）**：① + 一个**可选 Python 解析 sidecar**（只做「文件 → 文本/结构化字段」），两头都要。
- **状态**：**⏳ 待你拍板**（详见 `docs/07` §9-①）。

### ADR-007 · 审计日志 append-only

- **决策**：审计表只允许 INSERT，禁止 UPDATE/DELETE（数据库权限层约束，而非应用层自觉）。
- **对标依据**：OrangeHRM 的「审计追踪」与 Dify 企业版的「审计日志」都把审计列为不可省的企业能力。
- **状态**：① 已实现（应用层只插不改）；**数据库层约束为 ② 设计目标**。

### ADR-008 · 离线 / 在线双模式同源

- **决策**：同一份 `index.html`，双击 = 离线演示态，被后端托管 = 真实态；**两态的结论必须同源**（合规扫描在离线端也是真扫，不写死结论）。
- **理由**：作品集的核心场景是**现场演示**——断网、无后端、临时换机器都不能翻车；同时不能为了演示效果撒谎。
- **状态**：① 已实现（双模式回归各 23 页 + 16 项全绿）。

### ADR-009 · 权限做三层，注册即最小权限

- **决策**：**功能级**（能否访问该 API）× **行级**（只能看本部门/本人的数据）× **字段级**（PII 字段默认不返回，需显式提权 + 留痕）。
- **对标依据**：OrangeHRM 的「角色最小权限 + 行级限制 + 字段级防护」；Dify 企业版的 SSO/RBAC/审计三件套。
- **状态**：⏳ ③ 尚未具备（M1 交付）。

### ADR-010 · 模型走适配器，业务不感知供应商

- **决策**：`Llm.complete()` 统一接口 + 供应商适配器；业务层只声明「要什么能力」，不声明「用谁」。
- **对标依据**：Dify 的**适配器模式**（换模型只改配置，不重构业务逻辑）。
- **配套**：超时、重试退避、失败降级到规则模式、token 记账、输出审计、Prompt 版本化。
- **状态**：🟡 ② 部分（可插拔与降级已有；记账/审计/额度未有）。

## 五、数据模型与权限模型（② 设计目标）

### 5.1 核心实体（现状 13 张表，① 已实现）

| 域 | 表 | 说明 |
|---|---|---|
| 租户与账号 | `tenants` · `users` · `roles` · `user_roles` | 本期单租户，但 `tenant_id` 全表必带 |
| 岗位 | `jobs` | 含 `jd_text` / `keywords` / `must_have` / `jd_ver`（版本自愈） |
| 候选人 | `candidates` · `applications`（阶段机） | 参考 OpenCATS 的候选人阶段建模 |
| Agent | `agent_tasks` · `tool_calls` | 轨迹可回放 |
| 治理 | `approvals` · `audit_logs` | 审计 append-only |
| 知识库 | `kb_documents` · `kb_chunks` | M3 起加向量列（pgvector） |
| 自助 | `leave_balance` · `unanswered_questions` | 未解答问题清单 = 产品自我修复入口 |
| 合规（新增） | `consents` · `retention_policies` | 授权留痕与留存策略（M8） |

### 5.2 权限模型

```
请求 → 会话解析（谁） → 功能级（这个 API 他能不能用？）
                      → 行级（这个 tenant_id / dept_id 的数据他能不能看？）
                      → 字段级（这条记录里哪些字段要脱敏？）
                      → 命中拒绝 → 写审计（谁、何时、想做什么、被拦原因）
```

**关键纪律**：`tenant_id` **永不接受前端传入**，一律从服务端会话推导。现有 PoC 里 `SELECT COUNT(*) FROM users` 这类无租户过滤的查询，属于必须清理的技术债。

## 六、AI 能力层设计（L3 细化）

### 6.1 能力边界：谁做什么

| 任务类型 | 执行者 | 理由 |
|---|---|---|
| 年限 / 学历 / 硬性门槛 | **规则** | 0 token、可复现、可审计 |
| 合规扫描（歧视/违法用语） | **规则 + 法条表** | 必须能给出法条依据，模型给不出稳定依据 |
| 职能族识别 / 职责选取 / 行业语境 | **规则** | 30 族 242 句词库已覆盖，规则命中即答案 |
| 简历字段抽取（非结构化 → 结构化） | **模型 + 契约校验** | 格式千变万化，规则写不完 |
| 语义匹配、要点总结、话术组织 | **模型** | 规则不擅长表达 |
| 知识库问答 | **检索 + 模型** | RAG：检索保证事实，模型负责遣词 |
| 审批、发 Offer、拒信 | **人** | 高风险决策必须有人在场 |

> 一句话：**规则负责「不能错」，模型负责「说得好」，人负责「担责任」。**

### 6.2 模型网关

| 能力 | 现状 | 目标 |
|---|---|---|
| 可插拔 | ✅ `LLM_API_URL` 环境变量 | 适配器 + 多供应商注册 |
| 失败降级 | ✅ 自动回落规则模式 | 保留，并加**熔断** |
| 超时 | ✅ 20s | 分级超时（抽取/生成/问答不同） |
| 重试退避 | ❌ | 指数退避 + 幂等键 |
| 成本核算 | ❌ | 按任务/租户/模型记账，落 `tool_calls` |
| 输出审计 | ❌ | 输入输出留存（脱敏后）+ 可回溯 |
| Prompt 版本化 | ❌ | Prompt 与评测集绑定版本 |

### 6.3 检索 / RAG（M3）

```
文档 → 解析（含 OCR 兜底）→ 切片（按语义边界）→ 嵌入 → pgvector
                                                          │
查询 → 混合检索（向量 + 关键词）→ 重排 → 取 Top-K → 注入上下文 → 模型组织 → 带引用输出
                                                          │
                                        无结果 → 转人工（不编造）+ 记入未解答问题清单
```

对标依据：Dify 与 RAGFlow 均采用「多路召回 + 重排序」；无召回时**转人工而非编造**是本项目的硬纪律。

### 6.4 可评测性（M4）

| 项 | 设计 |
|---|---|
| Golden Set | 3–5 类任务 × 20 样本（含对抗样本：诱导歧视、跨职能技能污染、管培生年限） |
| 指标 | 任务成功率、证据引用正确率、越权拦截率、拒答准确率 |
| 门槛 | 低于阈值**阻断合并**（而非仅告警） |
| 回归 | 与双模式无头回归（23 页 + 16 项）并行 |

## 八、迁移路径：从现有 PoC 演进

**原则：不推倒重来。** 现有 PoC 是**可运行证据**，本身有演示价值，必须保留到新架构完全跑通为止。

```
阶段 0（现状，① 已实现）
  零依赖 Node + SQLite + 单文件前端 + 双模式回归全绿

阶段 1 · 抽离内核（低风险，先做）
  把 shared/req-lib.js 升为独立的「规则内核」包：
  ── 纯函数 + 契约测试（现有 21 岗位快照作为金标准）
  ── 语言无关，迁移时可整体搬运
  同时：把「规则内核」与「HTTP 层」解耦，为换栈做准备

阶段 2 · 换数据层（中风险）
  SQLite → PostgreSQL + 版本化迁移脚本（Prisma/Drizzle）
  ── 字段映射：JSONB ↔ TEXT(JSON)、UUID ↔ TEXT
  ── 顺带清理无租户过滤的查询
  ── 保留 SQLite 模式作为「离线演示」后端（双后端，按开关切换）

阶段 3 · 补可信底座（M1）
  自建账号 + 会话 + 三层 RBAC + 加密 + 审计增强

阶段 4 · 补能力层（M2–M4）
  文档处理 → 向量检索 → 模型网关增强 → 评测集与门槛

阶段 5 · 可运维（M5 之后）
  容器化 + CI/CD + 备份恢复 + 日志/指标/追踪
```

**每一步的出口条件**：双模式回归全绿 + 演示脚本可完整跑通。**出现任一失败即回退**，不允许「迁到一半不能演示」。

## 十、技术选型对照与未定项

### 10.1 选型对照（含备选与理由）

| 层 | 推荐（我的选择） | 备选 | 理由 |
|---|---|---|---|
| 前端 | Next.js（App Router） | 保留单文件 HTML | 生产要 SSR/路由/代码分割；**单文件保留为演示包** |
| 后端 | NestJS 或 Fastify + TS | FastAPI（Python） | 与前端同语言，复用 `req-lib.js` |
| 数据库 | PostgreSQL | MySQL | JSONB、pgvector、生态与迁移工具成熟 |
| 向量 | **pgvector** | Milvus / Weaviate / Elasticsearch | **少一个中间件**；数据量级（百万级切片以内）足够 |
| 缓存/队列 | Redis + BullMQ | RabbitMQ / Kafka | 单人项目不需要 Kafka 的复杂度 |
| 对象存储 | S3 兼容（MinIO 私有化） | 本地磁盘 | 简历原件必须可加密、可审计访问 |
| ORM/迁移 | Prisma 或 Drizzle | 手写 SQL | 版本化迁移是 P2 缺口，必须补 |
| 校验 | Zod | — | 前后端共用 schema |
| 认证 | 自建会话 + Argon2id | Auth.js / Keycloak | 你要「自建账号 + RBAC」，不引入重型 IdP |
| 模型 | 国内已备案 API + 本地适配器 | 纯云端 / 纯本地 | 合规优先，同时保留离线能力 |
| 容器 | Docker Compose | K8s | 单机/单容器足够，K8s 属过度设计 |
| CI | GitHub Actions | — | 跑双模式回归 + 评测门槛 |
