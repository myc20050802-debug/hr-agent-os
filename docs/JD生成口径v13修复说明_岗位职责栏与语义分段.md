## 一、这次修了什么（每条都有真实复现样本）

### 1. 行业语境句错配（语义错位 · 最严重）

**复现**：生成「采购工程师 × 制造业」的 JD，职责第 7 条是——

> 围绕**良率、OEE** 与交付准时率等现场指标开展复盘，推动**瓶颈工序**改善

采购岗不背良率。根因：`industryDuty()` 只做「是否重复」判定，从不判定「是否适配」——
行业语境句是按「该行业**主力职能**」写的，同行业的非主力职能拿到手就是错位的话
（同理：医疗行业的语境句是护理口径，拼给医疗行业的财务岗同样错）。

**修法**：`INDUSTRY_CTX` 每个行业新增 `fit` 白名单（该语境句适配的职能族），
`industryDuty(industry, duties, fnKey)` 增加适配闸——职能不在白名单或认不出职能 → 整句不拼。

**修复后**：采购工程师（制造业）职责恢复 6 条纯职能口径；生产主管（制造业）仍保留行业句（防一刀切误伤）。

### 2. 管培生岗位被补资深加分项（自相矛盾）

**复现**：「门店储备干部」（管培生口径，不设年限门槛）的加分项：

> 有**从 0 到 1 开新店或带店扭亏**的经验者优先；有单店业绩持续增长的量化成果者优先

招的是应届生，给的却是社招资深门槛——和「工作经验：无需相关经验」直接打架。

**修法**：`junior`（管培生/实习/应届）时过滤模板池中的资深句式
（`从 0 到 1 / 主导 / 独立负责 / 带店 / 扭亏 / 多年 / 资深…`），不足再用管培生专属池补齐
（实习经历 / 学生干部 / 校园项目竞赛）。**只在认出职能族时启用**——守住「认不出职能一律不补加分项」的既有铁律（test_jd 第 8 节继续锁死）。

### 3. 专业技能补位句「四连同款尾缀」（重复感）

**复现**：任何岗位的「专业技能」段都是——

> 熟悉需求分析，**能独立应用于实际业务场景**；熟悉 PRD 撰写，**能独立应用于实际业务场景**；熟悉用户研究，**能独立应用于实际业务场景**……

像机器批量生成。

**修法**：尾缀按序号轮换 4 种（`能独立应用于实际业务场景 / 并在真实业务中完整落地过 / 能独立完成该方向的日常工作 / 并了解常见的实践方法与工具`），确定性取模、同岗位产出可回归。
⚠️ **`AUTO_FILL_RE` 已同步扩族**——往 `SKILL_TAILS` 加尾缀必须同步它，否则 `stripMisfitAutoFill` 认不出自动产物，跨职能族历史错配（非技术岗里的「熟悉 Java」）会洗不掉。前后端两处同源实现已一起改。

### 4. 整段粘 JD 时末行条目被吞（内容丢失）

**复现**：粘入的 JD 以「加分项 → 有短视频策划经验更香」结尾，这条加分项**直接消失**。
根因：末行含「更香」，命中小标题词表且 ≤12 字 → 被小标题启发式判成标题，整条吞掉。

**修法**：裸行判标题必须「后面还有内容」；两个例外不受影响——
①「标签：内容」整行（自包含，照常拆分）；② 文末纯标签行（「加分项」这类 ≤6 字孤立标题）静默丢弃。
连带修复：`RE_NICE_DONE` 补「更具优势」（「更香」的书面化产物），否则会产出「…更具优势**者优先**」双后缀。

### 5. 生成 JD 全文的其他语义检查结论

对 AI 产品经理 / 供应链采购专员 / 储备干部 / 新媒体运营四类岗位全文核查，其余模块（引言、六维度要求、加分项、福利、EEO 声明）分段与语义无残句、无乱序；职责与要求的「一条一事、动宾开头、25–50 字」口径在 v12 已锁，本次未发现新违例。

## 二、新功能：岗位职责栏

### 用法

JD 工作台「任职要求」上方新增**「岗位职责」**多行输入框：

- **留空** → Agent 按职能族生成（`pickDuties` 按岗位名/已填要求挑最贴近的 6 条 + 行业语境句），与原默认逻辑一致；
- **已填** → **以你的内容为准**：条目全部保留、排在最前，经书面化润色（白名单，不命中原样透传）；
  只有 1–2 条时从职能模板**尾部补足**到 6 条（丰富细节，不替换、不掺前进位）；
- 支持整段粘贴（含「你会做什么」小标题），条目边界与任职要求同一套规则（换行 + 行首列表符，逗号分号顿号永不分条）。

### 持久化（这次的关键设计决策）

职责**不进打分关键词通道**（`must_have` 里没有它），所以必须单独落库，否则「编辑保存」和「词库自愈重算」都会把它静默替换成职能模板：

| 层 | 改动 |
|---|---|
| schema | 迁移 **v8 `job_duties`**：`jobs` 表加 `duties` 列（JSON 数组，只存用户内容，模板补足的不存） |
| 生成 | `runJD` 接收 `duty` → `parseDutyInput()` 统一解析 → 传 `buildJD` 的 `userDuties`（显式传入 > 库里持久化 > 粘文解析） |
| 落库 | `runJD` / `createJob` / `updateJob` 全部读写 `duties` 列；`updateJob` 把「传了空」视为「本次没填」而非「清空」（与 mustHave 合并语义一致） |
| 自愈 | `bootstrap` 重算 JD 时带着 `duties` 列——词库升级不再丢用户职责；`bootstrap` 同时把 `duties` 下发前端供「载入岗位」回显 |
| 离线 | `src/agent.js` 的 `generateJD` 同口径支持 `input.duty`，离线/在线产出一致 |
| 前端 | 工作台表单新栏 + `loadJob` 回显 + `saveJdAsJob` 随 JD 带入岗位表单 + 结果区「Agent 依据」行说明职责来源 |
