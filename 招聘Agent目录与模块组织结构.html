招聘 Agent 目录与模块组织结构

版本 v1 · 2026-09-29 · 适用范围：平台原型/src/app.js 导航层 一句话：把散落的 5 个招聘 Agent 收进一个招聘 Agent 目录，内部按招聘流程阶段分成 4 个模块。

一、为什么要动这个结构

改动前，5 个招聘 Agent 和「入转调离 / 员工自助 / 人力报表 / Agent 编排」平铺在同一个「智能体中心」分组里：

text
智能体中心
  📝 招聘 Agent · JD 工作台
  🎯 招聘 Agent · 简历筛选台
  📨 招聘 Agent · 邀约与调度
  🎤 招聘 Agent · 面试辅助
  📄 招聘 Agent · Offer 前置
  🔄 入转调离 Agent
  💬 员工自助 Agent
  📊 人力报表 Agent
  🧩 Agent 编排

三个具体问题：

问题表现后果
前缀重复「招聘 Agent ·」在一列里出现 5 次侧边栏信噪比低，扫读时眼睛要跳过同样的 8 个字才能看到区别
层级缺失招聘是唯一成体系的域，却和单点 Agent 同级看不出「这 5 个属于同一条业务链」，也看不出它们的先后顺序
扩展无处安放新增 Agent 只能继续往这一列里塞侧边栏迟早变成一条谁也不敢动的长名单；且没有「该放哪」的判断依据
一个补充发现：docs/01_产品需求草稿PRD.md 第七部分的菜单结构里，招聘 Agent 本来就写成「招聘 Agent → JD 工作台 / 简历筛选台 / 邀约与调度 / 面试辅助 / Offer 前置」的两级形态。也就是说这次改动不是发明新结构，而是让实现对齐回 PRD 的设计，并在中间补上「模块」这一层——此前的实现为了省事把两级压成了一级，PRD 里的层级关系在界面上丢失了。

二、目标结构：三层导航模型

分组（group） → 目录（catalog） → 模块（module） → Agent（页）

text
智能体中心                                    ← 分组（原有概念）
└ 🎯 招聘 Agent                    [目录]     ← 可折叠的一级容器
   ├ 岗位与需求                              ← 模块（本模块的标题）
   │  └ 📝 JD 工作台
   ├ 筛选与评估
   │  └ 🎯 简历筛选台
   ├ 面试与协调
   │  ├ 📨 邀约与调度
   │  └ 🎤 面试辅助
   └ 录用与入职
      └ 📄 Offer 前置
  🔄 入转调离 Agent                           ← 非目录节点，仍按叶子渲染（行为不变）
  💬 员工自助 Agent
  📊 人力报表 Agent
  🧩 Agent 编排

三个设计选择，都是有理由的：

  1. 目录只做一层。没有做无限嵌套——一层目录 + 一层模块已经能表达「域 → 阶段 → 工具」，再深就变成文件树，侧边栏不是资源管理器。
  2. 只把招聘做成目录。其余 4 个 Agent 目前是单点能力（每个只对应一个页面），硬拆成目录只会得到 4 个各含 1 个模块的空壳。目录是给「成体系、会继续长」的域准备的。
  3. 页面 id 一个都没改。jd / screen / invite / interview / offer 原样保留，所以权限、路由、测试、深链全部零回归。

三、模块划分依据

划分标准只有一条：按招聘业务流的时间顺序，不按技术实现、不按前端文件名、不按公司部门。

为什么：按流程划分时，业务同事和工程师能对着同一张表说话。新人要加一个 Agent，只需要回答一个问题——「它落在招聘的哪个阶段」。
模块业务阶段归类判据（一句话）现有 Agent可预见的扩展位
岗位与需求提出用人需求 → JD 成稿产出物是「岗位要什么」📝 JD 工作台岗位画像、职级带宽评估、招聘需求审批
筛选与评估收到简历 → 给出排序结论产出物是「人对岗位的匹配结论」🎯 简历筛选台笔试/测评编排、背景调查前置、人才库激活
面试与协调约面 → 面试结论落库产出物是「面试这件事本身」（日程 + 结论）📨 邀约与调度、🎤 面试辅助面试题库、面试官评分校准、面试官排期约束
录用与入职决定录用 → 入职前置产出物是「Offer 与入职动作」📄 Offer 前置薪酬测算、Offer 谈判建议、入职材料收集

边界示例（拿不准时用这个判）：

  • 「简历打分」→ 筛选与评估 ✓；「面试评分表」→ 面试与协调 ✓（前者评的是纸面材料，后者评的是当面表现）
  • 「薪酬测算」→ 录用与入职 ✓，不放筛选与评估——它依赖的是录用决策，不是匹配结论
  • 「背调」→ 筛选与评估 ✓（它发生在发 Offer 之前，结论反过来影响录用）

六、新增一个招聘 Agent 的 checklist

按顺序过，缺一项就会留下隐患：

  1. 归类：先回答「它落在哪个阶段」→ 写进 RECRUITING.modules[?].items，一行：{ id, ico, name, perm }。
  • 若都不属于现有 4 个阶段 → 在 modules 里新增模块，插在流程顺序对应的位置（不要追加在末尾）。
  1. 页面：在 app.js 里实现 PAGES.<id> = () => ...。
  2. 权限：先在 server/rbac.js 的能力清单里加码，再用它填 perm。
  • 只有新能力属于既有角色时，同步更新该角色的能力数组；否则新页对所有角色都不可见。
  1. 接口（需要真后端时）：在 server/routes.js 注册，need 用第 3 步的同一个能力码。
  2. 测试：把新 id 加进 平台原型/test_prototype.js 顶部的 ids 数组——不加就不会被逐页渲染用例覆盖，这是最容易漏的一步。
  3. 打包：node 平台原型/build.js。
  4. 回归：跑下面三条（见第八节）。

七、设计决策与取舍

决策理由代价
目录不挂 perm，可见性由子项聚合若目录按自己的 perm 判可见，只有 screen:run 的招聘专员会连目录带「简历筛选台」一起消失——丢的是功能，不是权限目录可见性判断多一层递归（已在 nodeVisible 里封装）
模块下全部页面不可见时，模块标题一起隐藏避免留下一个点不开任何东西的空标题无
折叠状态持久化到 localStorage只跑「简历筛选台」的人不想每次都被整列招聘菜单占地方file:// 双击演示时 localStorage 不可用 → 已用 try/catch 兜底，退化为「本次会话内有效」
跳转到目录内页面时自动展开该目录否则当前页在侧边栏里是「隐身」的，用户会觉得导航坏了用户手动折叠的意图可能被覆盖——只在跳到该目录内页面时覆盖，可接受
侧栏收起 / 窄屏时目录恒展开只剩图标的情况下还要求先点开目录才见得到子项，等于把「一步进入」变成「两步」窄屏下模块标题隐藏，层级感减弱（可用空间换的）
页面 h2 标题保留全名页面内部没有目录上下文，去掉前缀反而不清楚与侧边栏短名存在表述差异，属有意为之
目录头也是 .navitem（role=button / tabindex=0 / aria-expanded）键盘用户必须能用 Enter 收起它；无障碍最小集里「导航项必须可聚焦」对它同样成立无

九、后续可做的事（未做，供决策）

  1. 「智能体中心」下其余 4 个 Agent 的归位：入转调离 / 员工自助 / 人力报表 / Agent 编排 目前仍是平铺。PRD 里它们各自也有 3–5 个子页，若将来真正展开，应各建目录（如「员工服务 Agent」目录含入转调离 + 自助 + 报表）。
  2. 侧边栏搜索：Agent 数量到 15+ 时，纯靠层级浏览会变慢，应支持按名称过滤。
  3. 代码层的目录化：app.js 已 3100+ 行，5 个招聘页面仍住在同一个文件里。若继续增长，可按模块拆成 平台原型/src/agents/recruiting/*.js（现有 build.js 的内联机制支持扩展脚本列表）。
